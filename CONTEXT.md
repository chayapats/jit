# Jit

Jit is a single-owner, self-hosted assistant with a team of persistent Bots, durable work and sourced memory. Schway is its execution engine.

**Product target:** [S16](docs/specs/S16-rakazo-experience.md) is the owner-confirmed direction as of 2026-11-05: deliver the Rakazo-style persistent teammate experience comprehensively, retaining Jit + Schway and adapting useful upstream code/concepts. Files/artifacts, general browser/desktop work, connections/MCP/plugins/skills, delegation/routines/memory, voice and Web/desktop/mobile clients have required acceptance coverage. The owner explicitly permits changing existing stacks and incidental constraints for a simpler or better result; [ADR 0074](docs/adr/0074-rakazo-reuse-and-product-convergence.md) records engineering alternatives and reuse/license boundaries. Concrete stack choices are proposals, not accepted implementations.

**Retained authority baseline:** [S15](docs/specs/S15-conversational-autonomy.md), confirmed 2026-11-02, establishes normal conversational work within standing policy, shared team resources, automatic sourced memory and protected human-required gates. Product-default GitHub publication requires approval; an explicitly configured personal workflow may publish, remediate and auto-merge eligible selected work, while production still waits. S16 does not silently replace these owner decisions or turn a current static-browser limitation into the product ceiling. [ADR 0064](docs/adr/0064-conversational-authority-and-protected-control-plane.md) retains its versioned proof obligations; imported upstream source is never execution authority.

**Implemented runtime:** New unconfigured source runs/installations still default to [S14](docs/specs/S14-bot-first-local-assistant.md). Original architecture ADRs 0045–0048 remain proposed and are refined by accepted scoped implementation ADRs 0049–0063; their status does not certify an untested build. The project-centric S09–S13 runtime is retained through explicit `--legacy` and existing legacy service configs. The separate [owner-Pi cutover evidence](docs/evidence/s14-owner-pi-cutover.md) records the actual first reply, full legacy-byte preservation and prior-release rollback at `5eec7aa`, including complete post-reply R4 equality. Do not infer S15 implementation, another host's acceptance or permission to reinterpret existing private data from the new target. No hidden Project is an authorization root.

## Product language

S15/S16 target terms below refine product intent. Definitions explicitly marked S14 retain their versioned implementation meaning until replacement contracts land; existing commands/stores are not reinterpreted by editing this glossary.

**Owner:** The authenticated person who configures the installation, accepts obligations and grants execution or external actions. Model output, source content and inferred identity are not an owner.

**Installation:** One owner's local application state, configuration and services. It is not a multi-user tenant.

**Bot:** A persistent participant with a stable identity, responsibility, enabled generation, selected model/auth route and capability policy. It is not a model, provider session or container. Creating a permanent Bot requires owner acceptance of its exact proposal.

**Jit (main Bot):** The default conversational assistant and coordinator. It understands requested outcomes, chooses tools and approved team/model resources, and remains responsible for authorized work and evidence. It cannot widen policy or approve its own held actions. In implemented S14, coordinator-only chat has no tools or warm computer; work uses its separate grant path.

**Team:** Bots using installation-approved work resources/accounts for the assigned purpose. S15 defaults to shared team access without repeated per-Bot setup; explicit narrower restrictions still apply. This does not retroactively declassify S14-private sources or expose raw session/credential material.

**Working VM:** The dedicated computer for S15 execution and ordinary administration. By default (owner decision 2026-11-03) it is a nested KVM guest that Jit creates and manages on the controller host; owner-supplied VMs remain an optional enrollment path for extra compute. It is not the owner's everyday desktop or the protected control plane. RT15-01 option B (2026-11-03) accepts full guest root and expendable guest loss with protected snapshot recovery, not prevention; valuable originals, credentials and external-effect gates stay outside it. The opt-in VM module retains guest-reported cooperative scoped settlement versus strong hypervisor-stop settlement. Exact host adoption remains separate under ADR 0064.

**Protected control plane:** The authority/state/credential/effect boundary that working agents, including a guest administrator, cannot alter or impersonate. Physical placement and enforcement are proposed engineering, not established by a sibling process or a prompt.

**Standing policy:** Authenticated owner configuration of purposes, team resources, action classes, allowed routes/models, finite budgets and human-required gates. It avoids repeated per-task setup without authorizing a different task. A personal exception is explicit configuration, not the product default or a grant embedded in this repository.

**Default standing-policy proposal (S15, POLICY15-02):** The first standing policy Jit offers on an installation with no configured policy. It is derived from what the installation actually has, with the product-default gates and a finite, renewable expiry. It is only a proposal: the owner's one exact press installs it, and a changed resource set produces a new proposal instead of changing installed rules. See ADR 0073.

**GitHub connection (S15, GIT15-04):** The owner's Web-pasted fine-grained token, held only in the protected vault, plus the revisioned list of repositories the owner selected for Jit. Selected repositories become team resources and default-proposal rows. The connection grants no publication; the product-default and personal GitHub profiles decide that.

**Persona:** Owner-authored configuration of address, language and tone. It is trusted configuration, not model-authored memory.

**Bot proposal:** A revisioned draft for creating or changing a permanent Bot. Accepting it does not grant accounts or wider tools.

**Conversation:** A durable discussion with one or more Bot participants. Membership, a display label and an @mention do not grant execution or resource access.

**Shared client (S16, API16-01):** The browser/native-safe transport and ephemeral projection state over the existing protected Jit service. It submits exact owner commands, reads currently authorized snapshots/control events, recovers the original send identity and reviews exact actions. It is not a second authority, engine or store. The [client contract](docs/contracts/s16-client-v1.md) supports text/tool work and exact decisions. Explicit file composition additionally supports the first [UTF-8 file-to-artifact workflow](docs/contracts/s16-files-v1.md) and React `/s16` client; an explicit strict parser configuration additionally supports [isolated PDF/PNG/JPEG inputs](docs/contracts/s16-binary-files-v1.md) through actual guarded Schway image sends. File-derived memory and live steering remain unavailable; Linux isolation and live-account vision evidence remain separate pending acceptance.

**Work item:** A proposed or owner-requested obligation with a status, explicit completion rule, origin and evidence. A work item may involve multiple Bots and conversations without becoming a Project.

**Responsibility (S15 opt-in):** An authenticated conversational assignment retaining its original purpose, selected subject, completion rule and current policy authority across bounded attempts and durable waits. Waiting holds no VM/native session; interrupted effects reconcile before new attempts. A measured stall pauses this responsibility with evidence and a recommendation while other authorized work continues. See `src/s15/work/` and `docs/contracts/s15-responsibility-v1.md`.

**Stall-reply resume binding (S15 opt-in, WORK15-02):** A durable protected record that an owner's reply to a paused responsibility should resume it once that reply's own CHAT request completes. It is created with the reply, settles at most once in the service drain (after restart, without a page view) and only through WORK's resume checks. It names the responsibility; it is not authority, and model output or quoted text cannot create one. See `src/s15/work/resume.ts`.

**Bound owner channel (S15 opt-in, CHAN15-01):** A companion transport, currently Telegram, bound to the owner's stable numeric account and private chat by a one-time code issued in the authenticated Web UI. Bound messages are ordinary owner conversation requests under the same standing policy; the channel also notifies. It never approves held actions, installs policy or widens scope; approval stays on the exact Web slip. See ADR 0072 and `src/s15/telegram/`.

**Task acceptance:** The owner's decision to retain an obligation. Acceptance alone does not start execution.

**Work command:** An authenticated owner action requesting execution. In S15, ordinary conversation can request work within standing policy without Work mode; inspect/recommend requests still authorize only inspection/recommendation. In S14, typed work.start creates work plus its grant; message.post does not. Models and quoted/retrieved content cannot mint or widen authority in either version.

**Work grant:** A revisioned owner authorization for a purpose, allowed Bots/resources/tools, finite budgets and expiry. Effective access intersects it with current Bot and resource policy. A grant is not a model plan, task acceptance or conversation membership.

**Capability policy:** The owner-controlled ceiling on a Bot's tools/resources. A model may restrict it but cannot widen it. A work grant does not bypass the ceiling.

**Delegation:** A bounded assignment to an enabled Bot under the originating authority and current restrictions. S15 may use team-shared approved resources without another sharing ceremony. It grants no new purpose, account, provider or permanent Bot. S14 retains its per-Bot capability/share intersection.

**Context handoff:** A labelled subset of accessible command, evidence and memory references supplied to a delegated run. It is not unrestricted transcript/session sharing.

**Job:** A bounded, authorized unit of background execution, separate from an owner's obligation.

**Run:** One invocation of Schway for an assigned analysis or synthesis, with independent native ownership and finite limits. A persistent Bot may have many runs.

**Attempt:** One fenced admission of a job/step with immutable input/configuration/authority and recorded usage reservations.

**Work step:** A typed, bounded node in a trusted work graph. Its handler, not a model declaration, defines validation, resource leases and replay safety.

**Routine:** An owner-authorized standing purpose with selected resources/Bots/tools, schedule/timezone/misfire policy and finite limits. Findings outside it are proposals, not new execution authority.

**Decision:** A conclusion explicitly selected by the owner, retaining the proposal and evidence it resolves. An agent vote or recommendation is not a decision.

**Memory claim:** A retained statement with source/revision, originating Bot/conversation, fact-or-inference status and lifecycle state. It is not the entire transcript or unqualified truth.

**Shared memory:** Relevant sourced facts, preferences and working knowledge available to the authorized team. S15 standing policy authorizes automatic retention with fact/inference and correction/forget lifecycle; it never grants execution power. S14 requires its existing explicit publication/share path, and existing private data is not silently promoted during transition.

The opt-in S15 TEAM/MEM implementation now retains relevant sourced subsets automatically under protected retention policy. A correction creates a new owner-sourced claim while preserving inherited private/resource ceilings; forget suppresses source replay and retires dependent contexts/results. Claims, including owner-stated facts, remain data with no execution authority. S14 publication/share semantics and private data are unchanged.

**Bot-private memory:** Claims scoped to one Bot. Retrieval and context assembly enforce that scope before relevance selection.

**Source:** A revisioned owner/external evidence snapshot with provenance and lifecycle status. Attempt-derived sources retain their producing attempt's Bot/resource/computer fences through every descendant, including uncited handoff text. Source text is data and never expands authority.

**Share grant:** An explicit, revisioned permission for a named receiver/work scope to use a specified immutable source/artifact snapshot. S14 requires this for its cross-Bot private content. S15 team-approved resources do not require repeated sharing; explicit restricted-content releases still need their proper authority. A snapshot share is not a whole-volume or raw-account-session grant.

**Context packet:** A self-contained labelled input with current owner decisions pinned, accessible evidence, source revisions and purpose. Native history alone is insufficient.

**Report:** A committed, revisioned work result whose claims reference the evidence actually read and whose coverage/limitations are explicit. Ready for review does not imply complete source coverage. Owner acceptance is a separate exact-revision fact; a newer report or withdrawn lineage invalidates it without changing evidence coverage.

**Artifact:** A bounded immutable output with an opaque ID, hash, type, size, producing work/attempt and source lineage. A file in a box is not automatically a delivered artifact.

**Bot computer (S14):** A persistent logical computer on the owner's host, with isolated workspace/browser components and finite resources. Identity survives idle process stop. Each process/input generation fences prior handles and associated late results. S15's working VM/team default replaces the product requirement for a private computer per Bot, not this implemented record's meaning.

**Execution box:** The isolated workspace/process boundary of a Bot computer. No Jit/provider/channel/vault credentials, application state, backups, host home or control socket enter it.

**Browser profile:** Website session state in a protected browser component. S15 permits mediated team use of approved accounts; raw cookies/tokens remain outside working shell/MCP/prompts/exports. S14 profiles remain Bot-private. Website login is not permission to bypass action approval.

**Approved website (S15):** An exact public HTTPS origin the owner added in the Web (Resources → Websites). The protected browser may read it with credential-free GET navigations; unlisted origins are refused. It is not a sign-in, a send/payment approval or consent to disclose private data, which keep their own gates.

**Runner:** The agent-free execution process behind Jit's computer backend. Schway core tools use the supported ExecutionBackend; no host-shell fallback is implied.

**Input lease:** A generation-bound exclusive right to send input to one browser/desktop. Reads/screenshots do not imply input ownership.

**Takeover:** Owner control of a Bot browser/desktop while agent input is fenced. Returning control is not approval of a held effect.

**External effect:** An action leaving the execution boundary, including remote edits, communications, publication, payments and deletion. S15 distinguishes ordinary reversible authorized edits, narrowly captured standing exceptions and human-required actions. S14 retains exact-effect approval contracts. Unknown tools/actions cannot bypass the applicable mediation.

**Human-required action:** An action held for owner authority under current policy: outbound communication without a standing exception, a general financial transaction, production deployment, a new private-data recipient or an unapproved major change. Final approval binds the actual action; captured recurring/standing rules remain purpose/resource/amount/frequency bounded.

**Disclosure lineage (S15 opt-in):** The protected source/resource revisions and public/private/personal/business restrictions accumulated by work. Derived text, screenshots, artifacts and shared-VM inputs inherit ancestry even without citations. An exact new-recipient approval releases one prepared disclosure and never declassifies the source or approves that recipient generally. Registry destination control does not prevent content/covert-channel disclosure through allowed destinations; see [s15-private-data/v1](docs/contracts/s15-private-data-v1.md).

**Major change:** A change with destructive/bulk or difficult-to-reverse data impact, authority/authentication/credential/approval impact, breaking dependent API/behavior, important service restructuring or a new business obligation. Impact, not changed-line count, determines the need for an unresolved owner decision. Investigation can proceed inside existing authority.

**Approval card:** A revision-bound, single-use, expiring owner decision for one exact external action/content/destination. It is not a task acceptance or model confirmation.

**Repository grant:** An owner-controlled revisioned resource binding one Bot, exact repository origin and commit, optionally an explicit registry host scope. It is not repository content or a model plan.

**Registry scope:** An off-by-default exact registry host allowlist for boxed dependency/test commands. It can disclose workspace data to allowed registries through package requests; it never includes a service credential or general internet authority.

**Connection:** Owner-controlled credentials/account metadata kept outside prompts and execution boxes, usable only through a scoped service broker. Website session profiles remain a separate sensitive boundary.

**Kill switch:** A Bot/installation control that fences work, stops affected computers and blocks admissions until the owner resumes. Cancelling one work item does not cancel unrelated grants.

**Replay-safe step:** A step whose trusted handler can prove safe repetition under the same live authority, immutable inputs and remaining budget. Model intent or readOnlyHint alone is insufficient.

**Unknown effect:** An external action whose outcome cannot yet be determined. It is reconcile-only and never a reason to blindly retry.

**Auth route:** The selected provider identity/billing path, with model selection kept separate. S15 may choose model/effort within approved route/model policy and budget while honoring pins and recording choices. New providers, account changes and new billing require owner approval. S14 retains its exact selected-route/model behavior without silent fallback.

**Configured access:** A local credential/endpoint setting without proof of live readiness. It is not verified support.

**Schway session:** An opaque durable native conversation with workspace/branch identity. It is not a Bot, conversation, work grant or Jit scheduler.

**Outbound read:** A service-owned search/public URL read with bounded query/URL, audit and untrusted evidence. Local execution still sends necessary queries/URLs to Parallel.

**Quiet run:** A scheduled run with typed no_update outcome: retained history, no notification. It cannot hide a failure.

**Attention level:** Per-channel owner policy for notifications. It changes delivery, not report visibility or authority.

**Result contract:** Status, Result, Evidence and an actionable unblock reason when needed. A model's done text is insufficient.

**Attachment:** An owner-supplied file sanitized out of process and always treated as untrusted data. Its contents cannot configure tools, routes or grants.

**MCP proposal:** A revisioned source/version/command or endpoint proposal accepted by the owner. An advertised tool or readOnlyHint does not itself grant access.

**Local API:** An owner-enabled loopback API/CLI over the same authorized commands. It is not a general host shell.

**Webhook trigger:** A signed wake-up for already-authorized work. Its payload is data, not a mandate.

**Managed backup:** A credential-free versioned application/artifact image with opaque native snapshots, reconciled before activation.

**Lifecycle ledger:** Append-only identity records of deletion/forget outside backup images, used to prevent restored data from resurrecting withdrawn material.

**Installation upgrade / quarantined restore:** Owner-authorized staged validation, fencing, recovery point and atomic activation before workers resume. A fresh S14 store is not permission to erase or reinterpret a legacy installation.

S14 personal-effect refinement (#278): a committed run can end while an exact pending card keeps its work waiting on the owner; this retains only held-effect authority, never a right to resume model tools. Calendar update/delete binds an actually-read source and service-verified event version into that card. Personal source presentation does not change its privacy, and any bounded ingestion omission remains a visible coverage gap that cannot be a quiet no_update. See ADR 0057 and the personal/effect contracts.

S15 policy/payment refinement (#320/#333): `src/s15/policy/index.ts` is an explicit opt-in protected service with authenticated owner ingress, bounded durable work actors, finite model/effect reservations, exact prepared revisions/approvals, unique pre-I/O claims and unknown/reconcile-only outcomes. Its separate current ledger is never an S14 store or ordinary backup projection. `src/s15/payments/` supplies only a no-network fixture port and separately approved bounded recurring rules; operating budget does not authorize payments. The owner accepted RT15-01 option B on 2026-11-03: root in an expendable working VM, with valuable originals, credentials, publication and external effects protected outside. Host/browser/egress proof, runtime adoption and approval UX remain separate. See ADR 0066 and the standing-policy contract revision 2.

## Historical terms

**S15 installation:** The separate `jit-s15` installation that `install.sh --s15` creates (CUT15-01): its own controller identity, generated credential-free `s15-runtime/v1` config, fresh state, release link, unit and journald namespace beside, never instead of, the `jit` and `jit-s14` installations. The working computer's QEMU runs as the separate unprivileged `jit-s15-vmm` identity, which the controller reaches only through one argv-fixed launcher (VM15-03). Selecting S15 never reinterprets another installation's config or data. See `docs/runbooks/s15-install.md`.

**S15 staged adoption:** Explicit protected maintenance of one named S14 installation. Original bytes remain in place under the prior build's fence; a separate store retains restricted history, current withdrawals/effect/request continuity and nonrefundable usage. POLICY starts empty and needs an owner-installed proposal. Worker release is separate from activation; activity is durably recorded before admission/dispatch. Pre-activity rollback reselects unchanged originals; newer unrepresentable S15 facts refuse rollback under fences. Legacy continuity has no implicit mapper, omitted runtime remains legacy, and live host adoption/acceptance is separate. See ADR 0065 and `s15-state-transition/v1` revision 2.

Project, Project group, Topic promotion and General system project describe the implemented v1 model and historical specs. They are not required S14 entities, hidden permission scopes or aliases for a work item. Old sources retain their historical meaning in the old store; S14 requires no conversion.
