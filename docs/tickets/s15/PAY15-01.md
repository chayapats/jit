## Deliverable
A provider-neutral protected transaction flow holds final financial details and accepts recurring exceptions only within the approved payee/amount/frequency rule.

## Implementation steps
1. Define transaction/account/currency/amount precision, quote/version and purpose fields in a versioned protected payment-port contract.
2. Implement exact final approval and finite recurring-rule accounting with a scripted payment adapter; keep provider credentials external.
3. Enforce changes in payee/amount/currency/account/frequency, duplicate requests and unknown outcomes conservatively.
4. Keep real payment providers unavailable until a separately reviewed adapter/account/recipient scope and live opt-in evidence exist.

## Acceptance criteria
- [ ] A general invoice/purchase/transfer request never pays before final transaction review.
- [ ] A current recurring rule permits only its exact allowed payee/account/currency, ceiling and frequency.
- [ ] Operating compute budget cannot be repurposed as general spending or silently open a subscription.
- [ ] No bank/payment provider support or spending amount is invented by this implementation.
- [ ] Unknown settlement cannot be retried as a new payment.

## Tests and evidence
1. Scripted exact-approval and recurring-rule boundary fixtures -> allow/hold/deny.
2. Concurrent frequency/budget reservation, decimal/currency mismatch and stale quote fixtures -> conservative refusal.
3. Interrupted settlement/idempotency fixtures -> reconcile-only; no live money moves.
