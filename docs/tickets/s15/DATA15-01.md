## Deliverable
Private data cannot leave through a new recipient disguised as a browser read, upload, shell/MCP request or model call; approved recipients remain usable.

## Implementation steps
1. Freeze the disclosure classification, exact recipient/scope/revision and approval contract from the reviewed external boundary.
2. Mediate outbound work-plane and protected-service paths, including redirects, uploads, tool-derived queries and model context.
3. Keep ordinary public browsing usable without per-page approval while binding private releases to allowed recipients and purpose.
4. Recheck recipient/policy changes and sanitize/redact credentials without falsely claiming pattern screening detects all private content.

## Acceptance criteria
- [ ] A new service receiving private/personal/business content is held before disclosure.
- [ ] Previously approved providers/accounts are usable only within their captured data/purpose limits.
- [ ] A public GET/query, redirect, script or MCP call cannot disguise an unapproved private upload.
- [ ] Guest admin cannot change local DNS/proxy/settings to bypass the external disclosure boundary.
- [ ] Unknown classification/recipient is held or unavailable; no blanket website/disclosure guarantee is claimed.

## Tests and evidence
1. Controlled recipient/upload/query/redirect and model-context fixtures -> allow/hold/deny by current policy.
2. DNS/proxy/guest-root alternative-path attempts -> denied by independently enforced boundary.
3. Revocation/stale approval and secret-shaped output fixtures -> no disclosure or token leak.
