## Deliverable
A requested reversible solo calendar block executes under standing policy while invitations, existing-version conflicts and consequential changes are held.

## Implementation steps
1. Define the exact calendar account/event/version and personal-reversible action class under the shared policy.
2. Implement create/update within approved account/purpose, preserving read-before-update and timezone semantics.
3. Route attendee invitations, sensitive/ambiguous changes and unknown action classes through final approval or refusal.
4. Return committed event evidence and recovery/undo information without claiming remote exactly-once behavior.

## Acceptance criteria
- [ ] A clear request creates a solo block without per-event approval and reports the actual calendar/time.
- [ ] Adding a participant or notification-producing action is not disguised as an ordinary solo edit.
- [ ] Changed event version, ambiguous date/account or stale/revoked policy prevents an incorrect mutation.
- [ ] An unknown provider outcome reconciles before retry; no unrelated calendar data is exposed.

## Tests and evidence
1. Fake calendar fixtures for solo create/update, timezone and empty/changed attendee sets -> correct allow/hold.
2. Version/revocation/concurrent-edit races -> hold or refuse stale mutation.
3. Crash-after-provider-call -> unknown/reconcile-only without duplicate event.
