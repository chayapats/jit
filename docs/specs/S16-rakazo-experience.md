# Spec S16 — Rakazo-style persistent teammates on Jit

Status: owner-confirmed product direction, 2026-11-05; implementation is in progress, not accepted parity. Parent: [#392](https://github.com/chayapats/jit/issues/392). [Delivery graph](../tickets/S16-rakazo-experience-roadmap.md). [ADR 0074](../adr/0074-rakazo-reuse-and-product-convergence.md).

## Confirmed direction

The owner asked for the Rakazo experience, authorized reusing its concepts and code, and explicitly chose to keep Jit + Schway rather than start a Rakazo fork and port Jit back into it. The owner subsequently instructed that existing stacks and implementation constraints must not be treated as fixed: propose changes that make the product simpler or better.

The desired result is a useful, self-hosted team of persistent computer assistants. The owner talks naturally, supplies protected input when genuinely required, and receives completed work in the appropriate destination. Bots retain identity, useful memory, work and computer state across days. Files, browser/desktop work, connected apps, routines, delegation, voice and client applications are part of delivery, not an optional list of future ideas.

Rakazo is the primary product reference. The audited reference is [elie222/rakazo](https://github.com/elie222/rakazo/tree/abf3c08145a05cba92a912d6c24fdfb5f569d0e0), commit `abf3c08145a05cba92a912d6c24fdfb5f569d0e0`. Its root license is Apache-2.0. Record origin, license, applicable notices and modifications for any adapted source. Reference descriptions are not independent evidence that every upstream workflow works.

| S16-D03 | Reuse upstream code when it reduces work and fits the needed boundary; preserve licensing and Jit identity. |

The choices of React, a database, API protocol, frontend bundler, native application framework and upstream import layout are engineering proposals until their slices record the selected option and evidence. S16-D02 retains Schway's engine responsibility; a demonstrated missing public contract belongs in Schway, with an implementation proposal rather than an internal import or duplicate provider loop.

## Relationship to existing behavior

S16 extends [S15](S15-conversational-autonomy.md) as the current product target. S15-D01–D23 and S15-AC01–AC16 remain the authority/continuity baseline unless an owner decision explicitly changes one. A broad request for Rakazo-style capabilities does not itself select Rakazo's approval modes or give working agents reusable website credentials. Engineering constraints, such as the provisioned browser's current static GET-only policy, are gaps to solve, not the new product ceiling.

S14 remains the default runtime. Opt-in S15 is implemented at main `76e15e9faece6b321a242725f161271fe1c20cf2`, including the premium Web work in #391. Existing S14/legacy bytes, private scopes, installed policies and rollback retain their versioned meaning. [#340](https://github.com/chayapats/jit/issues/340) and [#341](https://github.com/chayapats/jit/issues/341) retain their exact-build live evidence and adoption scope. Neither this spec nor a copied upstream application activates a host or converts its data.

Keep FR-01–FR-42 and NFR-01–NFR-14 stable. The feature and acceptance IDs below refine those requirements; they do not renumber them.

## Required architectural recommendations

Each substantial slice records existing implementation, candidate upstream reuse, a simpler alternative and the chosen tradeoff. Do not force the old SSR UI, SQLite journals, API format, repository layout or packaging onto a feature merely because they already exist. Equally, do not import a second backend, database or orchestration engine only because upstream uses it.

The initial candidate is to reuse/adapt Rakazo's React frontend and shared client concepts behind a Jit-owned API boundary, replacing rather than indefinitely duplicating the old interface where appropriate. This is a proposal to prototype and review, not an owner-selected dependency/version or a promise that React components run unchanged. PostgreSQL versus current stores, schema migration, API transport and client frameworks need measured operational and integration costs. Keep state preservation separate from a requirement to preserve every internal implementation.

Protected gates must govern actual effects regardless of stack. If preserving a specific existing contract makes the desired workflow impractical, report the exact conflict and propose a replacement contract plus migration/proof plan. Unsupported functionality is an implementation gap; disabling all useful browser interactions is not a successful general-browser design.

## Evidence and delivery rules

- Follow [the repository workflow](../agents/workflow.md), check ownership/branches/PRs before implementation, and use issue-specific branches/worktrees. No implement-parallel coordinator/claim workflow.
- All UI/UX design requires the owner-designated author. On 2026-11-05 the owner selected Astra at high effort to replace the unavailable prior author and authorized detailed Mobbin MCP research before design. The primary implementation owner reviews architecture, logic, authority and contracts. A design handoff supplies concrete experience decisions; this spec does not author UI layouts.
- Use Bun and TypeScript for Jit implementation. Imported components may bring reviewed build dependencies; there is no blanket prohibition on changing frameworks.
- Use scripted models, protocol fixtures, barriers and fake clocks for deterministic checks. Test observable outcomes, effect duplication, cancellation, private lineage, credential custody, concurrency and crash recovery.
- Browser/device/provider/VM evidence is opt-in and tied to the exact tested artifact. Human credentials are owner steps after the implementation is concrete; do not stop independent development because a live login is absent.
- Release packages must carry applicable third-party licenses/notices and source provenance. Existing Jit code retains its license; imported Apache-2.0 code is not relabelled MIT-only.
- A roadmap row is not a completed ticket or public API. Only scoped issues with verified prerequisites can be ready-for-agent. This parent remains open until the required outcomes and accepted evidence are complete.

## Scope boundaries

The complete self-hosted assistant experience is in scope. Rakazo's hosted subscription sales, multi-user SaaS tenancy, public plugin marketplace operation and upstream branding are not implicit Jit requirements. One installation remains single-owner. Using a client on a machine does not authorize using that machine as an execution host. New business/billing obligations and changes to retained owner decisions must be proposed explicitly.

No delivery date, feature percentage or benchmark superiority is inferred. Jod interoperability remains deferred under the existing owner decision and is not made a blocker by adopting Rakazo concepts.
