# Working VM operations, protected management and independent settlement

## Implemented decision (2026-11-03)

The owner accepted **RT15-01 option B** and explicitly authorized implementation of #321. Full root/sudo runs in an expendable guest. Valuable originals, protected Jit/Schway state, management/provider/channel/vault credentials and sensitive browser profiles stay outside it. Snapshots recover guest state; they do not prevent its destruction or undo real external effects. Guest-local changes need no separate destructive-action hold. Restore itself remains owner-required unless a later explicit standing rule authorizes it.

The implemented path is the opt-in Bun/TypeScript module [`src/s15/vm`](../../src/s15/vm/index.ts), using only public `schway/host` backend/tool seams. S14 remains the default. This supersedes conflicting pre-admission choices below; the original proposal remains historical evidence, not a requirement to build its synthetic catalogs.

- Host-initiated one-shot SSH uses a generated dedicated key, pinned Ed25519 host key, explicit target, no ambient SSH config, no agent/X11/port forwarding, no host-shell fallback, and finite request/output/time bounds. One public-key bootstrap command plus typed address, observed fingerprint and transport-profile confirmation enrolls a VM. Read-only capability rows distinguish proven/unproven/unavailable; configured management alone is not proven recovery.
- Two active sessions by default share one VM with separate work/attempt directories and systemd slices. Fixed setup is protected infrastructure admission, not domain-write authority. Inspect sessions expose only the exact core read/grep/find/ls set and backend mutation refusal. A system-administration session is exclusive and automatically snapshots first. Raw root shells can still disrupt siblings or escape guest cgroups; directory/cgroup separation coordinates work, not hostile-root isolation between Bots.
- Unit stop/cgroup read-back over SSH is **guest-reported/cooperative settlement**, explicitly accepted by the orchestrator. A protected Jit-managed QEMU, Lima or Proxmox stop with independent read-back is **strong settlement**. Unknown or inconsistent cleanup fences the entire shared VM and retains capacity. Original metadata survives restart; no shell/action is automatically replayed. A guest snapshot cannot rewind the protected operation journal, policy claims, usage or generations.
- Lima/QEMU uses a protected wrapper with restricted user networking and only a fixed guest-forward route to the host registry proxy, no guest agent or shared host mounts. Proxmox requires NIC/firewall isolation and read-only Datacenter/Node/VM audit in addition to guest probes; missing permissions or a disabled layer keeps network isolation unproven. Root-local firewall changes are not enforcement.
- The protected finite HTTP/CONNECT registry proxy permits exact owner-editable registry hosts and only public resolved addresses pinned before connect. No upstream credential is injected. Per-session leases log host/byte metadata only. This is **destination control, not content-level disclosure prevention**: TLS hides actual content, registries may receive workspace content, and guest root can impersonate sibling leases. `github.com`/`api.github.com` are absent from the default set. Even a download hostname cannot be guaranteed release-only by TLS passthrough. New destinations use protected policy and the exact-artifact path where suitable.
- Pinned SSH enrollment must match the independently read hypervisor NIC (and Lima SSH forward); a different VM cannot inherit isolation/recovery evidence. Protected snapshots retain the latest three points by default through separately claimed exact retirement; active system-session fences cannot be retired. Recovery retires old live contexts/timers and prevents old generations from altering newer state.
- Lima and VM-scoped Proxmox management retain snapshot/stop/rollback authority outside the guest. `Sys.Audit` at `/` and `/nodes/<node>` is read-only, while mutation rights apply only to the enrolled `/vms/<vmid>`. No existing installation/VM/store is adopted or modified. Since 2026-11-03 these are the optional owner-supplied path; the default is the Jit-managed local VM below.

See the [implemented contract](../contracts/s15-working-vm-v1.md#implemented-server-contract-2026-11-03), [runbook](../runbooks/s15-working-vm.md), exported TSDoc and deterministic tests. Live addresses and evidence stay in ignored `.local` records. Full S15 browser/effect enforcement, migration, host cutover and x64 acceptance remain separate.

## Jit-managed nested KVM working VM (VM15-02, 2026-11-03)

The owner chose a single host as the default topology ([ADR 0064](0064-conversational-authority-and-protected-control-plane.md#single-host-topology-owner-decision-2026-11-03)): the controller creates and manages the working VM as a nested KVM guest. `QemuVmManagement` implements `VmManagement` with **direct QEMU management** using Ubuntu packages only (`qemu-system-*`, `qemu-utils`, `cloud-image-utils`, `netcat-openbsd`, OpenSSH). Lima on Linux was rejected for this path: it would add an unpinned third-party binary, and its argv-rewriting wrapper can drift with upstream releases. Direct QEMU lets Jit own the exact argv, pin the host key from the start, read hypervisor state back independently of the guest, snapshot live and run as a non-root service user.

- **Image and provisioning.** One pinned Ubuntu 26.04 LTS cloud image per architecture (dated `release-20261016` path, SHA-256 pinned in code from the signed `SHA256SUMS`). A hash mismatch deletes the download and refuses with `vm_image_unverified`; there is no fallback. The base is read-only; each VM has a qcow2 overlay. The controller generates an Ed25519 client key and the guest's Ed25519 host key; a NoCloud seed installs both (key-only `jit` user with sudo, no password or root login, no guest agent, no shares) and the proxy-friendly settings (sudo keeps proxy variables; apt pipelining off). `known_hosts` is written before first boot, so no trust-on-first-use exists; a different key fails closed with `vm_host_key_changed`. Docker (`docker.io`) is installed through the protected proxy under one bounded provisioning lease; failure reports Docker honestly as missing.
- **Lifecycle and re-attachment.** QEMU runs in a transient unit of the service user's lingering user manager (`systemd-run --user`), outside the controller cgroup, so it survives controller restarts and upgrades. `WorkingVmService.reattach()` re-verifies a surviving VM (QMP, `/proc/<pid>/cmdline`, pinned SSH, NIC, egress) and restarts a VM that was running before a host restart under a new generation; owner-stopped or restored VMs stay stopped. Start waits for the pinned host key and an admitted login (`pam_nologin`).
- **Network profile.** Exactly one NIC on QEMU user networking with `restrict=on`, IPv6 off, guest subnet `192.168.5.0/24` (host `192.168.5.2`), a controller-chosen MAC, one loopback-only SSH host-forward and one guest-forward from `192.168.5.100:3128` to the protected proxy's controller-only Unix socket. `inspect()` reports `proxy-only` only when the running argv rebuilds byte-for-byte as this profile; any extra device, share, forward or netdev is `unproven`. The existing direct-egress probe targets stay valid. Live x64 probes after a guest `iptables`/`ip6tables`/`nft` flush found no route to public addresses, slirp DNS, ICMP or host services, and the proxy answered 407 without a lease.
- **Settlement and snapshots.** Strong stop is QMP `quit`, then unit stop/kill if needed, then read-back: unit inactive, recorded and current PIDs gone, and the overlay's write lock released (`qemu-img info` without force-share). Anything else is `vm_stop_unconfirmed` and the shared VM stays fenced. Snapshots are qcow2 internal snapshots with the existing `^jit-[a-f0-9]{32}$` tags, taken live through QMP `blockdev-snapshot-internal-sync` (crash-consistent; sibling sessions keep running). Restore stops the VM, applies the exact tag with `qemu-img snapshot -a` and leaves it stopped; retire deletes only the exact tag. POLICY claims, usage, generations and the operation journal stay outside the guest and are not rewound. Capability rows become proven only after an observed protected stop/restore.
- **Sizing.** Defaults come from controller-side host facts: about half the CPUs and about 45% of RAM, clamped so the controller and protected Chromium keep 2 vCPU and 6 GiB (10 vCPU / 20 GiB gives 5 vCPU / 9 GiB), and a 60 GiB sparse disk that must fit in free space minus the installer reserve. The owner edits them through `POST /s15/vm/resources`; they apply at the next start.
- **Residuals.** A hypervisor or slirp escape would run as the service user on the controller host (ADR 0064). QEMU's seccomp subset omits `elevateprivileges=deny`, which kills the guest-forward helper on the live host. The guest-forward runs `/usr/bin/nc` through QEMU's `/bin/sh -c` with a fixed controller-chosen string. The QMP and proxy sockets live in the protected state directory, which must stay within 64 characters for Unix socket paths. Restricted slirp gives the guest no DNS; tools must use the proxy. aarch64 argv is covered by deterministic tests only; live evidence is x64.

## Proposed decisions

1. **Keep management authority outside guest root.** Use host-initiated bounded one-shot access through an instance-registered protected manager. Resolve endpoint/VM/boot identity from trusted configuration and external verification. Guest IDs, JSON, hashes and echoed nonces only correlate bytes; they cannot authenticate owner/manager handles. Protected ledgers/credentials/native storage/sensitive website sessions never enter the working guest, prompts or exports. No protected-host shell fallback exists.
2. **Version operation and runner data separately from S14.** Use closed `s15-working-vm-*/v1` records and `jit.vm.runner/v1`, canonical hashes, explicit finite frame/byte/time/resource caps and no downgrade. Bind registration/VM/boot/work/attempt/workspace lease/process epochs to immutable operation and request dedupe. Reuse opaque backend observations, ECHANGED and own-entry atomic replacement concepts without treating them as root-proof CAS or reinterpreting S14 private computers/no-network grants.
3. **Separate intent, claim and actual dispatch.** Acceptance commits an intent only. Bind the exact #320 action claim/reservation and VM claim before I/O under one current continuity boundary. A new call rejects existing claims; the original registered unconsumed context can continue under its exact already charged reservation/current final guards. Recovered claims never regain a mutation context. `action.decide` keeps the prepared-action revision/hash unchanged. Publication has independent current guards and expects its producing claim; no second approval/charge for that same operation. The backend receives exact captured results through actor-bound guarded result reads and a final synchronous publication callback; signal/explicit cancellation resolves only the memoized original cleanup context. Rejected evidence cannot rewind prior response/channel facts.
4. **Separate transport, execution and VM/service capacity.** Cooperative cancel/timeout/exit/native completion/connection closure cannot prove guest-root descendants stopped. Host channel closure can settle transport only; external exact scope/VM stop or authorized service-transfer evidence settles the corresponding capacity. Unknown usage remains unknown and conservative charged bounds are retained. A single-work cancellation cannot silently escalate to a shared-VM stop affecting siblings. If no independently enforceable scope proof exists, retain capacity and expose the unsupported boundary.
5. **Treat guest output as adversarial evidence.** Validate all result shapes, paths/bytes/hash/correlation and safe errors; bound/sanitize output before context/publication. A success string or hash records captured bytes, not actual test/command truth, effect compliance or protected state. Root can kill/forge the runner; the response cannot attest owner policy or external stop. Sensitive website/effect/disclosure enforcement belongs to separately protected later components, not a host/GET/read-only label.
6. **Historical RT15-01 proposal, superseded by the confirmed decision above.** Supply concrete asset/impact and prevention-versus-recovery matrices. Protected originals/ledgers may be externally defended; root can still destroy unique guest files/OS/Docker volumes and service uptime. Snapshots recover selected versions, not prevent destruction. Do not select option B, accept guest loss or silently substitute restricted/read-only administration. RT15-01 remains unresolved; an owner decision is needed only if actual evidence requires changing the confirmed capability/guarantee.
7. **Recover facts without replaying commands.** Keep request identity/claims/usage/VM generations/withdrawals/policy revocations in the single current protected continuity authority. Guest/VM/native snapshots cannot rewind it or revive old grants/approvals/routines. Keep native storage opaque/fixed-workspace through public Schway APIs, and preserve S14/legacy private scopes/source bytes/prior build. MIG15 owns complete target schema/maintenance/boot fence/reverse compatibility; unsupported rollback stays fenced.

## Alternatives and consequences

- A guest-owned runner, sudo wrapper, firewall or sibling service cannot enforce a protected boundary against unrestricted guest root. Protecting a control plane on another host also needs actual mounts/devices/management/egress proof; physical separation alone is insufficient.
- Unrestricted guest root plus snapshots cannot support a universal prevention guarantee. External originals/promotion is useful research but leaves guest disruption unresolved. Restricted privileged operations may narrow the confirmed administration capability; neither tradeoff is chosen by this ADR.
- A long-lived unbounded runner/control socket or generic SSH shell would need additional identity/reconnect/authority semantics. This proposal specifies a bounded transport-neutral request, without selecting a live hypervisor/SSH/vsock implementation or installing credentials.
- Process-group cancellation is useful cooperative cleanup but can miss daemonized/root-controlled descendants. External scope settlement is harder and may require a proven VM-level stop; retaining capacity is the honest result when that proof is absent.
- Conservative bounds and no automatic mutation replay reduce utilization but preserve unknown remote outcomes and current accounting. Real scoped service allocation/transfer is a named proof obligation, not a signature that magically makes arbitrary guest services safe.
- The pinned public `schway/host` `ExecutionBackend`/exact custom-tool/session seams can express this composition. No demonstrated missing host behavior warrants a new Schway issue. Do not import internals, implement provider protocols or fork the agent loop.
