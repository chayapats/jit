## Proposed decisions

1. **Keep management authority outside guest root.** Use host-initiated bounded one-shot access through an instance-registered protected manager. Resolve endpoint/VM/boot identity from trusted configuration and external verification. Guest IDs, JSON, hashes and echoed nonces only correlate bytes; they cannot authenticate owner/manager handles. Protected ledgers/credentials/native storage/sensitive website sessions never enter the working guest, prompts or exports. No protected-host shell fallback exists.
2. **Version operation and runner data separately from S14.** Use closed `s15-working-vm-*/v1` records and `jit.vm.runner/v1`, canonical hashes, explicit finite frame/byte/time/resource caps and no downgrade. Bind registration/VM/boot/work/attempt/workspace lease/process epochs to immutable operation and request dedupe. Reuse opaque backend observations, ECHANGED and own-entry atomic replacement concepts without treating them as root-proof CAS or reinterpreting S14 private computers/no-network grants.
3. **Separate intent, claim and actual dispatch.** Acceptance commits an intent only. Bind the exact #320 action claim/reservation and VM claim before I/O under one current continuity boundary. A new call rejects existing claims; the original registered unconsumed context can continue under its exact already charged reservation/current final guards. Recovered claims never regain a mutation context. `action.decide` keeps the prepared-action revision/hash unchanged. Publication has independent current guards and expects its producing claim; no second approval/charge for that same operation. The backend receives exact captured results through actor-bound guarded result reads and a final synchronous publication callback; signal/explicit cancellation resolves only the memoized original cleanup context. Rejected evidence cannot rewind prior response/channel facts.
4. **Separate transport, execution and VM/service capacity.** Cooperative cancel/timeout/exit/native completion/connection closure cannot prove guest-root descendants stopped. Host channel closure can settle transport only; external exact scope/VM stop or authorized service-transfer evidence settles the corresponding capacity. Unknown usage remains unknown and conservative charged bounds are retained. A single-work cancellation cannot silently escalate to a shared-VM stop affecting siblings. If no independently enforceable scope proof exists, retain capacity and expose the unsupported boundary.
5. **Treat guest output as adversarial evidence.** Validate all result shapes, paths/bytes/hash/correlation and safe errors; bound/sanitize output before context/publication. A success string or hash records captured bytes, not actual test/command truth, effect compliance or protected state. Root can kill/forge the runner; the response cannot attest owner policy or external stop. Sensitive website/effect/disclosure enforcement belongs to separately protected later components, not a host/GET/read-only label.
6. **Keep administration and destructive gates as simultaneous unproven obligations.** Supply concrete asset/impact and prevention-versus-recovery matrices. Protected originals/ledgers may be externally defended; root can still destroy unique guest files/OS/Docker volumes and service uptime. Snapshots recover selected versions, not prevent destruction. Do not select option B, accept guest loss or silently substitute restricted/read-only administration. RT15-01 remains unresolved; an owner decision is needed only if actual evidence requires changing the confirmed capability/guarantee.
7. **Recover facts without replaying commands.** Keep request identity/claims/usage/VM generations/withdrawals/policy revocations in the single current protected continuity authority. Guest/VM/native snapshots cannot rewind it or revive old grants/approvals/routines. Keep native storage opaque/fixed-workspace through public Schway APIs, and preserve S14/legacy private scopes/source bytes/prior build. MIG15 owns complete target schema/maintenance/boot fence/reverse compatibility; unsupported rollback stays fenced.

## Alternatives and consequences

- A guest-owned runner, sudo wrapper, firewall or sibling service cannot enforce a protected boundary against unrestricted guest root. Protecting a control plane on another host also needs actual mounts/devices/management/egress proof; physical separation alone is insufficient.
- Unrestricted guest root plus snapshots cannot support a universal prevention guarantee. External originals/promotion is useful research but leaves guest disruption unresolved. Restricted privileged operations may narrow the confirmed administration capability; neither tradeoff is chosen by this ADR.
- A long-lived unbounded runner/control socket or generic SSH shell would need additional identity/reconnect/authority semantics. This proposal specifies a bounded transport-neutral request, without selecting a live hypervisor/SSH/vsock implementation or installing credentials.
- Process-group cancellation is useful cooperative cleanup but can miss daemonized/root-controlled descendants. External scope settlement is harder and may require a proven VM-level stop; retaining capacity is the honest result when that proof is absent.
- Conservative bounds and no automatic mutation replay reduce utilization but preserve unknown remote outcomes and current accounting. Real scoped service allocation/transfer is a named proof obligation, not a signature that magically makes arbitrary guest services safe.
- The pinned public `schway/host` `ExecutionBackend`/exact custom-tool/session seams can express this composition. No demonstrated missing host behavior warrants a new Schway issue. Do not import internals, implement provider protocols or fork the agent loop.
