# Protected file custody and a small React client

The [Astra-authored handoff](../design/S16-rakazo-experience.md) recommends React over the shared protected API. Select React/React DOM 19.3.0, Bun's existing build pipeline, TypeScript and existing owner authentication. The [official React version record](https://react.dev/versions) and package registry were checked before pinning; upstream Rakazo's older client version is not copied blindly. No second router, RPC/auth backend, telemetry system, database server or execution engine is introduced. `/s16` is explicit selection on opt-in S15; existing default/owner host/state are unchanged.

Adapt narrow Rakazo preview classification and artifact-card behavior at pinned commit `abf3c08145a05cba92a912d6c24fdfb5f569d0e0`. Replace its RPC, authentication, i18n, icons, renderers and design-system dependencies. Retain Apache-2.0 source provenance, copyright, unmodified license and prominent modification notices. Preserve existing Schway/Jit notices. React, React DOM and Scheduler retain their MIT licenses. Release packaging now includes LICENSE, NOTICE and third_party rather than distributing adapted source without its notices. No upstream server or unreviewed binary/parser is executed.

Choose a separate protected file custody journal for this first slice, matching current service locks and additive composition inventory. Stage immutable output before the CHAT publication transaction; only CHAT's committed reference set makes it downloadable. This avoids claiming cross-ledger atomicity and makes a failed publication safely leave a private candidate. Reusing legacy project/topic attachment storage would import a different authority root. A full PostgreSQL replacement would add deployment/migration cost before solving the first input-to-output task. Consolidating file metadata/publication into the CHAT SQLite writer remains a plausible simpler follow-up if orphan retention, cross-request ancestry or garbage collection become difficult; no current store implementation is a product constraint.

An additive composition manifest alone is insufficient for rollback: the installer can restore an earlier manifest while the CHAT ledger already contains new file-derived results. Stamp CHAT format 2 atomically with the first committed v2 ingress. Existing binaries accept only format 1 and refuse before opening format 2; the new store accepts 2 only with explicit file awareness. This is a metadata compatibility fence, with no table or S14/legacy conversion. A compatible release/state recovery plan is required after file adoption rather than permitting an old binary to publish results without file lineage.

The [v1 contract](../contracts/s16-files-v1.md) freezes actual byte/type/identity/owner/resource/source and publication rules. Start with screened UTF-8 text/Markdown/CSV and real POLICY-backed file tools. Existing pure attachment filename/signature helpers are reusable without the legacy storage/authority code. Complex PDF/image decoding belongs in the existing disposable, networkless sanitizer boundary or a reviewed replacement; the protected service must not invoke a general parser on raw uploads. The current MODEL15 input is text-only and needs an explicit supported image/send/probe integration before images are advertised. A sanitized filename-only image result is not acceptance.

Distinct private file sources must reach DATA15 before any model stream. Artifact staging uses ordinary exact POLICY actions and current TEAM write ceilings. Existing installed rules remain unchanged; newly available file operations appear in a new default proposal for owner review. File bytes/names do not enter isolated interpretation, broaden frozen work scope or grant a recipient. New-recipient approval remains effective even though the file is stored on the installation.

Do not enable automatic file memory by treating a generic computer resource as precise file ancestry. For this first slice, file work has no MEM packet and no later interpreter-history replay. This is an explicit implementation gap, not rejection of S16's automatic-memory target. Complete transitive file ancestry across MEM, history, derived artifacts and future recipient selection before enabling it. The required next text/document/image and memory slices remain tracked under #396 and MEM16-01; the text vertical slice does not close them.

Evidence combines production composition with scripted models/transports, plus opt-in real Chromium execution of the actual React bundle at desktop/mobile widths. Host/session/resource/source withdrawal, uncertain sends, partial uploads, failed publication and restart must retain honest states. These checks do not establish live parser isolation, model vision, device or owner-host acceptance.
