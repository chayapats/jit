# Isolated PDF and image inputs over the existing Schway host

Extend the [first file workflow](0076-s16-file-custody-and-react-client.md) with a strict, explicit binary profile. Reuse `PodmanAttachmentSanitizer` independently of legacy project/topic attachment ownership. Reuse public `schway/host` image constructors, probes, resolvers and final dispatch authorization. No second parser service, image provider protocol, runtime fork, legacy authority root or new model dependency is needed. This is a smaller integration than moving file processing into a general working VM: decoding gets no network, service credentials, vault, control-plane state or arbitrary mounts.

The existing decoder needs a new strict profile. In particular, an encrypted PDF with an empty user password can be opened by Poppler without prompting; successful text extraction alone does not establish that it was unencrypted. Parser image generation 3 accepts `--s16`, checks `pdfinfo`'s explicit unencrypted result and emits the closed validation version. Older generation 2 remains usable by legacy decoding, but cannot advertise strict S16 support. Originals, decoded pixels/pages, expanded text, output files, elapsed time, memory and queue admission have independent finite bounds. Incomplete extraction is rejected rather than certifying complete source coverage.

Keep one serialized parser queue per protected file installation. The existing container name is installation-scoped; concurrent resets would kill another upload's parser. Each job mounts only a new private copy of the chosen original. Immutable per-attempt labels prevent late container cleanup from killing a successor. If cleanup is uncertain, retain the private job directory and fence subsequent jobs until a conclusive reset. On process restart, reconcile retained jobs before exposing the composition. Do not delete an input snapshot while its parser might still have it mounted. A bounded orphan alarm supplements process cleanup; it is not substituted for conclusive cleanup evidence.

Use separate immutable original and model-representation hashes. Original custody remains the private DATA15 source. A PDF representation is complete extracted UTF-8 text; an image representation is a re-encoded, metadata-free, possibly resized PNG/JPEG. The protected host checks only bounded output names, metadata, headers, hashes and dimensions; complex decoding stays inside isolation. Receipt `s16-file-receipt/v2` records validation and parser generation. It does not grant work, recipient or effect authority.

Actual image bytes are resolved freshly by Schway on every relevant model attempt/tool round. MODEL15 forwards transient `imageData` only to the supported adapter; disclosure payloads and durable model/native records contain references, not image bytes or base64. The caller's final image hook runs inside Jit's existing physical-send authorizer, including an auth resend. It rechecks owner/work/TEAM/resource/original/derivative/DATA15 fences, verifies the exact outgoing bytes and reserves a real POLICY read for every selected image. Input evidence says `admitted_for_model_send`, not that a provider received or understood the image. Successful model completion and CHAT publication are separate requirements. Existing text input hashes and public text behavior stay unchanged.

Installed capability evidence must match the pinned Schway revision and the exact selected route/model. Reject ambiguous duplicate probes and controlled-fixture revisions in installed configuration. The owner maintains probe evidence for the configured account and must remove/re-probe it after account, adapter or model changes; a text login, passing fixture, or model claim cannot manufacture live evidence. Trusted test composition can inject explicitly labelled fixture probes without enabling an installed account.

Fence rollback in both ledgers. First binary upload metadata atomically stamps file journal format 2, before a CHAT command exists; first binary-bearing command stamps CHAT format 3. Older file-aware binaries otherwise could interpret a staged PDF as ordinary UTF-8 after rollback. New readers explicitly accept the additional versions. Existing text formats, S14/legacy state and runtime defaults are unchanged. Recovery needs a compatible release/state plan; restoring only an earlier composition manifest is insufficient.

Implement the authored validating/error/source-details states over actual lifecycle polling. Ready receipts are the only sendable inputs. Capabilities advertise actual extension/MIME/byte pairs, independent text bounds and parser/model unavailability. Originals do not render as active content; artifact previews stay escaped text. The [binary contract](../contracts/s16-binary-files-v1.md) freezes this slice. File-derived memory, later history and artifact reuse retain their deliberate fence until #402 supplies transitive source ancestry.

Deterministic evidence includes actual repository PNG/JPEG re-encoding, actual Poppler extraction, a real encrypted fixture, complete composed publication/download/restart, controlled provider transports with actual image data URIs and Grok auth resend refusal, plus actual React execution at desktop/mobile widths. Controlled local parser fixtures are never production fallback and do not prove rootless Linux isolation or live model vision. The opt-in Linux test and separately authorized live route challenge remain distinct acceptance evidence.
