# Offline S14 backup and quarantined activation

The owner confirmed credential-free consistent images, current independent lifecycle reconciliation, exact cutover authority and workers fenced until reconciliation. Legacy behavior remains unchanged behind the separate S14 opt-in. UI and real Linux evidence remain separate deliverables.

Restore/upgrade use one stopped-service maintenance process under the existing OS-backed runtime lock. Activation never has an online shutdown/cutover authority surface. Routine backup additionally uses the running service’s held runtime lock plus a durable writer-only capture fence; it requires settled operations rather than cancelling them and permits authenticated progress reads. Transaction rechecks under the SQLite writer lock exclude other processes, and every worker pump pauses during capture. A durable external control journal/fence survives process death and covers both the application rename and native session-store pointer. Normal store reads/writes and boot fail closed while it exists. Offline status and recovery commands authenticate the current owner.

Use combined schema 16, one above main schema 15 (including personal connectors) and above this branch’s earlier schema 14. There is no released previous S14 format to migrate; support 16→16 staging/revalidation now and refuse unreleased 1–15, future/legacy schemas and unknown builds before candidate writes. Future actual migrations require an explicit compatibility matrix and preservation tests. The stage creates a normal credential-free recovery point before copying. Before cutover, discard leaves the prior application intact. After cutover, rollback is another quarantine restore with current tombstones.

Immutable artifacts already live as transactional SQLite BLOBs, so the main image carries them with an exact hash inventory. Native snapshots use the pinned public Schway format-4 APIs only. Native correlation workspaces remain fixed; a separate session directory is restored/reconciled and selected during fenced activation. This supports the existing host/path only: native workspace relocation is not invented. The old application/native store stays private installation recovery state and is not an ordinary export.

Classify every application table explicitly. Remove credentials/session/connection/transient input state, scan retained plain/opaque bytes for registered or credential-shaped secrets, zero free pages and compact. Do not recursively copy any filesystem tree, vault, native home, computer workspace or browser profile. Images contain hash-only ledger positions, never replacement lifecycle authority. Existing identity, source/access/share/Bot/computer withdrawals, native catalog and monotonic reservations remain in the separate current lifecycle database.

Quarantine reuses S14 lifecycle, report/share and REC14 reconciliation against a private copy of the current independent ledger. Candidate-derived facts stay private through prepare/validate/discard. The exact action hash binds both candidate and quarantine-ledger bytes. Only after durable owner activation intent does an idempotent transaction append validated facts and merge monotonic usage maxima into the actual ledger, verifying its exact target digest before the application rename. A crash on either side of this transaction stays fenced and accepts only the recorded prior or target ledger on retry. The installation ledger is never replaced by the copy. Revoke restored work grants, block old routines/chat, expire approvals and keep unknown effects/unsent deliveries reconcile-only. Preserve the current owner generation for historical evidence contracts while deleting all sessions; this keeps valid reports readable without re-authorizing execution. Unresolved native or computer/Bot cleanup blocks activation. The CLI has no computer runtime. Quarantine may settle its boot-only stop from the current installation's already confirmed stopped computer only when Bot, workspace, profile and disk-slot identity/cleanliness match. It advances the generation and clears leases without starting a process. Missing, changed or unsettled cleanup evidence still blocks and must be resolved through the trusted live service runtime.

Online backup uses the typed owner/CSRF ingress and a bounded 60-second progress deadline, retaining the fence through actual native close if a call does not support cancellation. Before boot opens the store, the runtime-lock owner resolves an interrupted online request from the durable registry, never from a manifest-shaped orphan. Initial production worker admission also stays closed until REC14 completes. Offline CLI route defaults and retained resource ceilings match normal serve, so valid evidence does not disappear merely because no custom route environment was set.

A destructively withdrawn archived computer generation uses the current installation’s matching stopped/deleted generation and volume identities during quarantine. Missing cleanup evidence blocks; old volumes and raw profiles never come from the archive.

Finite MVP limits remain: ten registered backups, one hundred durable command receipts, 64 MiB image plus serialized native bytes, 2 MiB manifest/control, 1024 native intents and 200000 rows/ledger records. Online capture keeps at most nine images (one slot reserved for offline recovery), rotating only its oldest unpinned images after verified replacement; offline points and current stage source/recovery IDs stay protected. Both online and offline journals have separate 100-request bounds; archival and arbitrary archive/cross-install import need later scoped contracts. Schway still has no caller byte ceiling, so one session may allocate its host-side bounded capture before Jit rejects serialized size.

New maintenance directories and their parents are fsynced before descendants or registry/pointer publication. Component contents are fsynced before the manifest; the shared atomic journal helper is followed by a strict directory fsync, so swallowed best-effort failures cannot report success.

Evidence is deterministic public-host local-storage round trip and fault injection, not Linux power-loss/isolation or paid provider verification. `docs/runbooks/s14-backup-restore.md` supplies the opt-in x64/arm64 evidence procedure. No UI design or acceptance is claimed.

## Personal connector reconciliation (#277 after #278)

Schema 16 retains every schema-15 personal connector table. Explicitly exclude personal_flows, including OAuth state hashes, and retain credential-free client/connection/grant/source/read/draft/observation metadata. Sealed vault contents and keys remain outside capture. Quarantine fences connection revisions into reauth_required (or current-ledger revoked), so a surviving installation vault cannot reactivate archived consent. Pending remote revocations become unknown, never automatically reissued. Current lifecycle forget/delete/connection/consent/resource withdrawals reach cached reads and derived reports before activation; held send/Calendar cards and independent effect claims remain non-replayable. Credential-sentinel and managed round-trip tests cover these choices without live Google calls.
