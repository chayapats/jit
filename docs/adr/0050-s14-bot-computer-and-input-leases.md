# Separate Bot workspace/browser processes with finite fail-closed boundaries

Confirmed product direction remains S14-D02/D03/D10/D13, FR-35/36/38/40 and NFR-04/06/07/14. Owner orchestration for #248 fixes rootless Podman, lazy computers, ordinary Jit authority, the existing script-free takeover transport and Phase A public-read/report scope. These are engineering choices, not a redesign or a claim that all S14 capabilities shipped.

The BotComputer adapter reuses the runner/backend and protected CDP stream without legacy Project authorization or combined workspace/profile mounts. Two rootless containers have distinct mounts and PID/IPC/UTS/network namespaces. Both use no network. Only the workspace has a runner gateway; only the protected browser has a CDP pipe. No cookie/profile/JS/CDP/MCP tool is advertised to a model. Public reads use the separately granted service-owned Parallel gateway (#249/#250); browser website reads and login remain unavailable; unknown effects cannot escape through shell/network. Owner text is transient protected CDP input, never a shell command.

Finite persistent disk enforcement is a release gate. ADR 0046's confirmed install-time pool supersedes the original operator-provisioned per-Bot mounts: root prepares bounded loop/ext4 pairs and the service transaction claims them, without privileged runtime provisioning. Missing mounts or unproven capacity fail closed. See the pool contract and ADR 0046 for wipe/reuse and sparse-overcommit rules.

Unconfirmed stop retains its capacity slot until an exact stop verifies settlement. Initial safety ceilings are two live computers and, per component, 0.5 CPU/512 MiB/128 PIDs/1 GiB persistent disk, bounded transient filesystems and no swap. Startup is 30 seconds; idle is five minutes. These are not hardware sizing evidence. Actual kernel cgroups and exact isolation are verified before tool access; ambiguous inspect/kernel formats refuse. Local rootless Podman and the service identity's verified same-host Unix API socket are supported; truly remote clients refuse without fallback.

Persistent browser restart uses stable component hostnames and removes only Chromium singleton symlinks after verified process stop; it does not erase profile/session data or follow the links. Podman 4.9’s exact `CgroupMode=private` field and systemd’s identical same-target mount layers are verified alongside the existing kernel checks; aliases, conflicting layers and child mounts still refuse. Remote client bookkeeping uses only the bound service-owned API directory, avoiding Podman 4.9’s concurrent fallback-directory race.

Install and compatible-code service upgrade prepare each configured digest-pinned image's exact `keep-id:uid=1000,gid=1000` mapping through the service identity's local Podman API before activation. Podman may copy/chown an image's top layer when storage cannot shift IDs at mount time; building or finding the image alone does not prepare that cache. Preparation creates and removes a uniquely named, never-started container, with no Bot mounts, inherited environment or network. The cached image mapping survives container removal and reboot. Preparation and exact-name cleanup must both succeed; configured-computer upgrade failure leaves the prior release selected and the service stopped. Install remains feature-off when images cannot be prepared. No runtime root helper, mapping relaxation, SQLite durability change or startup-deadline increase is involved. Host disk latency and Podman version differences remain separately measured live evidence, not inferred support claims.

The lifecycle drainer runs at most two different computers concurrently, matching the existing active-computer ceiling. A newly committed intent wakes an occupied drainer so a second Bot does not spend its startup deadline waiting for an unrelated Bot. Operations for the same computer retain sequence order and the per-computer runtime/input barrier. Startup still expires 30 seconds after the committed open intent; concurrency does not extend it. Shutdown joins all admitted operations before releasing the drainer.

Lifecycle commands commit revisioned operations before runtime mutation. Generations fence startup, input, runner access and publication. Boot stops old processes and never replays startup, input or destructive operations. An immutable attempt/computer-generation binding prevents late reports after reset. Takeover changes durable ownership immediately; a per-computer barrier waits for old dispatched input to settle before new input. Returning control never approves effects. Agent scroll on the offline surface is the only reviewed input class.

Transient owner text uses a separate endpoint consuming an input ID with a process-keyed HMAC and safe outcome. Text stays in memory/the protected pipe. Lost responses/crashes are unknown and never replayed. Images are owner-only, bounded and no-store; state/SSE contain no website material, and SSE is one bounded event per connection. Rendering remains the designated Opus slice.

Schema 6 combines the foundation result-state table with the computer, memory and Parallel tables. Earlier unreleased schemas 1–5 and unknown/legacy formats refuse with fresh-state before writable open; no automatic upgrade is supported. This is a narrow schema addition, not backup/restore/native recovery completion (#254/#263). Fixtures establish contracts/barriers; x86_64 LXC and arm64 Lima kernel/resource/persistence/reboot evidence remains pending in the runbook.

Registry check/proxy cleanup uses an explicit zero stop grace, as ordinary computer removal already does. A sleep PID 1 may ignore SIGTERM; Podman's default forced-removal grace can exceed the runtime's five-second cleanup deadline. Removal must still settle successfully before releasing the handle/network; failed or uncertain cleanup continues to fence the handle. No timeout, authority or isolation bound is widened.

Podman namespace planning (`info`, `create`, `run`) remains single-flight within the computer runtime, with authority rechecked after waiting and before dispatch. On the x64 Podman 5.7/libsubid build, overlapping API requests produced a duplicate-length UID map despite a single configured subordinate range, causing another expensive cache miss. Serialize planning without serializing whole computer lifecycles or changing the keep-id mapping. This is a conservative compatibility boundary; the precise upstream race and a same-host Podman 4 comparison remain unverified.

Concurrent starts share only their currently in-flight Podman readiness/host-info response and reuse that exact fresh response for local-daemon verification. A later start probes again. The cold info request may use the existing startup budget instead of a separate five-second cutoff; the original committed-open guard still rejects startup at 30 seconds. Socket ownership/locality, host UID/hostname, dedicated mounts and cgroup checks remain required. No completed readiness result is cached across later starts.

The private Podman namespace-planning queue also covers the scoped registry proxy's `create` request. Its separate proxy implementation must receive the queued runner rather than bypassing the queue with the raw client. A deterministic held-info regression proves proxy creation and another computer's readiness cannot overlap planning. This prevents the previously observed process-global keep-id mapping race; it does not turn an OS AppArmor network-cleanup refusal into success or relax cleanup fencing.

Registry teardown removes the check before the proxy, rather than issuing concurrent removals against the same Podman storage/network namespace. On slow x64 storage the concurrent check removal completed on the API after its unchanged five-second client deadline while proxy teardown was also active. Sequential cleanup avoids that unnecessary contention; each operation retains its original timeout, immediate stop grace and exact-name boundary. Both removals are attempted even if one fails, and any unconfirmed cleanup still fences the handle. No retry or inferred cleanup success is introduced.
