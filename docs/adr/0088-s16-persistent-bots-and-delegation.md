# Persistent Bots from exact proposals, and bounded Bot-to-Bot delegation

## Context

S16-AC01 asks for accepted persistent Bots that the owner can configure, talk to across restarts, archive, restore, duplicate and export without copying credentials or silently widening resources. S16-AC08 asks a Bot to hand bounded assignments to an enabled peer or a temporary worker, with results returning to the originating responsibility, failure or cancellation of one worker preserving sibling evidence, a finite shared budget, and no new permanent Bot.

The S15/S16 runtime had exactly one Bot: `conversation.bot` from the installation config. The standing policy names Bots (`StandingPolicy.bots`, each rule's `bots`), so any new Bot needs a policy revision, and POLICY treated every newer revision as `stale_authority` for all running work. There was no protected place for Bot profiles, no conversation-to-Bot link and no way for a running work to start another bounded work.

Owner decisions on 2026-11-07, before this work: one PR for #412 and #413; a Bot is created from the chat (the main Bot drafts a proposal card) or from a New Bot form, both ending in a one-press acceptance of the exact proposal, and a changed proposal needs a new acceptance; a new Bot gets the team defaults (shared computer, team resources, the main Bot's rules), listed on the card and removable before accepting; Bots delegate on their own within a cap and the parent's budget, peers accept assignments by default, a temporary worker uses the parent's model and a narrowed context and is not kept; one conversation talks to one Bot, chosen when it starts; archiving stops running work at once, fences new messages, pauses routines and keeps unknown effects for reconciliation, and restore needs routines to be turned on again; per-Bot model/effort is picked only from approved routes (switching routes mid-work and real usage reporting stay with #421); the main Bot cannot be archived; importing an export makes a new proposal that lists what is missing.

## Decision

1. **Explicit opt-in.** `s15-runtime/v1` gains `bots: true` (composition `bots: {}`), set by the generated installer. It adds the additive store `bots.sqlite`. Without it every conversation still talks to `conversation.bot` and nothing below applies.
2. **Bot directory** (`s16-bots/v1`, `src/s16/bots/service.ts`). Protected records: profiles (name, responsibility, route choice, excluded team resources, accepts-assignments, state), exact proposals and immutable conversation-to-Bot bindings (triggers refuse update/delete). A created Bot owns its POLICY catalog identity (`bot_<24 hex>` from the accepting request, revision 1, generation 1); the directory answers the `bot` catalog for it and for a configured Bot it archived. The main Bot and configured Bots keep their config catalog identity and get a profile row only when edited.
3. **Exact proposals.** A proposal (`s16-bot-proposal/v1`) binds the draft, the standing-policy revision and the listed team resources in `proposalHash`. The New Bot form, an edited card, duplicate (`bot.duplicate`), import (`s16-bot-export/v1` → proposal with `missing`) and the main Bot's `propose_bot` tool all create proposals; none creates a Bot. `bot.accept` names the proposal and its hash; a changed draft, policy revision or resource list refuses `stale_proposal`.
4. **Team defaults through POLICY.** Acceptance installs one standing-policy revision that adds the Bot to `bots` and to every rule that names the main Bot, except separately approved personal GitHub rules and recurring payments. Nothing else changes. The default-policy proposal (POLICY15-02) names created Bots too (`extraBots`), so renewal keeps them and the rules page does not show a change. An excluded resource is refused by the composed catalog `allows` for that Bot, so POLICY refuses admission and dispatch, and it is not offered to interpretation.
5. **Membership-only revisions keep running work.** POLICY's work guard accepts a work bound to an older revision when the newer revision differs only in other Bots' references: both revisions compared with every other Bot removed from the top-level and rule Bot lists must be equal, and an unchanged reinstall is still a fresh start. Creating a Bot therefore does not stop another Bot's work; a change to a work's own Bot memberships or to any other field still does.
6. **One conversation, one Bot.** `conversation.bind` binds a not-yet-started conversation to a Bot; a started conversation keeps its Bot, and an unbound one is the main Bot's. The conversation policy resolves the Bot per conversation for interpretation and admission (`bot`, `selection` and `selectionPin` are the Bot's route, falling back to the installation default when the chosen route is no longer approved), and the Bot's owner-confirmed name and responsibility reach the model as owner decisions. Memory scope, computers and TEAM resources already key on the work's Bot.
7. **Archive and restore.** Archive (`bot.archive`, not the main Bot) first marks the Bot's catalog identity inactive, so POLICY refuses every work of it at the next guard (`authority_revoked`), then stops the unfinished requests of its conversations and assignments (which revokes their works) and pauses its active routines. Settled and reconcile-only requests are kept as they are. The conversation ingress refuses `bot_archived` for every new message, routine occurrence or assignment. Restore (`bot.restore`) reactivates the same identity without a policy change, so the Bot's history and sourced memory are readable again; nothing revoked resumes, and paused routines stay paused.
8. **Delegation** (`s16-delegation-run/v1`). A non-delegated, non-file work gets the host tool `delegate` (up to 3 assignments per call): `to` is `temporary` or an active peer that accepts assignments. In one conversation-store transaction `submitDelegation` checks the parent is running in its work phase, at most 6 children per request and 3 unfinished at once, charges the child's slice to the parent's own counters (model calls `max(2, ⌊limit/3⌋)`, tool calls `max(1, ⌊limit/3⌋)`, never refunded, keeping one model call for the parent) and records a queued child request in its own conversation (`dc_…`, bound to the assignee) with an immutable pin of the parent's frozen purpose, resources and access. A child has no interpretation call, no memory retrieval or retention and no `delegate` tool; it is admitted under current policy for its Bot (a temporary worker is the parent's Bot with the parent's route) with limits capped by its slice, and `named` recipients never carry over, so a send the child starts itself still waits for the owner. The tool waits for every child to settle and returns their states and published results; a held child keeps its own Needs-you item. Children run in their own drain pool sized to the default computer's free sessions (at least one), so a waiting parent cannot starve them. Stopping a parent stops its unfinished children; stopping one child leaves its siblings. Child conversations are not listed as chats; the parent row lists its children and each child row names its parent.
9. **Narrowed context and privacy ancestry.** The task text is captured as a TEAM source whose parents are the TEAM sources of every claim in the parent's context packet and whose file pins are that packet's. If any of those claims is Bot-private, a peer assignment refuses `private_context` before anything starts; a temporary worker (the same Bot) may take it. DATA15 derives the task from everything the parent work read. Before every model send of a child, the TEAM handoff from the still-current parent work to the child must admit the task's full ancestry for the child's Bot (a stopped parent, withdrawn source or file refuses `lineage_withdrawn`), and DATA15 merges the task's sources into the child, so the send is checked for them. A child's result reaches the parent only through its own publication guard, after DATA15 merges the child's read ancestry into the parent.
10. **Restart.** Running requests (parent and children) become reconcile-only as before; a queued child becomes `blocked/context_lost`. Child results, slices and the child list are stored once, so nothing attaches or charges twice and a settled parent starts no further child.
11. **Owner surface.** `GET /api/s16/client/bots` (`s16-client-bots/v1`), `GET /bots/:id` (`s16-client-bot/v1`, with conversations and the archive impact), `GET /bots/:id/export`, `POST /bots/proposals`, `POST /bots/imports`, `POST /bots/:id/duplicate` and `POST /bots/commands` (`s16-bot-command/v1`: `bot.accept`, `bot.dismiss`, `bot.update`, `bot.archive`, `bot.restore`, `conversation.bind`), idempotent per `requestId` with CSRF rechecked after the body. Capabilities gain `bots`; bootstrap gains the roster and each conversation's `botId`; snapshots gain `botId`. The React client adds the Bots pages (`/s16/bots`, `/s16/bots/new`, `/s16/bots/:id`), the Bot roster in the rail, a "Talk to" choice for a new chat, the chat proposal card, child cards and the assignment banner, in English and Thai.

## Consequences

- Several Bots share one standing policy and the team's resources by default. A Bot's narrower scope is an exclusion list; giving one Bot a resource the others lack still needs a separately reviewed rule.
- The persona text is owner-confirmed data the model sees; it never widens scope or decides an action.
- Delegated work costs part of the parent's own finite limits; three peers cannot be given three full budgets. On the default computer (2 sessions) children run one at a time while the parent waits.
- File-bearing requests do not offer `delegate` yet (their tool port is the file workflow's); a temporary worker or peer cannot see the parent's attachments except through the parent's task text.
- During an archive, memory produced by the Bot is unavailable to every Bot (its producer is not current) and returns on restore.
- Live account evidence (real provider routes per Bot, a real peer on a second route) belongs to LIVE16-01 (#431).

## Alternatives considered

- *Bots outside POLICY (a Jit-side allow list)*: avoids policy revisions, but POLICY could no longer prove which Bot a work is for; rejected.
- *Restore under a new generation*: makes old authorities unusable, but also withdraws all memory and hides every earlier result of the Bot; archive already revokes the unfinished work, so the same identity is safe and keeps continuity.
- *Delegation inside the parent's own work authority (a sub-run)*: shares the budget automatically, but a peer runs as another Bot with its own route and persona, which needs its own authority.
- *Interpreting the task text like an owner message*: adds a model call that would see the parent's context and could reinterpret scope; the pin already fixes the narrowed scope.
