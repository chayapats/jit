# app.work-grants/v1

Implemented AUTH14-01 (#247) logic, using app.bots/v1 and app.conversations/v2. S14-AC03/05/12; FR-06/14/17/21/35/38, NFR-05/07. Product design integration remains with Opus. Exported types are in `src/s14/authority-types.ts`; the shared ingress is `S14Application.execute(actor,command):S14Receipt` with typed overloads. Actors, CSRF, retry receipts and exact-key validation follow [app.bots/v1](app.bots-v1.md).

| Kind | Payload | expectedRevision |
| --- | --- | --- |
| `task.accept` | `{taskId}` | current proposed Work revision |
| `work.start` | `StartPayload` below | conversation revision; task revision is additionally pinned in payload |
| `work.stop` | `{workId}` | current Work revision |

`StartPayload` is exactly:

```ts
{
  conversationId: string;
  task: { id: string; revision: number } | null;
  title: string; purpose: string; completionRule: string;
  bots: { id: string; revision: number }[];
  tools: string[];
  scopes: { kind: 'resource' | 'share'; id: string; revision: number }[];
  limits: { attempts: number; steps: number; calls: number; outputBytes: number; wallMs: number; concurrency: number; reads: number };
  expiresAt: number; // absolute milliseconds, >now and <=now+wallMs
}
```

All limits are explicit positive safe integers, bounded by safety maxima of 64 attempts, 64 steps, 256 calls, 1 MiB reserved output, 24 hours, 8 concurrent Bots and 256 public reads. There are at most 8 selected Bots, 64 tools/scopes and 128 KiB canonical JSON per envelope/record. These are validation ceilings, not measured host operating profiles or promised capacity. No default grant or ambient computer/account/resource exists. Commands with credential-bearing purpose/title/completion are refused before persistence. Task suggestions have only title/purpose/completionRule and originate in committed replies; exact owner acceptance retains the obligation and creates no grant, queue intent or run. `message.post`, @mentions, classifier output and source text have no work-start authority.

Explicit `work.start` commits Work + immutable WorkGrant + revocation row + reservations row + queue intent + audit + receipt in one writer transaction. It increments the conversation revision. A retained task must be accepted at its exact revision, same conversation and same title/purpose/completion rule; it cannot already have a grant. No second confirmation is introduced. Duplicate/restarted commands return the original receipt and never requeue. Grant snapshots retain the exact typed owner command, owner generation, Bot/configuration/route revisions, purpose, scoped snapshots, finite limits and expiry. SQL rejects grant mutation and attempt-snapshot mutation.

Task text is derived content. Acceptance resolves its committed `sourceMessageId`, checks conversation and live source/access ancestry, and records the exact `Work.source:MemoryRef`. Start, admission and every live grant barrier recheck it; an already withdrawn source refuses with `memory_source_unavailable`. The attempt packet includes the task source independently of current relevance selection. Parent-to-child input also retains the parent's source/access provenance. Acceptance still creates no execution authority, and a direct owner start has no inferred task source.

Authority is the intersection of the live owner generation, originating grant, captured/current enabled Bot capability and generation, exact selected route and current resource/share policy. No Schway session identity supplies authority. `ScopePort.current(tx,ref):ScopePolicy|null` is a **trusted read-only service integration port**, using the same transaction for atomic policy reads. Its default denies all resources. Later resource/share owners supply revisioned active policies: owner Bot, optional named receiver/work scope, tool list and immutable snapshot `{id,revision,hash}`. A private resource is accessible only to its owner Bot; a share only to its named receiver. The reference must also appear in the Bot's explicit resource ceiling. Model/request data cannot install this port or create a share. Raw paths, transitive shares, changed revisions/content hashes and revoked records refuse. Concrete share creation/storage/lifecycle remains #253/#262; fixtures supply trusted current policies to prove these barriers without pretending that physical isolation shipped.

`S14Authority.admit(workId,requestId,Admission,parentId=null):Attempt` captures immutable input, Bot, route, grant, tools, scopes and per-attempt call/output ceilings. It reserves one step/attempt/model call and all allowed output bytes before dispatch. An identical admission retry returns its original record and cannot create a second queue claim; the trusted scheduler must never redispatch a returned historical attempt. `delegate(parentAttemptId,requestId,Admission)` additionally intersects the parent's narrowed tools/scopes and the receiver ceiling. Waiting parents can delegate a bounded child. No permanent Bot is created. TEAM14-01 now admits bounded concurrent graph steps under app.work-graph/v1 and the conformance-tested shared public credential lifecycle. Actual unsettled transports retain capacity; excess lanes queue.

`reserveTool(attemptId,tool,ref|null)` rechecks live authority and charges a call immediately before a trusted scoped adapter uses it. Both attempt and grant call ceilings apply. `commit(attemptId,WorkOutput)` repeats owner/grant/Bot/route/resource checks before writing immutable result evidence; oversized, stale or late output rolls back. Reservations are not refunds or actual provider usage (`actualUsage:null`). Separate committed sibling results are retained in `work_results`, outside the 128 KiB JSON record cap, up to the reserved 1 MiB total output. `Work.result` is the latest committed attempt ID (or null), never an inline or concatenated body. `WorkView.results: WorkResult[]` returns immutable `{attemptId,workId,state,text,committedAt}` rows in commit order; the Web result renders their text in the same order. Command receipts retain only the bounded work reference and never hydrate result bodies. Each row records the executor's original `ready`/`waiting` state independently of the attempt's effect-held lifecycle. When an effect is denied, expires without execution or finishes with a known outcome, the service re-evaluates waiting attempts and their work. Only a committed `ready` result with no held effects can move an attempt to committed and its otherwise settled work to ready. An explicit `waiting` result stays waiting; unknown effects remain held. Stop preserves the stopped/stopping fence. Ready means evidence for owner review, never an automatic assertion that a completion rule/report is complete. Structured reports and exact source/coverage validation use app.report-artifacts/v1; ordinary result readiness alone certifies no report or owner completion.

Stop immediately revokes only the named grant generation and queue intent, denies its unstarted cards and fences all later calls/publication. Transport cancellation is requested **after commit**, so a rolled-back stop cannot abort a live call. State stays `stopping` until actual running calls/effects settle; then `stopped`. Unrelated grants remain untouched. No routine dispatcher is integrated in this slice (#255). Interrupted native attempts retain capacity and become blocked/reconciliation-required on exclusive boot; no automatic work replay is enabled before #254 supplies native discovery/reconciliation. Unknown effects remain reconcile-only. Cancelled work is not requeued.

`drain():Promise<void>` admits the finite trusted DAG through independently scoped `WorkExecutor` runs; see app.work-graph/v1. The opt-in root installs bounded internal research through the same pinned `schway/host` adapter and the grant-bound public-web adapter in [app.parallel-web/v1](app.parallel-web-v1.md). BOX14-01 also adds explicitly granted local report work over the pinned public Schway core-tools backend; computer and public-web tools can be combined in the same work attempt. Its two-component computer has no network and no browser-session extraction; public reads stay in the service-owned gateway, never the computer. It installs no routine, external performer or fallback; see app.bot-computer/v1. Programmatic test fixtures exercise scoped guards/delegation and external-ledger races without actual sends. Later handlers must integrate these barriers rather than treat model-supplied tool names as authorization.

Queries: `authority.list(actor):Work[]`, `authority.view(actor,workId):WorkView` (work/grant/current revocation/reservations/actualUsage/attempts/effects/results); HTTP `GET /api/s14/work`, `GET /api/s14/work/:id`. Lists expose the newest 100 work items; individual work retains all bounded grant attempts/cards. Work states: proposed, accepted, queued, running, waiting, ready, blocked, stopping, stopped. Attempt states: running, waiting, committed, settled, interrupted. Reasons are safe machine codes. Owner UI maps these to the existing Opus states.

Final bundled store: application_id `0x4a495431`, user_version **16**, no automatic upgrade from unreleased schemas 1–15. The combined schema retains the reviewed original result `state` (`ready`/`waiting`) in `work_results` alongside memory, Parallel and computer tables; older S14 versions refuse with the same fresh separate-path next action. Added tables: work_items (conversation FK); work_grants (unique work FK, immutable JSON); grant_state (grant FK/generation/revoked); grant_usage (grant FK/reservation counters); work_queue (unique work FK/queued-claimed-blocked); work_attempts (work FK, unique work/request ID, payload digest, immutable snapshot); attempt_usage (attempt FK/calls); work_results (unique attempt FK/work FK/immutable text/time/original state). Computer tables are `bot_computers`, `input_leases`, `computer_operations`, `computer_inputs` and `computer_attempts`. Effect tables/triggers are in [app.effect-approval/v2](app.effect-approval-v2.md). Fresh/unknown-format refusal and backup classification remain documented in app.conversations/v2; these tables are application state, while passwords/session hashes are sensitive authentication state and not ordinary export material. No new backup/export capability is implied (#263).

They require the original live unchanged grant, remaining budgets, settled transports and no held/unknown effects; no new grant, refund, fallback or external-effect retry occurs. Retry uses a fresh bounded attempt. Summarize uses a bounded selection of existing current evidence owned by the first granted Bot, zero tools, exact source refs and explicit coverage limitations. `Work.recovery` records mode/requestId/source refs; `work-recovery.ts` supplies the bounded selection/input and the shared graph drainer uses its retry-specific key with the same capacity/transport reservations. Unstarted original lanes are cancelled with retained history; committed results remain. Active transports still block recovery after provisional result commit. Combined schema 16 retains computer activity together with graph/report/review storage; recovery itself uses existing JSON/queue/receipt storage. See the UX14-01 HTTP handoff for all bounds and error states.
