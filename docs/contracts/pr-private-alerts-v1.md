# `pr.private_alerts/v1`

Owner: Jit #24 (PR03). Parent spec #1, blocks on #19 (PR02 report) and #13 (TG03 outbox). Uses `pr.private_report/v1`, `pr.monitoring_authority/v1`, `delivery.outbox/v1` (including its send-time guard) and `jobs.attempt_fence/v1`.

A committed report creates a private alert only for findings that pass the visible evidence policy, with duplicate/stale suppression and delivery linkage. Producing an intent in `waiting` (no Telegram binding yet) is valid; nothing here claims live Telegram delivery.

## Storage

Additive tables created by `ensurePrSchema` (PR tables stay outside the formal `user_version` ladder, as in PR01/PR02):

- `pr_alert_policies(project_id, version, record_json)`: versioned owner policy history; latest version is current.
- `pr_alert_decisions(sequence, id, project_id, report_id, digest, record_json)`: append-only `AlertDecision` records; an identical re-evaluation returns the latest record instead of appending.
- `pr_alerts(intent_id, project_id, report_id, finding_id, candidate_id, monitor_id, policy_version, record_json)`: `AlertLink` from each outbox intent to the report/finding/base/head/trigger-policy/owner generation that produced it.

## Policy

- `DEFAULT_ALERT_POLICY` (version `ALERT_POLICY_VERSION` = 1): categories `correctness,security,behavior`; `requireEvidence:true`; `requireActionable:true`; `minimumSeverity:"info"` (no threshold); `notifyPartial:true`. The default is explicit and persisted as version 1 on first admission or first owner change.
- `readAlertPolicy(tx, projectId)` returns the latest `StoredAlertPolicy` (or the default with `persisted:false`; reads never write). `listAlertPolicies` returns history.
- Owner command `pr.alert_policy.set` (`SetAlertPolicyCommand`, `Application.execute`, shared `command_receipts` + audit, web channel only): `expectedRevision` is the current policy version; payload `{allowedCategories ⊆ correctness/security/behavior, minimumSeverity, notifyPartial}`. Evidence and actionability cannot be disabled; extra fields, `style`/`uncertain` categories and stale revisions are rejected (`invalid_alert_policy`, `stale_revision`). Receipt `AlertPolicyReceipt {policy, previousVersion, retiredIntentIds, decisions}`: pending intents whose finding no longer qualifies are cancelled with `alert_policy_changed` (sent ones untouched) and current non-stale reports are re-evaluated (`trigger:"policy_change"`). Every report of the project is processed in the command transaction; there is no cap.
- `evaluateReport(report, policy)`: pure pass; held reasons include the finding's first validation error / `not_actionable`, `category_not_notifiable`, `evidence_required`, `severity_below_minimum`, `partial_scope_held`. Severity only narrows evidence-backed findings, never substitutes for evidence.
- HTTP: `GET /api/projects/:projectId/pr/alert-policy`; `POST /projects/:projectId/pr/alert-policy` (session, Origin, CSRF; form fields `cat_<category>=on`, `minimumSeverity`, `notifyPartial=on`; JSON `allowedCategories[]`, `minimumSeverity`, `notifyPartial`).

## Keys and admission

- `alertKey`: `pr-alert/<reportId>/<findingId>/v<alertPolicyVersion>/<head12>/<triggerPolicyVersion>` (hashed fallback when long).
- Report commit: the `pr.review` job's fenced commit calls `admitCommittedReportAlerts` in the same transaction as `persistReport` (`trigger:"report_commit"`). Admission runs inside a savepoint; any failure rolls back only the admission and never loses the report or faults the queue. `prReviewWork({ alertBytes })` bounds payload bytes (service wiring passes `config.messageBytes`).
- `admitReportAlerts(tx, {projectId, reportId, maxBytes?, trigger?}, now)` (also `Application.admitPrAlerts`, `trigger:"owner_admit"`):
  1. re-read report (stale overlay incl. owner generation), monitor and candidate; whole-report suppression for stale/failed/incomplete/running, monitor not active/revoked, candidate closed/superseded/cancelled/stale, base/head/trigger-policy drift, or a whole-report owner dismissal (`report_dismissed`);
  2. evaluate the persisted project policy; finding-level dismissal holds `finding_dismissed`;
  3. hygiene-recheck each qualifying finding (secret-like or Telegram destination content held as `payload_hygiene`);
  4. a finding grouping (the finding plus its same-report `duplicateGroup` copies, matched by service-canonical finding ID) that already has a notified alert under another policy version of this report is `already_notified` (no duplicate). Notified means pending (`waiting`/`queued`/`claimed`), `sent` or `unknown`; `cancelled` and definitive `failed` deliveries never reached the owner and do not count;
  5. commit one guarded intent (`guard:"pr-alert"`) per remaining finding via `commitDeliveryIntent` replay dedupe; per-finding outbox failure is held `admission_failed`;
  6. store the `AlertDecision` (per finding: `notified`/`already_notified`/`held`/`suppressed`, reason, intent id) and the `AlertLink`s. Result: `{admitted, suppressed, held, decision}`.
- Payload (`buildAlertPayload`, ≤ min(maxBytes, 3500) bytes, condition/impact truncated by bytes): repo `owner/name#number`, base/head short, trigger policy, finding id/category/severity/title, location, condition, impact, evidence type/ref, service-owned report path `/projects/<projectId>/pr/reports/<reportId>`, plus `คำเตือน: ตรวจไม่ครบ…` when coverage is not complete. Every PR-derived field passes `neutralizeDestinations` (`src/security/destinations.ts`): any URI scheme, protocol-relative URL, Markdown link/autolink, e-mail, Telegram/WhatsApp link, `www.` host and bare host with a path or port is replaced by `[ลิงก์ถูกตัด]`; other domain-like/IPv4 tokens are defanged (`a[.]ts`). Credentials are detected by the shared `containsCredential` (`src/security/credentials.ts`: provider API keys incl. `sk-proj-`/`sk-ant-`/`xai-`, GitHub/GitLab/Slack/Stripe/Google/AWS/npm tokens, JWTs, private keys, auth headers, Telegram bot tokens, URL userinfo, secret assignments); a match marks the finding suspected, holds it at admission, and makes the builder and the outbox throw. `redactCredentials` is exported for export/diagnostic callers.

## Send-time recheck and retirement

- `prAlertCurrentness` is registered with `registerDeliveryGuard("pr-alert", …)`. The outbox runs it inside the claim and send transactions immediately before invoking the sender, and again when a result lands. It requires: link present; report not stale (base/head/trigger policy, monitor active, candidate current, owner generation); report status alertable; link base/head/trigger policy equal the report; owner generation equal the link; no report/finding dismissal; the finding still qualifies under the current policy. Paused monitoring holds the intent `waiting` (`wait_for_current_source`); every other failure cancels it before send with `stale:true` and the reason. A result landing after drift keeps the actual outcome and is marked stale.
- Finding IDs are unique per report: `canonicalizeFindingIds` (normalize + persist) renames repeats of one model-supplied ID `<id>-dup<n>` and records the raw ID as `PrFinding.duplicateGroup` on every copy, keeping each copy's own validated status. `evaluateReport(report, policy, preferred?)` notifies at most one copy per group among copies passing the current policy (a copy that already holds a live alert is preferred, else report order); other passing copies are held `duplicate_finding_id`. Policy-change retirement and the send guard judge each copy on its own (`findingQualifies`), so a live group alert is neither churned nor duplicated. Legacy rows that still repeat an ID hold every copy at admission and fail the guard (`duplicate_finding_id`).
- Legacy intents: the outbox reserves the `pr-alert/` dedupe namespace for guard `pr-alert`, so a guardless legacy intent is guarded (and the field persisted) and a new guardless `pr-alert/` commit is rejected. The guard backfills a missing link (`backfillLegacyAlertLink`, decision `legacy-backfill`) only when the key names an existing report/finding/head/trigger policy and the stored text equals today's sanitized payload; otherwise the intent is cancelled stale `legacy_alert_unverifiable` and its stored text is passed through `redactCredentials` in the intent payload, delivery report and source version (`scrubDeliveryIntentText`). `quarantineLegacyPrAlerts` (idempotent) runs at service start via `prepareServiceState` (`src/bootstrap.ts`), which `main.ts` calls before the job queue, delivery work or HTTP server are constructed, to cover settled legacy intents the guard never revisits: unsent ones are cancelled, settled ones keep status/remote/failure reason and only become stale.
- Per-attempt reports (`pr.private_report/v1`, schema v22): only the newest non-stale report of a candidate admits. `persistReport` retires older reports' alerts in the same commit (`superseded_by_newer_review`: pending cancelled, settled marked stale), and the send guard reads that overlay as not current. Across attempts, equivalence uses the service-derived `findingFingerprint` (sha256 of location path/line, evidence type, normalized evidence ref and normalized condition; stored on `AlertLink.fingerprint`, derived from the linked report for older links when the finding ID is unambiguous there), never the raw model finding ID or `duplicateGroup`. A grouping whose fingerprint was already notified by an earlier review of the same candidate (pending/sent/unknown, even if now stale) is `already_notified`, so a re-review does not re-alert it; a reused generic ID for a different defect alerts, and a retry after a definitive `failed` delivery admits one new intent for the current report. `retirePrSnapshot` retires alerts as `source_retired`.
- Backups: `pr_alert_policies`, `pr_alert_decisions` and `pr_alerts` (and the lazily created PR01/PR02 tables) are classified `include` in `backupImageTables`; none holds credentials. Export runs PR/delivery/output-source strings through the shared `containsCredential` via `exportSecretLike`/`sanitizeExportStrings`.
- Eager retirement (`retirePrAlerts`) in the same transaction as the change: poll supersede (`candidate_superseded`) and close (`pr_closed`), snapshot stale refs (`candidate_stale`), monitor revoke (`monitoring_revoked`) cancel pending intents and mark already sent/unknown/failed alerts visibly stale; dismissal (`report_dismissed`/`finding_dismissed`) and policy change (`alert_policy_changed`) cancel pending intents only. A terminal `failed` delivery keeps its status, remote rejection and failure reason (only `stale`/`staleReason` change). Retirement never claims a remote message was withdrawn.

## Read model

- `Application.prReports` returns `{project, items, reviews, pending, policy}`: `reviews` is every candidate's projected review state (`listReviewStates`, `pr.private_report/v1`); `pending` is the subset whose projected attempt has no report yet, `not_reviewed` or `running` (live `pr.review` job), with `reportId: null` (a running re-review keeps the earlier report only as `previousReportId`).
- `Application.prReport` returns `{project, report, annotations, evaluation, alerts, policy, decisions, decision}`; `evaluation` previews the current policy, `decisions` is the stored history, `alerts` are the linked intents (with `findingId`).
- Web shows `data-state` `not_reviewed`/`running`/`no_findings`/`findings`/`partial`/`incomplete`/`failed`/`stale` and per-alert `data-delivery` `waiting`/`queued`/`claimed`/`sent`/`failed`/`unknown`/`cancelled`, stale alerts labelled "ไม่ใช่ผลล่าสุด". `unknown` never reads as delivered and the report stays readable on Telegram outage.
- Owner dismissal is a revisioned `pr_report_annotations` row (`findingId` optional, `decisionId` = latest decision); it never rewrites findings and never writes memory claims.
