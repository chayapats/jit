## Conclusion and evidence boundary

The pinned public `schway/host` surface can compose a Jit-owned VM execution adapter and protected service/browser tools without replacing Schway's loop, providers, retries, compaction or native persistence. It does **not** supply a VM manager, protected browser, semantic website-effect firewall or guest-root isolation. Those are host integration and enforcement obligations, not missing engine APIs merely because they are absent from the export list. No demonstrated missing Schway contract warrants a new upstream blocker in this audit.

Unrestricted guest root cannot be assumed to obey a destructive-action gate inside that guest. Arbitrary authenticated website input and unrestricted outbound networking cannot be assumed to obey communication, payment, production or disclosure gates. These limits remain explicit activation gates below. Local fixtures verify integration behavior only; they do not certify S15 enforcement or make dependent implementation ready.

## Confirmed decisions versus proposed choices

Confirmed inputs are [S15-D02/03/05–12/17–21/23](../specs/S15-conversational-autonomy.md): an owner-supplied administrable working VM; core general browser work; shared approved team resources with narrower restrictions; system-enforced human gates; default GitHub publication holds versus a separately configured personal exception; production approval; and approved routes/budgets. The interview chose no numeric budget, VM transport, hypervisor, protected-browser product or complete website coverage.

The following placement, transport, policy matching and support limits are proposed engineering. Reviewing this audit can accept an integration direction without proving it or authorizing installation. A weaker product guarantee or narrower administration power needs a separate owner decision, not an implementation assumption. S14 remains the implemented default, including its private Bot computers, grant intersections, network restrictions and exact effects until explicit replacement slices land.

## Candidate trust domains and transport

The review candidate has three domains, separated from the guest administrator's authority:

| Domain | Custody and permitted operations | Required exclusion / proof |
| --- | --- | --- |
| Protected host/service | Authenticated owner ingress, standing rules/revisions, budgets, approval executor, work/effect/continuity/receipt ledgers, source access/withdrawals, vault/provider/channel credentials, Schway runtime/native home/sessions/correlation workspaces, management credentials, recovery control journal and original checkpoints | None is a working-VM disk, mount, environment, prompt field, guest socket or export. The owner may administer this host separately; working agents cannot. A sibling process/user/container **inside the administrable guest** is rejected. Host placement alone still needs mount, management and network evidence. |
| Administrable working VM | Work-scoped data, bounded temporary/output files, installed programs, guest Docker/services, untrusted shell/scripts and utility MCP processes | Treat root and every returned byte as adversarial. No host Docker/Podman/hypervisor socket, shared host home, vault mount, browser profile, control-plane service credential or guest-accessible unrestricted control API. Guest Docker controls guest resources only. Root may kill/forge the guest runner; that is loss of work/uncertain evidence, never owner authority. |
| Protected browser/effect domain | Website profile/cookies/2FA, approved account use, exclusive input leases, permitted observations, actual action execution and recipient checks | Must be beyond guest root, separately from shell/MCP. No reusable unrestricted authenticated handle, arbitrary JS/CDP/cookie export or profile mount. A browser on the protected host is still unsafe if unrestricted inputs can bypass its gate. |

Proposed transport is host-initiated, bounded request/response access to a guest runner through a protected VM-management adapter. The management credential and command admission remain outside the guest; no Jit/provider/channel/vault credential is installed there. VM endpoint identity comes from trusted configuration and a pinned VM generation, never a guest-supplied address. No concrete hypervisor/SSH/vsock protocol is selected here. A candidate requiring a guest-held Jit control credential must be redesigned or returned for review.

Freeze the transport protocol before VM15 implementation admission: version/framing/byte and time caps; VM/work/attempt/lease generations; request dedupe; canonical backend paths; file observation/atomic replacement semantics; exact environment; process-tree cancellation and real stop acknowledgement; output redaction/type/hash; errors and unknown outcomes; and reconnect/reboot behavior. Recheck current policy before dispatch and after every wait/publication. The runner may report exit status, but guest root can fabricate test output. Captured bytes/hashes prove what was observed, not a trustworthy guest attestation or compliance with held-action gates.

Schway stays in the protected domain with explicit native paths; its host workspace identity is separate from the backend's guest workspace. [research.ts](../../src/s14/research.ts), [native-recovery.ts](../../src/s14/native-recovery.ts) and [box-backend.ts](../../src/exec/box-backend.ts) already demonstrate that composition through public exports. Imported native workspaces remain fixed; a different guest VM does not authorize rewriting or relocating native history.

The external network control must be outside guest root. It denies direct IPv4/IPv6, DNS, UDP/QUIC, proxy/CONNECT, tunnels, link-local/metadata and control-network routes unless a reviewed capability explicitly permits them. It must survive guest firewall/routing/DNS changes and nested containers. A host/domain allowlist cannot distinguish private uploads or approved effects inside encrypted traffic. TLS pass-through to GitHub, a mail/payment site or a general proxy does not prove exact-action mediation. Even anonymous public sites can accept messages, uploads or purchases; lack of cookies is not a safe classification.

For dependencies, a protected bounded package acquisition/cache route is a candidate; exact destinations and outbound data need owner policy and fixtures. Existing registry scope explicitly permits disclosure to allowed registries and cannot be advertised as content-level prevention. No inherited S14 registry authority or new private-data recipient is implied. General browsing occurs through the separately mediated browser; unrestricted guest internet remains unavailable until its required effect/disclosure constraints are proven or the owner explicitly changes the guarantee.

## Operation and attack matrix

These are **required candidate outcomes**, not observations of a live S15 system. **Allowed** means current protected policy authorizes the exact operation; **held** means prepare only, awaiting applicable exact owner/rule authority; **denied** means no dispatch through that route; **unproven** means activation must refuse that advertised capability until the named gate passes. Each human-required row covers guest-root shell, scripts, dependencies and guest MCP as alternate paths as well as the browser/service route.

| Operation / attack | Guest-root shell, script or MCP route | Protected browser / service route | Proof status / gate |
| --- | --- | --- | --- |
| Ordinary scoped files/tests, sudo/package/program install, guest Docker/environment/services | Allowed within accepted administration boundary and finite limits; no host-shell fallback | Not a browser approval | Public backend logic verified locally; actual admin/transport/resources unproven G01/G02/G06 |
| Kill runner, reboot guest, erase `/`, destroy guest Docker volumes or work tree | Root can do this; hard prevention cannot be claimed. Unapproved major destruction must be held under the target, creating unresolved RT15-01. | Host recovery can restore protected checkpoints, not prevent the delete | **Unproven G02**; no activation with both unrestricted root and an unsupported prevention claim |
| Read/change protected policy, approvals, owner identity, ledgers, native state, vault, management socket | Denied by external custody/routing, irrespective of guest UID | No agent operation to edit authority; owner ingress authenticates separately | Actual denial unproven G01/G05; sibling guest service rejected |
| Steal browser cookies/profile, attach CDP, export tokens or invoke authenticated arbitrary JS | Denied; no session material/endpoint in guest | Denied to agent; narrowly reviewed browser operations only | Unproven G03; login/takeover is not session export permission |
| Public navigation/read, site scripts/redirects/popups/downloads or a GET with side effects | Direct general network denied; approved bounded read acquisition only | Allowed only for proven supported read workflows/destinations; unknown effects denied before dispatch | Unproven G03/G04; screenshot/GET/readOnlyHint alone never proves safety |
| Requested reversible personal document/task edit or solo calendar block; routine business record update | Direct account path denied; use protected broker | Allowed on exact current policy match; recipients/invitations/new terms divert to their holds | Policy/broker implementation unproven G05; ordinary writes need not all become manual approvals |
| Email/chat/public post/GitHub comment or PR publication/update | Denied as direct send/API/network route, including command-line clients and guest MCP | Held on final recipients/content/attachments; bounded current standing rule may allow its class | Unproven G03/G04/G05; exact changed action cannot consume old approval |
| Push/PR/review remediation and merge under personal GitHub exception | No raw repository token or generic authenticated client; protected action route only | Product default holds publication; merge requires separate authority. Personal rule must bind selected issue/start, repository/target/head, checks/reviews/evidence and revocation. | Unproven G05; this repository text installs no exception. Approval of another PR never supplies merge authority for the current PR. |
| Production deploy, including merge-triggered deploy or a browser admin action | Denied direct production identity/network | Held before merge/deploy unless an effective separately protected production gate prevents deployment | Unproven G03/G04/G05; green CI is not deployment authority |
| Purchase, transfer, bill payment; recurring-payment deviation | Denied direct payment/session route | Held on final payee/amount/currency/account; current bounded recurring rule may allow an exact match | Unproven G03/G05; new payee/limit/frequency never inferred |
| New business obligation/price/discount; major service/auth/approval change | Investigation and isolated reversible preparation allowed; execution held. Guest-root destruction remains RT15-01. | Held on actual impact/commitment, including alternate website/API paths | Unproven G02/G03/G05; line count/model labels do not decide impact |
| Private data in URL/query/DNS/path/header/body, browser form/upload/clipboard, script/MCP request or new model recipient | Direct unapproved egress denied, including allowed-host tunnelling; permitted release must bind actual bytes/recipient/purpose | Held for new recipient before disclosure; current approved services/providers usable within policy. Derived text/screenshots inherit restrictions. | Unproven G04/G05; public browsing and registry access cannot disguise a new disclosure |
| Provider refresh, route switch, new billing/budget increase | Denied credential/refresh access in guest | Schway owns selected-route refresh; Jit may select approved route/model/effort under finite reservations. New provider/account/billing/ceiling held. | Public lifecycle fixture verified; S15 reservations and live readiness unproven G05/G06 |

Never execute an unknown action just because an owner approved an incomplete card. | G03/G04/G05; unavailable reason must identify missing semantics/support |
| Stop/revoke/takeover, stale lease or changed action after approval | Fence new dispatch/publication; retain capacity until actual stop; do not replay guest command | Fence input across takeover and effect claims; changed/stale approval refuses. Lost response after dispatch becomes unknown/reconcile-only. | Native settlement fixture verified; cross-domain settlement unproven G05/G06 |

The browser gateway must control all effective paths in a supported workflow: navigation and redirects, frames/popups, keyboard shortcuts and form submits, script/service-worker/network requests, file chooser/download/upload, clipboard, cross-profile handles and owner/agent lease changes. Inspecting a visible button before a click does not bind the resulting request. If the backend cannot constrain and bind the actual effect to a current approved action, keep that flow unavailable; do not offer unrestricted authenticated control and claim the prompt will hold sends.

## RT15-01: guest destruction versus major-change prevention

This remains a **named owner tradeoff**, not a resolved enforcement design. Guest root can erase writable guest files, kill services and corrupt its own OS even if protected authority survives. Snapshots and disposable disks offer recovery; they cannot make the original unapproved destructive action impossible. No command-string denylist, guest-local sudo policy or wrapper can support both arbitrary root and universal prevention of that root's actions.

| Option | Capability / guarantee | Assessment |
| --- | --- | --- |
| A: unrestricted root plus snapshots | Broad administration; guest-local destructive changes remain possible without a gate | Reject as proof of the current prevention requirement. Selecting this weaker guarantee needs explicit owner acceptance of the residual impact and scope. |
| B: root in a bounded expendable guest; valuable/durable data and publication outside it | Preserves useful administration and protects externally held originals; loss of guest state/service still possible | Recommended research candidate. Freeze asset/service classification, approved maintenance impact and protected promotion/reset rules. It **does not resolve** every guest-local major disruption; remaining guarantee changes need the owner. |
| C: restricted privileged operations through a protected executor | Potentially prevents defined destructive operations if every effect is mediated | Requires a finite operation contract and bypass proof; may narrow S15-D03's administration capability. No silent replacement with a read-only VM or nominal sudo wrapper. |

Before activation, VM15/POLICY15 must supply concrete operations, asset/impact inventories, adversarial results and an exact recommendation. If no design meets both confirmed capabilities and gates, bring these evidence-backed alternatives to the owner. No decision is needed merely to complete this read-only audit; do not claim the owner selected B or accepted guest data loss.

## Protected action and continuity obligations

Implementable logic can be developed through the public seams above: authenticated owner-derived admission; current purpose/resource/route/model/action matching; finite reservations; immutable prepared action/content/recipient hashes; single-use claims; and publication fences. Actual exported TSDoc, rule/action schema, trusted actor/adapter signatures, supported-effect classes and deterministic protocol fixtures must be frozen in [POLICY15-01 #320](https://github.com/chayapats/jit/issues/320) before its implementation is declared ready. This document defines boundary requirements, not a hidden executable S15 API.

An approval executor must recheck current owner/policy/resource/Bot/VM/input generations, expiry, source/privacy lineage, destination, exact action revision and remaining budget immediately before dispatch. A standing match is a protected rule decision, never model self-approval. Unknown support is denied; a known action missing authority can be prepared/held. A durable claim precedes external dispatch. After interrupted dispatch, retain uncertainty and use explicit read-back/reconciliation, never automatic retry on a missing response. No distributed exactly-once promise is made.

Preserve [s15-state-transition/v1](s15-state-transition-v1.md) and ADR 0065 boundaries:

- Current continuity authority, command dedupe, independent withdrawals/effect claims, monotonic usage and policy revocations stay outside the guest and ordinary recovery images. A guest/VM/native snapshot cannot rewind them.
- Old S14/legacy stores and original checkpoints stay preserved; imported queues/grants/approvals never become fresh S15 execution. Private sources/accounts, receiver-bound shares and withdrawals retain restrictions before team relevance. No raw profile/volume merge or retrospective automatic-memory publication.
- Exact owner adoption selects build/artifact/schema/policy/host evidence. Absence of a personal GitHub rule means default publication holds and no merge authority. Surviving vault credentials or product requirements install nothing.
- A protected coordinator fences old and new runtime admission, including the prior executable. Do not assume a new S15 flag can fence a prior binary that ignores it. Freeze external service/management admission and current-ledger compatibility; raw process restart is not adoption or rollback proof.
- Pre-worker-release rollback must preserve any continuity already committed by cutover. After activity, an unrepresentable newer withdrawal/usage/effect/revocation or unsettled native identity makes reverse transition refuse. Restore of guest files cannot undo remote mail, push, payment or disclosure.
