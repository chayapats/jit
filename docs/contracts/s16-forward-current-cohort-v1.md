# s16-forward-current-cohort/v1

Status: implemented protected preparation component under
[ADR 0117](../adr/0117-s16-forward-payload-recovery-with-current-control.md).
Aggregate activation and complete service/client acceptance remain pending.

An original restore binds every selected/retained current SQL image, current
FILE/GitHub present bytes and missing pins, original physical identities, current
public native custody, authenticated helper observations, external/client facts
and the actual executing compatible package. Current native ancestry is deeply
verified in original private scratch; old candidate custody remains separate.
No history is merged into current authority and no byte is yet activated.

Actual complete SQLite writer reservations protect a synchronous complete cut.
One original capability is registered before reservation, including partial
opener failure; unknown rollback/disposal retains that capability and process
exclusion for original close retry. Only documented journal bytes 18/19 normalize.
Every current image is integrity checked and retained as a separate immutable
staged image, never written over a live source. Source identity/format/hash must
match on retry; missing current authority refuses instead of taking old SQL.
The SQL component separately pins each private source inode/owner/mode and its
complete logical image. A real WAL checkpoint may change main-file size/timestamps
while preserving those pins and that exact image. Byte physical identities cover
the actual byte namespaces; SQL main-file attributes are not duplicated there as
an extra incompatible consistency rule. Each actual collector still verifies its
original main-file attributes within that individual current observation.

A fixed SQL staging directory is empty before its inode and complete current
plan are independently pinned in a capture_backend intent. The bounded protected
current.json includes original operation/config/time/revision, recovery-stage
scope, all component values/physical identities, native/package hashes and exact
SQL manifest. Journal hashes precede metadata/image writes. A saved independent
intent can reconstruct absent unprepared metadata only from identical fresh
current facts and its original still-present directory; it never recreates an
owned missing directory or overwrites changed/partial SQL. Confirmed or prepared
missing members/metadata refuse recreation. Extra/linked/foreign/over-budget
members refuse without cleanup or eviction.

After original copies and independent integrity/readback, reservations release
conclusively before asynchronous native/helper validation. All current byte,
external, public-native, helper and package facts revalidate; a final fresh
complete SQL cut must match every original image. Only then is the independent
original current-cohort action observed, while that final genuine SQL writer cut
still excludes independent writers. Its conclusive release precedes returning.
Operations revision alone never proves
freshness. New SQL/WAL/native/reference/helper/external facts invalidate the cut.
A closed/retired parent or original session invalidates its observations.

Preparation is not activation, admission or proof of compatible service/client
lifecycle. The future repair coordinator must bind exact absent current pins to
an independently verified candidate, record original parent/temp/target identities
before bytes, and explicitly verify every planned transition. Strict current byte
observations reject even matching repaired members; no generic ignore-changes
callback weakens that guard. After planned repair, complete original SQL/native/
helper/external/package facts and every original present byte must still match.
Unknown effects retain their original identities and stay blocked/deduplicated.

Existing 256-source/1-GiB-per-image/2-GiB complete SQL and per-component bounds apply.
The protected combined current record is bounded to 64 MiB, allowing both existing
4-MiB FILE/GitHub catalogs, two 16-MiB host identity sets and separate bounded
helper/external/native metadata without truncation. The shared original recovery
staging limit includes these records, all SQL/native copies and candidate scratch:
12 GiB, 250,000 nodes, depth32 and 1 GiB per file. The coordinator must separately
reserve same-parent repair temps before ingestion. Physical/account/device and
owner-host cutover evidence remain separately labelled.
