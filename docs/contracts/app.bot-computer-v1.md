# app.bot-computer/v1

BOX14-01 (#248), FR-35/36/38/40; NFR-04/06/07/14. Opus product UI is delivered (design section 17); device, assistive-technology and real Linux host evidence remain pending. See ADR 0050 for engineering choices and limitations.

`src/s14/computer-types.ts` exports the exact data shapes. `S14Application.computers:S14Computers` is the service seam. Public methods are `view(actor,botId):ComputerView`, `prepare(attemptId):Promise<void>`, `open(attemptId):ComputerSession`, `drain():Promise<void>`, `sweep():void`, `recover():void`, `screenshot(actor,botId):Promise<Uint8Array>`, `activity(actor,botId,limit?):ComputerActivity[]`. `activity` is read-only: the newest bounded lines from existing owner receipts, input outcomes and attempt bindings, with no text, coordinates, image or runtime detail. It lists neither service-initiated stops nor what a Bot did on screen. `ComputerSession` contains the pinned public `schway/host` `ExecutionBackend`, an `InputLease` and `release():void`. Trusted handlers alone call `prepare/open`; model/request data cannot install a runtime or select a handle.

`BotComputer` is `{id,botId,revision,generation,botGeneration,ownerGeneration,workId,state,reason,limits,workspaceId,profileId,lastUsedAt}`. All IDs are opaque; none is a path, URL, cookie or control endpoint. `ComputerView` is `{computer:BotComputer|null,lease:InputLease|null}`. Creating a Bot or conversational reply provisions nothing. Jit follows the same grant checks as every Bot. The foundation Bot's reserved `computerId/profileId:null` fields remain unchanged; this query is the authoritative computer binding, avoiding a Bot configuration revision solely for runtime activity.

Typed authenticated commands use the foundation envelope, shared receipts/CSRF/exact-key rules and owner-scoped retry namespace:

| Kind | Exact payload | expectedRevision |
| --- | --- | --- |
| `computer.open` | `{botId,workId}` | computer revision, or 0 before creation |
| `computer.stop` | `{botId,computerId,generation}` | current computer revision |
| `computer.reset` | `{botId,computerId,generation}` | current computer revision |
| `computer.delete` | `{botId,computerId,generation}` | current computer revision |

Open rechecks the original live typed `work.start` grant, owner/Bot generations, enabled Bot, exact captured configuration/route/resources and explicit `computer` tool in both grant and Bot ceiling. It creates no broader grant. `prepare` lazily records the same intent for an admitted attempt; there is no extra owner confirmation. An attempt binds immutably to one computer generation before tools. Stop/reset/delete fence its future tools and late publication even when the originating Work grant has not been cancelled. Lifecycle commands require a current authenticated owner and exact Bot/computer/revision/generation, including when the original grant has expired. Reset/delete are destructive exact commands; UI must show the two data scopes before submitting them. Full Bot retirement/deletion remains #262.

States: `starting`, `running`, `stopping`, `stopped`, `resetting`, `deleting`, `deleted`, `unavailable`. Start/stop/reset/delete commit an intent first; receipts retain that original intent snapshot. Query again for runtime settlement. Reasons are safe codes, never stderr. At most two logical computers may hold runtime capacity. Unavailable/uncertain runtimes retain their slot until an exact stop verifies settlement; reopening the same logical slot does not allocate another one. Each has two isolated components. Default **per component** ceilings: startup 30 s for the complete pair, CPU 500 millicores, RAM 512 MiB, 128 PIDs, dedicated persistent filesystem capacity <=1 GiB, `/tmp` 64 MiB, `/run` 16 MiB, shared memory 64 MiB, swap disabled. Idle is five minutes measured by the injected clock. Trusted configuration may select finite limits up to four times the defaults; these are safety ceilings, not measured host sizing. Idle stop removes processes, preserving identity/data. Reset/delete stop both components before wiping only that Bot's two filesystems; opaque volume IDs rotate after verified success. Filesystem roots remain mounted. A deleted computer is a tombstone; a later current scoped open may provision a fresh generation.

The rootless local Podman runtime uses two digest-pinned images, separate PID/IPC/UTS/cgroup/network namespaces and independent ext4 filesystems, exact mounts, read-only roots, dropped capabilities, no-new-privileges, fixed environment and `--network=none`. The workspace sees `/workspace` only; the browser sees `/profile` only. No host home, application/native state, backup, Jit/provider/channel/vault credential or control socket is mounted. The existing `jit.box.runner/v1` and `createBoxBackend` are reused only for workspace operations. The protected browser uses the existing bounded `jit.box.cdp-stream/v1` pipe; no listening control endpoint exists. Copied/cross-computer runtime handles refuse.

Persistent disk enforcement requires **two separately mounted dedicated ext4 filesystems per Bot** beneath `<JIT_S14_COMPUTER_ROOT>/<botId>/{workspace,profile}`. This is an operator prerequisite, not folder isolation. Jit verifies canonical non-symlink parents, filesystem mount root/device uniqueness and total capacity before any process, then exact container mounts and actual kernel CPU/memory/PID/swap ceilings before runner/browser dispatch. Missing/unverifiable enforcement refuses; no quota estimate, directory-size watcher, privileged mount helper, remote/local retry or host-shell fallback exists. Rootless/nested namespace, subordinate UID/GID, cgroup, FUSE and TUN failures have safe diagnostic codes in the [runbook](../runbooks/s14-bot-computer.md).

Phase A exposes local report tools in the computer. Both components have **zero network egress**; separately granted public reads use the service-owned Parallel adapter (#249/#250), which can run with the computer and scoped memory in the same attempt. Browser navigation/login/site adapters, browser text/cookie/profile extraction, arbitrary CDP/JavaScript, MCP and consequential browser effects are unavailable. Unknown submit/confirm/write actions are refused, including after takeover ends. This deliberately does not claim usable logged-in websites or general browser research. Local report edits stay inside the workspace; no local shell can send/push/publish remotely. `runComputerWork` uses exact public Schway core tools and reserves each model continuation/compaction call at dispatch through the public route-bound Model, as well as every runner call. No Schway bump/private import is needed: `vendor/schway-1.0.0-rc.2-697bf40.tgz`, `schway.host.release/v2`, `schway.host.core-tools/v1`.

Schema **8** includes `bot_computers`, `input_leases`, `computer_operations`, `computer_inputs` and `computer_attempts`. It also retains `work_results` with original result state and all memory/Parallel tables. Earlier unreleased schemas 1–7, legacy and unknown versions refuse with fresh-state before writable open; no automatic upgrade is supported. Boot fences leases/attempts, consumes interrupted input as unknown and stops existing components; it never replays startup, input or a destructive operation. Native recovery, managed backup/export and full lifecycle integration remain #254/#263.

Evidence: `tests/s14-computer.test.ts`, `tests/s14-computer-podman.test.ts`, and existing runner/backend tests. Fixtures prove service/argv/protocol barriers, not kernel isolation. Linux x86_64 unprivileged Proxmox LXC and arm64 Lima process/network/resource/persistence/reboot smoke are explicitly **pending**.

CODE14-01/02 refinement (combined schema 14): the same network-free backend now supports typed owner-granted repository clones, edits, offline install/test commands and actual diff/check artifacts through app.coding-work/v1. It does not acquire network or credentials; registry-required checks remain skipped/unavailable. Exact approved push/PR effects run in the separate trusted broker after object/diff verification under app.git-effects/v2. No authenticated process or service Git credential runs in the computer.
