# APP01 application foundation contracts, v1

Owner: Jit #3. Status: implemented on this issue branch; integration requires the reviewed artifact to land in the target base. These are Bun/TypeScript application contracts, not a claim of production Schway or Pi support.

| Contract | Public entry and behavior |
| --- | --- |
| `jit.app.foundation/v1` | `src/main.ts`: `setup`, `reset-owner`, `serve`; `readConfig` in `src/config.ts` validates finite development settings. No provider or external service is loaded. |
| `app.transaction_store/v1` | `TransactionStore` / `AppTransaction` in `src/store.ts`: synchronous immediate `transaction`, consistent deferred `read`, `close`. Never await inside callbacks. State, receipts and audit share one SQLite commit. |
| `app.owner_identity/v1` | `Application.setupOwner` is trusted local-only; `login` → opaque session; `authenticate` → `OwnerActor`; `logout` revokes it. Actors are instance-issued capabilities checked against a current server session at every operation; objects decoded from model/channel payloads cannot impersonate them. Future bound channels require their own verified issuer adapter. |
| `app.command_receipts/v1` | `Application.execute(actor, CreateProjectCommand)` → `ProjectReceipt` after commit. `(ownerId, requestId)` is the receipt identity across browser sessions. Canonical payload identity includes command kind, explicit null project scope, exact name and expected workspace revision. Exact replay returns the committed result before checking current revision; different payload rejects with `request_id_conflict`. |
| `app.project_commands/v1` | `project.create` has `requestId`, `projectId: null`, `expectedRevision`, `payload: {name}`. Create is scoped to the installation's project collection revision; creates distinct stable project/group UUIDs together, with one group enforced by a unique project relation. Subsequent project mutations must use an explicit stable project identity and revision. |
| `app.project_read_model/v1` | `Application.workspace(actor, offset?)` → `Workspace`; `project(actor, projectId)` → `Project`. Bounded pages include `hasMore` and collection revision. Same display name can identify multiple projects; it never resolves scope. |

The HTTP ingress maps `POST /projects` forms and `POST /api/projects` JSON to that same command. JSON fields: `requestId`, `expectedRevision`, `name`; send the authenticated HttpOnly cookie, exact configured `Origin`, and `X-CSRF-Token` from the owner form. Actor/project identity cannot be overridden in payload fields. `GET /api/projects?offset=0` returns a bounded workspace; `GET /api/projects/<id>` reads one project. Failures use safe error codes; internal SQLite errors and auth secrets are not returned.

Schema v1 is an application store, not a session transcript. Migrations take an exclusive writer transaction, recheck the current schema, snapshot an existing v0 database to a mode-0600 `.pre-v0-<id>.sqlite` before applying DDL, and atomically advance `user_version`. Snapshot failure aborts the migration. A future schema is rejected before journal/schema changes. Fresh empty stores have no previous state to snapshot. Snapshots contain private data including password hashes and need the same protection as the original database; they are not the full managed-backup/restore feature from OPS01/02.

APP01 test evidence: owner setup/login/create/reopen, duplicate/mismatched/stale commands, concurrent independent writers, process death at both write stages, COMMIT failure rollback, reset/expiry/logout fencing, form rendering, future schema and snapshot fixtures. `bun test` and `bun run typecheck` require no subscription or Schway checkout. Full human host/account/reboot evidence remains FEAS03/04/05 and OPS05.
