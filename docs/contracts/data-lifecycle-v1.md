# Owner data deletion lifecycle and deletion ledger, v1

Owner: Jit #30 (MEM05). Schema: 17 (`deletion_previews`, `deletion_ledger`, `deletion_operations`); later shape changes live in `record_json` and need no migration. Contracts delivered: `app.data_lifecycle/v1` (preview `app.data_deletion_preview/v1`, operation `app.data_deletion_operation/v1`) and `app.deletion_ledger/v1`. Consumed: `app.memory_lineage/v1`, `app.source_records/v1`, `app.run_port/v1`, `jobs.attempt_fence/v1`, `jobs.session_reconcile/v1`, `ops.backup_manifest/v1`, `app.command_receipts/v1`.

## Public application surface

- `Application.execute(actor, DeleteCommand)` accepts `memory.delete.preview`, `memory.delete.confirm` and `memory.delete.retry` from the authenticated Web owner only, through the shared receipt path (replayed request ID returns the original result; changed payload is `request_id_conflict`). Model output and retrieved content cannot issue or confirm these commands.
- `Application.deletionPreview / deletionOperation / deletionOperations / deletionLedger` read previews, per-scope operations and the identity-only ledger. Web: GET/POST `/[api/]projects/:id/memory/deletions[/:previewOrOperationId]`.
- `JobQueue.reconcile(port)` (startup, in `serve` and `startFullApp`) runs session reconciliation, then one budgeted managed-delete pass, and retains `port`. `JobQueue.reconcilePendingDeletions()` requests one further serialized pass through that port; the application calls it after a committed confirm/retry. Without a reconciled port nothing is dispatched and operations stay pending until the next startup.
- `startFullApp(input)` is async and awaits `queue.reconcile(teamPort)` before returning an active handle.

## Preview (`DeletionPreview`)

Scope is one exact committed lineage `{projectId, source:{sourceId, revision, generation}}` that is current and available. The preview is bound to the project revision, expires after 15 minutes and lists the complete affected inventory:

- `affected.sources`: the scope (`relation: "scope"`) and every descendant output (`"derived_output"`), resolved by lineage, not text: outputs recorded in `memory_derived_sources` for affected memory contexts, and outputs attributed (`attribution.runId`) to runs whose manifests cite an affected source/claim. It also includes `"quoted_copy"` sources: a source committed from owner task or decision wording that quotes an affected source or claim payload of at least 8 characters verbatim. Such a source is the text source of an `origin: "owner"` task proposal, or the `memory_decision_sources` source of an owner decision. It is matched by exact reference whatever its availability, since supersession only fences a decision source and its payload stays. These sources mirror owner wording, so each is deleted with the scope: payload nulled, tombstoned, derivatives purged. Its proposals follow `affected.taskProposals`. Other owner messages and topic titles are separate lineages that the owner deletes on their own. Resolution is transitive and may cross projects.
- `affected.claims`: claims from any affected source plus dependency/conflict closure, any project.
- `affected.contexts`, `affected.pendingJobs`, `affected.nativeSessions` (`DeletionNativeSession`: `jobIds`, `dispatched`, `selectiveErase: false`, `collateral` = manifest sources/claims outside the scope).
- `affected.backups`: every recorded whole-store snapshot (retention bounds the list). Neither the bounded manifest coverage nor wall-clock order is proof of absence; `evidence` is `"coverage"` when the manifest names affected data, otherwise `"whole_store_snapshot"`. `state` is never the persisted manifest state: it is `verified` or `incomplete` (with `reason`, e.g. `image_missing`) from `verifyBackupArtifacts` against the application's backup directory, or `unchecked` when no trusted directory is supplied.
- `affected.exports`: app-owned export artifacts that confirmation purges: every non-failed export of an affected project (`evidence: "affected_project"`), plus any export elsewhere whose coverage names affected data (`"coverage"`). Coverage lists only resolver-emitted sources and claims, while raw task, proposal and decision text is serialized too, so complete coverage that does not name the deleted data is never proof of absence. Exports are regenerable and bounded by retention, so the purge is conservative. Failed exports published no artifact and are skipped.
- `affected.obligations`: owner tasks and decisions, recorded only as `{kind, id, revision, evidence, effect}`. No title or other payload-bearing text is persisted in a preview, receipt or operation. Included are every active task/decision of the scope project (paged, not a prefix) with lexical overlap (`evidence: "lexical"`), any linked by source lineage (`"lineage"`), and any task or decision in any project whose text quotes an affected source/claim payload of at least 8 characters (`"quoted_copy"`). An active task whose current proposal is blocked, and a current (unsuperseded) decision holding a copy, are `effect: "blocked_owner_copy"`. The decision adds the blocker `owner_decision_copy:<decisionId>` until the owner supersedes it. A superseded decision holding a copy is `"redacted"`. All others are `"retained_unchanged"`.
- `affected.taskProposals`: every task proposal revision (current or historical) citing an affected exact source generation (`evidence: "provenance"`) or whose title/summary quote an affected payload of at least 8 characters (`"quoted_text"`), with owning task, task state and revision. Historical proposals, and current proposals of inactive tasks, are `effect: "redacted"`; the current proposal of an active task is `"blocked_active_task"` and adds the blocker `active_task_current_proposal:<taskId>` (edit or close the task first).
- `affected.taskEvidence`: every task completion evidence artifact (`task_evidence_artifacts`) whose exact source generation is affected, with task state and revision, artifact revision and whether it is the task's latest artifact. The latest artifact decides an active task's readiness (`ready_for_review` versus `evidence_stale`). So for an active task (`proposed`, `accepted`, `ready_for_review`) that artifact is `"blocked_active_task"` and adds the blocker `active_task_evidence:<taskId>` until the owner completes, cancels or supersedes the task. Deletion never silently downgrades it. Older artifacts and those of closed tasks are `"reference_unavailable"`: identity stays and the source reads unavailable.
- `affected.deliveries`: local delivery copies, linked by provenance (the report's own source generation is affected; schedule summaries of affected outputs are followed through their occurrence to the delivery report source) or holding an exact quoted copy of an affected payload. `effect` is `cancel_and_redact` for unsent intents and `redact_keep_state` for settled sent/unknown/failed ones (the outbox never rewrites a terminal transport outcome, so a definitive failure keeps its status and failure reason while its text is redacted).
- `wholeSession {required, reason, reasons[], sessionScope[]}`: required for a shared topic identity (`topic_identity_shared`), an unresolvable orphan (`native_orphan_unresolvable`) or a dispatched native session holding collateral (`native_session_collateral`). The run port has no selective erase, so `sessionScope` enumerates each such `context:`, `source:` and `claim:` identity the whole-session delete removes.
- `blockers[]`: `unreadable_record:<table>` (including unreadable backup/export manifests, and any quoted-copy target record in `team_runs`, `coordinator_syntheses`, `jobs`, `job_attempts`, `decision_proposals` or `command_receipts` that mentions an affected payload but is not parseable JSON), `active_task_current_proposal:<taskId>`, `active_task_evidence:<taskId>`, `owner_decision_copy:<decisionId>`, `scrub_set_exceeds_bound` (more than 4,000 distinct affected payloads), `short_payload_unlinked_copy` (a payload under 8 characters appears in an output, delivery, decision proposal, task proposal, owner decision or job record not covered by provenance), `inventory_scan_ceiling:<table>` (200,000 rows per table), `inventory_truncated:<list>` (display bounds on sources/claims/contexts/pendingJobs/nativeSessions/exports/obligations/taskProposals/taskEvidence/deliveries) and `inventory_closure_ceiling`. Any blocker disables confirmation (`memory_delete_blocked`). Backup truncation is flagged only, because backups are a declared residual.
- `inventoryDigest`: SHA-256 over canonical affected identities, revisions and lifecycle states (source availability, claim status, job state, native app state/dispatch/collateral, obligation revision, task proposal and task evidence identities with task revision/state and effect, backup/export IDs, blockers, whole-session scope).

Inventory scans page through whole tables by rowid; relevance is decided before any bound applies.

## Confirm

`confirmDeletion` rejects an expired/unknown preview, a project revision change, a changed scope or a recomputed `inventoryDigest` that differs (`memory_delete_stale_preview`; re-preview). Blockers reject with `memory_delete_blocked`. `acknowledged` is required, and `acknowledgedWholeSession` whenever `wholeSession.required` (`memory_delete_ambiguous`). A duplicate confirm of the same preview (any request ID) returns the existing operation (`duplicate: true`) and deletes no new scope. It is answered right after the preview identity and project ownership are validated, before the expiry, revision, acknowledgement and scope checks, so an expired preview or an advanced project never turns a duplicate into `memory_delete_stale_preview`.

In one transaction it fences first (pending/in-flight citing jobs invalidated with `source_retired`; affected `team_contexts` moved from `active` to `retired`), then purges `content_text` and marks every affected source generation unavailable, marks claims deleted with the redaction marker, redacts cited text in `memory_extractions`, `team_runs`, `coordinator_syntheses` and `job_attempts` manifests and in command receipts, redacts producing-run outcomes and proposal artifacts of derived outputs, deletes affected delivery reports (cancelling unsent intents with `source_deleted`) and redacts their local report/intent text while attempts and delivery state stay, scrubs exact quoted copies of the complete affected payload set (each ≥ 8 characters, sorted, in chunks of 500) in model outputs/job records/proposals and command receipts (raw and JSON-escaped forms; each JSON record is parsed and only its string values are rewritten, never object keys or values under structural keys such as `id`/`*Id`/`kind`/`state`/`status`, so a payload equal to a schema key like `projectId` cannot corrupt a record or a receipt replay; an unparseable record is never raw-replaced), re-fences stale contexts/extractions, redacts affected task proposal titles/summaries (whole fields for `provenance`, the quoted copies for `quoted_text`) and the mirrored task text of inactive tasks, removes the quoted copies from `redacted` superseded decisions, nulls `title`/`summary`/`text` of matching receipt records, deletes affected format-2 exports (`export_artifacts` plus `export_artifact_bodies` rows) in the same transaction, writes identity-only tombstones and opens the operation. Only format-1 `legacy_file` exports have a file, removed right after commit. Owner tasks, decisions and deliveries are never completed or cancelled. Their text changes only through the redactions above. A current copy is a blocker, never silently rewritten. Identity rows (sources, messages, lineage) remain so references resolve as unavailable.

## Operation (`DeletionOperation`) and reconciliation

`contexts[]` holds one `DeletionContextScope` per native session: `state` (`pending | deleted | delete_failed | retire_failed | missing`), `attempts`, `reason`, `nextAction`, `updatedAt`; completed entries are kept. `exports[]` holds one `DeletionExportScope` per affected export: `storage` `sqlite` (purged at confirm), `legacy_file` (`pending | purged | failed`, own attempt count up to `maxAttempts`) or `none` (no artifact). The persisted path is never a deletion target: only `<authorized root>/<id>.json` is removed, the persisted path must equal it (else `export_outside_authorized_root`) and it must be a regular file, not a symlink (else `export_path_untrusted`). The authorized root is the format-1 writer's root `<database>.exports` (resolved absolute), used identically by the application and restart reconciliation. `scopes[]` separates `app_store` (`purged`), `retained_backups` (`retained` or `none`), `local_exports` (`pending | purged | failed | none`) and `external_copies` (`not_attempted`: Telegram/provider copies). `state` is `complete` only when every context is `deleted` and every export is `purged`; otherwise `pending`, `blocked` (some native scope failed/missing) or `failed` (`retry_budget_exhausted` or `export_purge_failed`). Completion covers active-local serving and managed native sessions only; it is not forensic erasure.

`reconcileDeletions(store, port, now)` atomically reserves one pass per pending/blocked operation (operation and per-context `attempts` incremented before dispatch, never refunded), refuses at `maxAttempts = 5` and persists `retry_budget_exhausted`, then calls `port.delete(context)` per remaining context (the adapter's supported retire-then-delete lifecycle; Jit never edits native bytes) and settles each outcome. Startup passes and owner retries share the budget. `memory.delete.retry` only re-arms a pending/blocked operation; it never adds budget and leaves an exhausted operation failed. `purgeDeletedExports(store, now, operationId?, exportRoot?)` removes pending export files outside any transaction; it runs after a committed confirm/retry and at the start of each reconcile pass, and never consumes native budget. `reconstructLegacyExportScopes(store, now)` runs at the start of every reconcile pass (so at startup): operations persisted without `exports` get every live export of a tombstoned project (plus any their preview listed) as pending purge scopes, the registrations are removed and a `complete` operation is downgraded until the files are purged; it is idempotent. Post-commit work is queued only for a newly created or re-armed operation: receipt replays and duplicate confirmations queue nothing.

## Ledger and lifecycle consumers (`app.deletion_ledger/v1`)

The ledger fails closed: any ledger query error on a current schema raises `deletion_ledger_unavailable` (503) from `readDeletionLedger`, `deletedSource` and `deletedClaim`, which blocks extraction, context use, export and restore replay. Only the explicit pre-migration path (schema older than 17 and the table absent) reads as "no deletions recorded". `readDeletionLedger(tx)` returns `{operationId, projectId, kind: "source"|"claim", sourceId, claimId, revision, generation, deletedAt}` ordered by deletion time, with no payload, actor secret or duplicated text. `deletedSource`/`deletedClaim` deny extraction, context assembly, notification and late writers; exporters apply tombstones; restore replays the latest installation lifecycle ledger (below) into the quarantine before workers are enabled ([ops-quarantined-restore-v1](ops-quarantined-restore-v1.md)). `lifecycleSafeManifests(tx, value)` projects persisted manifests for owner APIs (the job API uses it for attempts): unavailable source/claim text is replaced by the marker.

## Installation lifecycle ledger and checkpoint (`app.deletion_ledger/v1`, schema 23)

`lifecycle_ledger` is the latest trusted ledger for restore (OPS02). Triggers on `deletion_ledger`, `memory_suppressions`, `memory_suppressed_claims` and `memory_suppressed_sources` append one entry per committed row in the same transaction: `{sequence, kind: deletion|suppression|suppressed_claim|suppressed_source, entry_key, subject (source:<id>:<rev>:<gen> or claim:<id>), project_id, record_json, recorded_at}`. Records are identity-only (ids, revisions, generations, timestamps; never payload, forget reasons or overlaps). Migration 23 backfills existing history. The table and `lifecycle_checkpoint` are installation-scoped: backup images exclude them and every activation keeps the live rows. `deletedSource`, `deletedClaim`, `suppressedSource` and `suppressedClaim` also consult it (fail closed with `deletion_ledger_unavailable`; only a store older than 23 without the table reads as empty).

The checkpoint file (`ledger: "jit.deletion.ledger/v1"`, `contract`, `revision` = count + 1, `head`, `count`, `digest`, `writtenAt`, `entries`) lives at `<db>.lifecycle-ledger.json` or the service `ledgerPath`; it is atomically replaced after each committed confirm/forget, at boot, by `startFullApp` and by every restore step (`syncLedgerCheckpoint` in `src/ops/lifecycle-ledger.ts`). A ledger is trusted only when the checkpoint is a verified prefix of the table (a lagging one is extended); `lifecycle_checkpoint` records the location and position already checkpointed, so a missing or placeholder file at an established location, a corrupt/self-inconsistent/other-format file, or a table that lost checkpointed entries is untrusted (`ledger_checkpoint_missing`, `_unverifiable`, `_incompatible`, `_mismatch`) and keeps a restore quarantined and `startFullApp` blocked at the quarantine gate. A seed placeholder (`{ledger, revision}`) is replaced by the real checkpoint only while no checkpoint was ever established; afterwards a changed location must hold a checkpoint that equals or extends the one at the previously established location, which must itself be readable and consistent with the table; the marker moves only after that proof (`ledger_checkpoint_relocation_unverified` / `_mismatch` otherwise), and a checkpoint older than the recorded position is `ledger_checkpoint_mismatch`.

## Deterministic evidence

`tests/memory-delete.test.ts` covers cross-project collateral, stale/duplicate/forged commands, digest-bound confirmation, crash/reopen at preview and confirm, budget exhaustion across restarts, per-scope partial failure in API/UI, direct-source sessions, whole-store relevance and unreadable-record blockers, lineage purge of paraphrased derived outputs and job-attempt redaction, whole-session acknowledgement and an end-to-end Schway worker session deleted by `queue.reconcile` alone and still deleted after reopen. `tests/ops-service.test.ts` proves `startFullApp` completes a pending deletion before returning. ### Jit reply lineage (app.jit_reply/v1, schema 25)

Role proposals (app.role_proposals/v1) live in the same reply record. When a deletion purges a reply output as a derived output, the name and responsibility of Jit-authored proposal revisions are redacted with it; owner-authored revisions and roles created by acceptance are owner configuration and stay.

A forget also binds every Jit reply output that was given a forgotten source, directly or through an earlier reply, into `memory_suppressed_sources`, and therefore into the lifecycle ledger. It also fences pending replies that cite any of them. The lineage is identity-only (`jit_reply_sources`, `jit_replies.reply_source_id`). Jit reply records live in `team_runs` (`kind: "jit_reply"`) and follow the same deletion scrubbing as other runs.
