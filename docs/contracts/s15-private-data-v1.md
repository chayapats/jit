# s15-private-data/v1

Executable DATA15-01 (#335) contract, 2026-11-03. Requirements: **FR-13/17/18/35/37/38/39/41; NFR-07/09/14; S15-AC11**, with S15-D20/D23. Exported TSDoc in `src/s15/disclosure` defines the host API. This is an explicitly composed S15 service; S14 remains the default. It installs no account, provider, standing approval, budget or owner-host adoption.

## Lineage and custody

The protected owning source catalog supplies exact source/resource revisions, `public`, `private`, `personal` or `business` classification, withdrawal and owner-release eligibility. Unknown classifications/revisions refuse. Classification comes from the source/resource scope; string patterns do not discover private data.

`read` stamps ancestry before source bytes are released. The work's accumulated lineage and its admitted source fences apply to all subsequent output, including uncited paraphrases, tool arguments, query strings and screenshots. `derive` records text/screenshot/artifact descendants; `inherit` transfers their ancestors only after current resource/source checks. Neither a model nor caller-supplied citation list can remove an ancestor. The protected SQLite journal has an exclusive process lease and refuses missing/foreign continuity; restart preserves lineage without recreating a dispatch context. Stored lineage contains refs, not source contents or credentials.

Protected ingress/read/attachment/memory adapters must call these host ports before giving private bytes to a work closure. Private execution must compose the disclosure catalog and owning hooks. The module does not infer classification for unregistered guest files, intercept arbitrary host networking or retroactively reinterpret S14-private data.

The shared journal's reserved record slots preserve updates to admitted work/VM/browser ancestry when new admissions reach capacity. New work lineage or descendant rows refuse before release when no slot remains; capacity never clears an ancestor or turns a denied route into public data.

## Recipient and exact-action gates

A fixed protected route resolver derives every recipient from complete actual outbound arguments. Browser URLs include host/path/query, method and body bytes; protected adapters include their actual target fields and attachments. Unknown routes/recipients refuse before resolution or send. A recipient ref is an owning-service identity including revision and generation; a model label, hostname suffix or source assertion cannot register one.

Standing recipient approvals are finite and bind purpose, resources, data classes and optional exact source revisions. Each nonpublic ancestor must fit its applicable captured approval. Existing approved recipients remain usable inside current work/policy ceilings. A new recipient requires owner-releasable ancestry and a POLICY action with `disclosure` and `new_egress`. Missing nonreleasable/current source authority is a denial, not something an approval can repair.

The existing `ActionSlip.action.disclosure` contains recipients, purpose, source revisions/classes and an exact-byte length/SHA-256 summary. The existing immutable payload and `payloadBytesBase64` retain all exact credential-free bytes. Approval uses the existing authenticated POLICY API and binds the complete action revision/hash. It permits one disclosure, does not approve the recipient generally and does not require a second confirmation for another field of that same action. Changed content/recipient/ancestry, withdrawal, expiry, owner/work/policy revocation and a claimed action refuse. Unknown outcomes remain charged and reconcile-only.

Standalone emitters require installed effect classification as well as recipient resolution. They cannot erase communication/payment/publication/production gates. `protectAdapter` preserves the original adapter's classes, transaction/GitHub preconditions and final payload contract, adding disclosure ancestry and rechecking inside its original commit callback. An owning adapter remains responsible for actual single-send behavior, final bytes, response semantics and no redirects/retries. This module supplies no new email/GitHub API or credential transport.

## Actual route integration

- **BROW:** `BrowserOptions.disclosure` checks every non-login broker request. A public-looking GET/query with private work ancestry becomes an exact held action before `fetch`. Form and supported complete text-body submissions receive the same checks; background/unattributable requests, unknown semantics, multipart/file-picker uploads, opaque bodies and redirects remain unavailable under BROW's existing support boundary. Protected response/text/image source refs are recorded before work publication. Browser input and results exchange accumulated profile/work ancestry, preventing a lease/navigation change from laundering private DOM/form/storage state. `browser(route, profileRef)` uses the protected profile identity; omission conservatively shares ancestry across the route. Owner-only credential entry stays in BROW's protected login path, outside action payloads.
- **MODEL:** `ModelOptions.disclosure` filters candidates before selection and rechecks current lineage/recipient before every public stream and publication, including after tools read new data. Complete credential-free model request content is screened at the public stream seam. Unapproved private recipients are excluded, without sending private context to classify itself or switching account/provider/billing. Registering the hook also binds selection recipients for `CatalogPort.allowsModel`; POLICY rechecks that resolver when reserving/consuming calls. Omission of recipient registration cannot make a private call eligible. MODEL's known provider-internal credential/retry/physical-send limitation remains; no Schway internal/protocol interception is added.
- **VM acquisition:** `VmPolicyIntegrationOptions.disclosure` enriches the real `working_vm` acquisition action. The exact URL/query and download descriptor stay in the original payload. Already approved data recipients can use the ordinary scoped path; a new data recipient holds. `WorkingVmService.acquire` retains an unclaimed held invocation so repeating the exact request after approval continues that same prepared action. Changed bytes create a different action; lost sessions cannot resume it. The original live POLICY claim is rechecked before DNS and after DNS immediately before HTTPS request creation. Downloads remain bounded, public-address pinned, hash-verified and nonredirecting.
- **VM registry proxy and output:** `WorkingVmOptions.disclosure` plus `proxyLease: proxy.lease` binds the protected actor/VM to each real proxy lease. The proxy checks the callback before DNS, after DNS, before tunnel release and on traffic. `vmInput` stamps current ancestry before guest input. `vmOutput` imports the VM's ancestry before returning any guest result; inaccessible ancestors withhold the result. Sibling work cannot launder stolen guest bytes through a protected browser/model/acquisition route. All registry sessions on that VM also inherit its accumulated releases. VM labels survive work/session/reboot changes; this slice provides no automatic declassification/reset. Unknown registry host-to-recipient mappings and new recipients of private ancestry refuse opaque egress. A CONNECT tunnel cannot present exact future private bytes for one-action approval.

Compose `disclosure.catalogs(vm.catalogs(baseCatalog))` with the real POLICY catalogs, register protected adapters before opening POLICY, attach the services, and pass the BROW/MODEL/VM hooks only from protected host code. The base catalog remains responsible for Bot/resource consent; the decorator intersects it and cannot grant access. Install the host registry recipient map explicitly; a guest-provided recipient cannot select the destination. A callback or route resolver never enters prompts or guest JSON.

## Honest enforcement limits and evidence

The owner selected RT15-01 option B: keep valuable/private originals, credentials and real effects outside the administrable VM where possible, with external deny-by-default networking and a destination-controlled registry proxy. **The registry proxy is destination control only.** TLS tunnels and even allowed public registries can receive content/metadata; covert channels through approved destinations are not prevented. No claim of content-level prevention, a universal disclosure firewall or prevention of guest-local destruction is made. Releasing private data to the VM can conservatively restrict later package acquisition; owners must establish actual destination/data/purpose approvals rather than relying on an encrypted host allowlist.

Credential screening rejects registered/credential-shaped content and checks supported URL-encoded and UTF-8 base64 body fields before persistence. Generic opaque/binary bodies refuse; safe binary/file upload support needs a separately protected sanitizer/owning adapter contract. Screening is defense in depth, not private-data classification or proof against arbitrary encoding/steganography. Browser screenshots can be retained with ancestry; this slice does not add BROW file-picker uploads or a generic binary screenshot upload API.

Deterministic evidence lives in `tests/s15-disclosure*.test.ts` and the DATA15 cases in `tests/s15-vm-policy.test.ts`: real POLICY held/slip/approve/one-send behavior, source/recipient/policy/approval races, derived handoffs, restart continuity, actual public Schway scripted model loops, actual broker requests to disposable local sites, actual proxy parsing with controlled DNS/connect seams and artifact final-request guards. These tests make no paid/provider/live-host calls. New guest-root/firewall/DNS isolation evidence on a real VM, Linux x64/arm64 acceptance, every service/site/adapter, prior-build rollback and owner-host adoption remain EVID15/CUT15 obligations. Existing VM/BROW evidence is not expanded by these deterministic tests.
