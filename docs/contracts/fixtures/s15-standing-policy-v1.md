# Standing-policy documentation fixture interpretation

The [JSON fixture](s15-standing-policy-v1.json) is complete synthetic **documentation input → required outcome**, not an executed suite, production store, imported permission or claim that these ports exist. All account/route/model/budget evidence is artificial. The [contract](../s15-standing-policy-v1.md) supplies the closed record schema. This guide fixes scenario interpretation so an implementer need not invent omitted values.

## Base world and isolation

Each scenario starts with an independent deep copy of `base`; operations run in listed order. `base.actions`, `rules`, `approvalExample`, `receiptExample`, `claimExample`, `reservationExample` and `observationExample` contain complete proposed records. Example approval/claim/reservation/observation records are **not** live entries in `initialContinuity`. Only the seeded work and its seeded request receipt exist initially. `commandExamples.execute` is a distinct new owner request; command scenarios count newly created work in addition to the seed. Scenario outcomes are required observations after the listed operations, not execution logs.

`current` is the fixture owning-service resolver, never client input or an authentication record. All exact refs in the base policy/rules/authority/actions resolve to active immutable synthetic catalog entries with the displayed identity/revision/generation. The enabled Bot ceiling, resource purpose/operation permission, current account consent and approved recipient restrictions are exactly the base policy's sets. The sole selected route/model/effort is the base selection, with live fixture availability. `recipient_new` exists as a known endpoint but has no standing private-data release; this synthetic resource permits the owner to release its exact current bytes to that recipient for one action. `source_fixture` is an accessible restricted source with no withdrawal. Its transitive dependencies are empty. No other catalog entry, provider, account, authority or numeric allowance exists. Unknown refs fail lookup, except deliberate malformed/stale inputs which refuse earlier.

The no-send adapter accepts only `replace/send/publish/merge/pay/disclose/major`, respectively deriving the exact classes and fields of the corresponding base action. It binds the complete final payload/attachment bytes in `blobs`, target version, recipients, transaction, GitHub evidence and impact. `replace` is a reversible edit; `major` has unresolved major impact. Other operations and unknown classifications are unsupported. The adapter's schema blob/hash is included. Its fake I/O is one conditional mutation with no redirect/retry; every listed final-boundary race has deterministic ordering. These properties are fixture assumptions, **not** evidence that a real VM/browser/broker provides them.

Required GitHub evidence is the complete `github_evidence` blob: synthetic exact head, acceptance, checks and reviews. The selected issue and execute authority are already present. Production impact is initially `none`; no protected deployment gate is installed. There is no personal GitHub, recurring-payment, communication or deny rule in the active base policy; the additional full rule records are proposals until the explicit `install_rule` setup operation.

`replace(path,value,rehash)` uses an RFC 6901 JSON pointer into the copied base. The target must exist; no merge/default inference or array append occurs. It is a scenario input/state override, not a production mutation API. A runtime mutation of an immutable record would require its own revisioned command. `rehash:["action:<name>"]` recomputes only that complete action's `actionHash` under the contract domain after replacement. An empty list leaves hashes unchanged deliberately. `current` overrides represent independent protected resolver facts such as revocation or a later generation. Names refer to exact complete records in the copied base, not abbreviated record fragments.

## Exact operation semantics

| Operation | Fixture transformation / observation |
| --- | --- |
| `owner_command` | Authenticate the named live actor and apply the exact `commandExamples[command]` through the owner port. Seeded receipt continuity is retained. `execute_changed` keeps the same request ID and changes selected issue to 321; it conflicts after `execute`. A first execute creates exactly one new local work intent/receipt and no remote mutation. |
| `owner_request` | A fresh authenticated request with listed intent, otherwise the complete base request and a distinct scenario/operation ID. `inspect` permits only inspection; `accept_obligation` retains one obligation with no queue/effect. |
| `prepare` | Evaluate the complete named action against current catalogs, action hashes, installed rules, live work and approvals. Materialize the same unclaimed revision once; no mutation dispatch/reservation. |
| `approve` / `deny` | Call exact action.decide for the current action/hash/revision using a fresh request ID and expiry `min(now+38000, action.expiresAt)`. Authenticate/check hard eligibility first; holds for missing final action approval may be decided, but unsupported/stale/out-of-scope actions cannot be approved. Use the full `ApprovalV1` shape exemplified in the JSON; record a deny for the exact revision. |
| `revise` | Mark prior unclaimed revision superseded; increment current action revision by one, recompute actionHash; no old approval matches. Refuse if any claim exists. Prior overridden payload is scenario input, not permission to mutate claimed content. |
| `install_rule` | **Synthetic owner setup**, not an agent mutation: accept the complete named rule plus policy change, then obtain fresh authenticated same-purpose execute authority and reprepare all unclaimed actions. Increment policy/work revision and generation once, add/sort the rule ref, set the matching personal pointer where applicable, recompute policy/authority/action hashes and rebind work/policy refs. Use a new ingress/request ID suffixed with scenario ID and operation index; append its complete receipt. Preserve old records/continuity as history. No old approval is reused. No claim exists at these setup points. `deny` takes precedence; ordinary mode supplies the hard action scope but never a human-required exception. |
| `claim` | Reevaluate all gates, atomically record the full ClaimV1/reservation and charge `action.upperBound`; mark capacity open. No fake mutation yet. The matching approval/rule and continuity generation are pinned. |
| `dispatch` | Prepare/evaluate, claim if eligible, final guard/permit consumption, one fake mutation and observation. `outcome:succeeded` yields `remote_verified`, conclusive settled transport and `actual=Vector(calls:1,spendMinor:"3", all other dimensions:0)`. `unknown` yields uncertain/null actual fields and unsettled transport. A claimed key refuses every subsequent dispatch, including when the first response is lost. |
| `final_dispatch` | Continue the existing claim at its final boundary. Recheck current authority/approval/payload. On pre-I/O revocation/expiry/hash mismatch, make zero mutations and record `not_dispatched/local_guard`, retaining charged reservation/claim; fake transport is then conclusively settled. No new reservation. |
| `concurrent_claims` | Independently approve listed actions, then use a protocol barrier at the same budget/claim writer boundary. The named winner commits first; the other observes the remaining ceiling. No fake I/O. Different effect slots share the same continuity budget; concurrency is 2. |
| `substitute_wire_payload` | Replace only the fake transport's proposed payload bytes, leaving protected action and hashes untouched. Final binding rejects the mismatch before fake I/O. |
| `crash_recover` | Lose process actors/permits and non-durable fake results; retain every durable claim/reservation/receipt. An unsettled claim projects unknown/reconcile-only. Reissue only the seeded work actor after current metadata reconciliation; do not auto-dispatch or release unsettled capacity. |
| `restore_old_projection` | Replace application projections with their pre-scenario seed, then reconcile against **current** continuity. Keep claims/reservation maxima, request IDs, usage unknowns, withdrawals/revocations and open capacity; no old queue dispatch. Missing continuity refuses rather than seeding empty state. |
| `owner_statement` | Append exact current owner's `did_not_occur` statement for that claim with basis owner_statement. It is not verified no-effect proof or permission to clear/retry. |
| `reconcile` | Perform one independently authorized/budgeted fake read-back; `ambiguous` keeps unknown. Charge an additional vector with calls=1, reads=1, all other numeric fields=0 and spendMinor="0". It sends no mutation and does not overwrite the retained owner statement basis with remote verification. |
| `dispatch_pause_after_io` | Approve/claim/final-guard the exact action and perform one fake mutation; pause before recording the conclusive response or result publication. No automatic retry while paused. |
| `observe` | Append the matching conclusive fake remote observation after the pause, preserving the actual remote fact even if work publication was revoked. No additional fake I/O. |
| `publish_result` | Resolve current work/access/lineage before publishing. Refusal leaves the protected effect observation intact; withdrawal suppresses payload reads and derived output. |
| `logout` | Revoke only the named owner session/actor; do not change owner generation or existing work/approval authority. |
| `ambiguous_ingress` / `quoted_ingress` | No typed approval command results: multiple pending candidates or source quotation provides no exact owner decision. Return `approval_reference_required`; no approval/effect. |
| `inspect_same_purpose` | A bounded read-only inspection inside the current admitted purpose; creates no decision or mutation authority. |
| `import_s14_history` / `recovery_drain` | Preserve listed historical states, private scopes and reservations; old grants/cards/routines are nondispatchable. Unknown remains reconcile-only. Drain admits none. No S14 record is interpreted as a new S15 allowance. |
| `withdraw_receipt_payload` | Withdraw only the prior scenario receipt's private result payload. Preserve request ID, original command hash and safe historical result identity in current continuity. Duplicate ingress returns `historical_withdrawn`, changed payload still conflicts. |
| `validate_raw` / `validate_number` / `validate_minor` | Raw closed-envelope/primitive validation before side effects. Duplicate object keys are rejected before JSON.parse; valid ownerId-shaped JSON still fails exact envelope shape. Negative zero and leading-zero minor-unit strings refuse. |

Only `owner_live` is an issued live owner actor initially; `owner_expired` is revoked, `forged` is arbitrary JSON. Work operations use a separate registered seeded work actor, never an owner actor. Actor names in the file are fixture control labels, not serializable credentials. Fresh deterministic IDs are `fixture_<scenario-id>_<operation-index>_<record-kind>` (hyphens replaced by underscores). Reference sets are canonically sorted after synthetic setup; payload sequence order is retained. Any unspecified fake provider interaction is forbidden; any unspecified numeric field comes from the complete base record, not an implicit zero.

`expected` lists required observable assertions; it does not purport to be a full database dump. `claims/reservations/mutationCalls/reconcileReads/openCapacity/newWorkIntents/publishedResults` are scenario-local counts except openCapacity, which is the current unsettled count. `decisions` records the listed evaluation/dispatch outcomes of interest, not duplicate internal guard invocations. Charged vectors are cumulative and nonrefundable. Policy setup itself incurs no fake remote cost. Hash examples are static canonical-byte calculations only; no scenario was executed and no test pass result is claimed.
