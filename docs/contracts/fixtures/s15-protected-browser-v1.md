## Complete input and expected-outcome meaning

Every `ScenarioV1.input` is a complete `WorldV1`, with no omitted defaults, patch DSL or inheritance: registration, binding/operation/support, complete optional #320 PreparedActionV1, exact child request/payload/action-or-read bindings, optional prior receipt, prior actual-capture inputs/bytes/target records, optional claimed context correlation, captured response, proof data, independent facts and all declared fake trusted-port facts. Null/empty fields are explicit. The ordered events and complete expected outcome are authored data. They are not generated by executing an implementation or calculating policy behavior.

`response` is an already retained immutable response and must agree with the input facts. `scriptedResponse` is a separate complete fake transport reply scheduled for a later `capture_response` event; it is not already recorded evidence. Initial sent/captured/closed facts describe history before the listed events. Those events do not re-send an already recorded physical input/request. Positive dispatch traces start with an unconsumed claimed context and no sent/captured facts, then explicitly dispatch, capture, close and observe scope before retrieval. Static trace checks validate these distinctions without executing the events.

The outer `PortFactsV1` describes **fake fixture setup at trusted seams**, not a production message or authenticatable JSON actor. `actor`, `context`, `verifier`, `supportRegistered`, `targetRegistered`, policy verdict/code, current binding/continuity, clock, remaining bounds, approval/personal-rule/deployment mode and write-only owner-input setup must be supplied by a future scripted harness's privately registered objects. A copied actor/verifier case installs a different object identity, not a valid identity string. Positive fake support/proof/policy facts establish no real browser capability or boundary.

The full #320 action samples use its exact pinned shape and `s15.action.v1` hash projection; this document does not redefine policy matching, actor issuance or full catalog storage. Each parent action payload is canonical ActionPayloadV1 with null policy.action before action hashing. Child payloads pin its projection hash, never the final operation hash. All input/child payload sizes/hashes and request body bytes are provided. RequestBindingV1.authority is exactly `action` with a complete PreparedActionV1 or `read` with a complete ReadRequestReservationV1. Read records pin operation/request hashes, work/attempt/profile/session, budget/continuity, finite bound/cost basis and expiry. Request bindings alone are scripted trusted request-admission inputs, not pre-existing charge facts or model-issued authority. `ports.requestContext` supplies a fake original/recovered/consumed child context; no serialized reservation authenticates it. Both arms pass through the same authorizeRequest/dispatchRequest ports. Fake policy decisions are explicit inputs; these are not whole-policy runtime tests or authentication evidence.

WorldV1.readCharges separately contains complete **already committed child read charge facts**. Each ReadRequestChargeV1 pins its reservation ID/hash, exact operation/request, budget/continuity generation, charged vector, usage snapshot and charge time/hash. ExpectedV1.readCharges records the complete resulting child charge history. Every initial charge remains byte-identical, with no refund or duplicate ID; any new child reservation requires a new authorized charge. `facts.charged` remains a parent-operation fact and cannot substitute for these child records. Existing actually dispatched public reads also carry their charge history explicitly.

D100 starts with one exact committed child read charge, an original unconsumed child context and zero remaining allowance; its expected charge record and requestReservationCount remain unchanged at one. D101/D102 retain that already paid history while refusing recovered/consumed contexts. D059 likewise records the previously charged child before its zero-allowance continuation. D103 is the contrasting **new** read: zero allowance, no child charge and no original child context; it returns budget_exhausted with zero sends/reservations and an unchanged empty child charge history. A future fixture harness can therefore distinguish continuation from admission without inferring charges from input labels or a parent's reservation.

`priorCaptures` holds complete synthetic previously captured document bytes and targets, whose observation/binding/document hashes must match an interaction/download. The producing prior slot is a synthetic immutable registry fact; it is not a real observed website. Target strings are narrowed references resolved in the private registry, not CSS selectors, owner authority or bearer tokens. A future harness must reject a target absent from the exact observation/current registry. No screenshot or target label proves effect semantics.

`untrustedInput` is exact raw bytes for deliberately unsupported/malformed proposals, frame failures or unsafe-content metadata. These bytes are **not** admitted operations, real credentials or executable content. The validated baseline world remains complete. A historical priorReceipt can bind a different valid operation hash to demonstrate request conflict. Expected rejections do not mutate those historical bytes.

Counter meanings are exact:

- `inputCount` counts actual physical input sequences in the illustrated history, including an owner sequence when present; it does not claim a remote effect.
- `networkCount` counts actual website requests, never cooperative cleanup or manager inspection. An already sent parent remains counted when a child is held/refused.
- `claimCount` / `reservationCount` count parent-operation claims/conservative reservations. `requestClaimCount` / `requestReservationCount` count separate committed child effect claims / child request reservations, including historical reservations that have not dispatched. They never combine a parent allowance with uncharged children. Continuation of an existing child reservation does not increase its count.
- `cancelCount` counts original-scope cleanup sends across all repeated cancel/signal events, not proof of cessation.
- `payloadAvailable` means the illustrated result path may hand off its exact retained sanitized payload at current scope. `facts.published` records the distinct final publication event. Boundary events have no observation/output/download bytes.
- Action revision/hash are those of the original parent prepared action (or an explicit unused sentinel for a read with no parent action). `action_decide`, claim, cancel and proof recording do not change them. `lease` / `takeoverGeneration` describe final input ownership; release never revives an old lease.

Facts are independently captured input/network, responseHash, channel, operation scope, process, outcome, cancellation, conservative parent charge, actual usage and publication. A response can be captured while outcome remains unknown, process running or output withheld. Rejected proof changes only decision/code; already recorded response/channel/input/network/usage/settlement facts remain. A valid process stop can change exact process/scope while an independently open channel stays open. Stop is not proof a historical remote action did not occur. Unknown usage stays null and conservative charges never refund.

## Byte and frame interpretation

Named records provide complete instances for proposed port/data signatures. Two frames contain both complete typed JSON records and **all** exact framed bytes as canonical base64/length/SHA-256. Frames use 4-byte unsigned big-endian payload length plus C(record); raw byte hashes include the header. Invalid frame cases provide their full raw bytes in untrustedInput and expected rejection, including after possible dispatch. No decoder, transport or backend was exercised.

FrameV1 uses separate directional RequestFrameBytesV1 and ResponseFrameBytesV1: 131076 / 4194308 total bytes and 174768 / 5592412 base64 characters, including the header. Payload BytesV1 retains its 2796204-character base64 cap. A complete response carrying a permitted 2 MiB image therefore need not fit the image payload's smaller byte wrapper.

`imageBoundaries` adds the complete deterministic `image_2mib_response` definition without duplicating several MiB of repeated bytes. Its input is a complete synthetic world containing a small valid synthetic PNG response template. RepeatedBytesV1 specifies **every** image byte as decoded prefix, exactly repeatCount copies of octet, then decoded suffix, plus full length/SHA-256. There is no omitted data, external file, random byte or runtime fetch. The prefix/suffix describe a 1x1 RGBA PNG with a private ancillary padding chunk; the final image is exactly 2097152 bytes. This is serialized synthetic protocol data, not a browser screenshot or visual-route evidence.

The exact materialization projection is: copy input.response; replace output with canonical BytesV1 of the recipe bytes; set observation.source to browser_image; replace observation.payload with `{id:'image_payload',bytes,sha256,mediaType:'image/png'}`; recompute only ObservationV1.hash using its stated domain/projection. Other response fields remain exact. Canonicalize the complete response, prefix its four-byte length, and wrap those full framed bytes with ResponseFrameBytesV1. The expected record gives all image/base64/response/frame sizes and response/frame hashes. A static checker materializes and validates these bytes/shapes in memory; it neither runs a browser/scenario nor decodes/renders an image. The materialized frame fits the response schema and intentionally exceeds payload BytesV1. No runtime payload/image bound is widened.

Canonical JSON, hash domains, projections, byte/time/resource ceilings, set ordering, response refinements, current-fence checks and protected dispatch obligations are normative in the contract. JSON Schema checks shape only; static semantic checks additionally verify hashes/bytes/projections, child bindings, prior-capture target lineage, response correlations and monotonic expected facts. The schema's `Text`/character bounds do not replace UTF-8 byte bounds, credential/sensitive-field validation or actual authority. Full target storage/DDL, real sanitizer/import/broker/verifier and protocol/platform proof remain open freeze obligations.

An eventual admitted implementation must turn these definitions into Bun/TypeScript scripted-port/fake-clock/barrier tests, including concurrent claim/reservation races, every wait/final-I/O boundary, wrong private object identities, abrupt process/manager loss and current-ledger rollback. Controlled real website/browser/VM/guest-admin/egress/account tests remain separate opt-in exact-build evidence. Static documentation validation never counts these scenarios as passing tests.
