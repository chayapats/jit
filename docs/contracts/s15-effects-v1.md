## Protected Google adapters

`registerGoogleEffects` registers `gmail_send` and `google_calendar` with the existing protected POLICY service. The host supplies current account/resource bindings, exact address-to-recipient identities, immutable attachment lookup, protected token acquisition, a `GooglePersonal` instance and explicit finite read/mutation/reconciliation bounds. Register its adapters/read validator before opening POLICY, then `attach` that service. Existing S14 Google protocol and event validation/serialization are reused; S14 authority and approvals retain their original behavior. No additional OAuth scope is requested: only existing `gmail.readonly`, `calendar.readonly`, `gmail.send`, `calendar.events` are understood.

Account/token lookup belongs outside the VM. Work tools have no account selector, token, host file path, generic HTTP endpoint, owner/control port or alternative shell/MCP send. Token acquisition happens before final `DispatchContext.commit`; exact current account, attachment bytes and POLICY authority are checked again before the fixed no-redirect/no-retry Google request. All final credential-free URL/method/conditional headers/body bytes are immutable in the action. Credentials are injected only into the protected protocol transport.

`calendar_read` acquires one bounded event observation through real POLICY read claims. Updates require that work's observation and exact etag, and send `If-Match`; stale provider versions fail without overwriting. Ambiguous dates, mismatched timezone offsets, unsupported all-day/special event types and unbound accounts/recipients refuse. Create uses a work-derived event ID and cannot overwrite an existing event. A solo one-time block matches an ordinary rule immediately. Current or proposed attendees, another organizer and notifications add `communication`; removing attendees does not hide the previous participants. A recurring series adds `major_change` by its multi-occurrence impact. Read-back verifies the exact event/timezone and retains a fresh-version undo proposal for an update. Undo is a new requested action, never an automatic retry.

`gmail_prepare_send` freezes From, To/Cc/Bcc, subject, complete body, attachment revision/name/type/size/digest/bytes and deterministic multipart MIME. Even a request saying send, including sending email to oneself, is held on the final action. CHAT replies to its authenticated owner use its ordinary guarded output port instead. Exact POLICY approval sends once. Re-preparation in the host-owned final-message slot supersedes the revision; changed recipients/content/attachments cannot reuse approval. Changed attachment bytes at the same revision are fenced before dispatch. A current bounded `communication` rule can authorize its whole configured class; a personal GitHub rule cannot authorize general email. A newly bound recipient outside work scope additionally requires exact disclosure authority and protected catalog release eligibility.

One final message and one calendar create are supported per work; separate existing event IDs have separate host-derived update slots. These conservative slots prevent a model retry from selecting a fresh effect ID after a claim. Multiple unrelated messages/blocks require separately admitted work, not a new caller-chosen retry key. Provider timeouts, mismatched sent copies and uncertain saves remain reconcile-only. Message reconciliation searches for the stable Message-ID and verifies the one SENT copy, including exact MIME/attachments; calendar reconciliation reads the stable event ID. No write is repeated to discover an outcome. Provider responses and conclusive rejections are separate from owner statements.

POLICY's additive `ActionAdapter.reconcileUpperBound` and `ReconcileContext.beforeRead` support the two physical reads required for Gmail reconciliation. The profile is charged before I/O in the existing recovery lane; each actual read rechecks authenticated owner/current catalogs/privacy and the original finite reservation after credential waits. The context expires when its invocation ends. The compatibility default remains one call/read for existing adapters. Optional bounded credential-free `AdapterResult.evidence` is committed with the observation, so verified provider identity/content/version/undo survive process restart. Dispatch/reconciliation return control facts only; private evidence is read through current guarded `inspect`, ActionSlip and `publishable` projections, and cannot enter cached CHAT approval-status records. These hooks introduce no Schway or S14 contract change.

## Controlled browser record service

`openFixtureRecordService` is a disposable loopback HTTP reference service with its own SQLite CAS, immutable record versions and durable operation journal. It is a controlled fixture, not an authenticated production document/task/CRM server. Place it outside the working VM and expose it only to the protected test broker. Its setup/evidence/rule methods are protected test composition, not agent tools or HTTP administration. No Drive, Docs or Tasks integration, vendor selection or universal website-write claim is made.

The service renders native forms for one versioned document, task or business record. Its trusted `BrowserSitePolicy` classifies the actual URL/form bytes and known server-side consequences; the real protected browser gateway performs reads, preparation, approval, single dispatch and observed publication. The service independently checks record/rule/evidence versions inside the actual commit transaction. Unknown fields, bulk operations, unknown recipients and payment-triggering records refuse before saving. Hidden notification/fulfillment metadata shares the record version, so it cannot silently change after observation.

Document title/body and task title/completion changes are reversible ordinary edits. A successful response contains the actual before/after version and content, with prior snapshots retained for recovery. Sharing adds `disclosure`, notifications add `communication`, and deletion adds `major_change`. Duplicate operation IDs cannot commit twice. Stale record/rule/source revisions require fresh observation. A lost response leaves browser/POLICY uncertainty; the optional protected `reconcileEffect` reads the service operation journal, never repeats POST. `BrowserOwner.reconcile` clears only the matching browser uncertainty after conclusive observed evidence. This works after losing the original resumable request; an absent/ambiguous remote journal entry stays unknown.

Business note/classification edits require one active exact factual source revision for each changed value and the current existing rule. Inferences/missing facts become held proposals. Prices, discounts, terms, governing policy, commitments, destructive changes and fulfillment consequences add `major_change`. A short price change waits while a long evidenced note may execute: field semantics and actual consequences determine impact, never line count or a model impact label. Hidden payment effects are unsupported without an exact transaction adapter.

The owner-only `decisionCard(owner, policy, actionRef)` projection authenticates through the existing ActionSlip and returns the exact target/version, impact reasons, fact/inference/missing evidence, apply/investigate/keep options and a recommendation with no authority. One existing exact approval authorizes that prepared direction; it does not authorize a later different price or commitment. JSON data follows the existing Claude-authored [F4 ActionSlip/DecisionCard](../design/S15-conversational-experience.md#f4-held-actions-approved-once-hold-) contract. No product screen or new UI/UX is authored; Thai/English state keys are additive.

## Conversation and route composition

Google registration supplies a real `ConversationToolPort`. `createEffectsConversationTools` optionally composes that with the protected browser and exposes a host-only `dispatchAction` hook for `ConversationPolicy`. Mount this hook so a held browser action resumes the original paused request, rather than using generic direct dispatch or repeating a click. Normal tool close retains only that bounded pending request; approval runs no further model/tools. Missing/lost/expired browser contexts refuse and require reconciliation. Inspection exposes only read operations; actual POLICY guards prevent a reversible scope from gaining communication authority.

`communicationClasses(route)` supplies the same communication gate for email/messages/public posts, and additionally GitHub publication for a GitHub comment. Real routes still need trusted exact semantics, recipient bindings and (for GitHub) current repository/head evidence. The controlled browser conformance routes exercise these classes; this does not install Slack, Telegram, GitHub or public-posting adapters. Unsupported shell/script/MCP/raw-browser routes receive no credentials or callable effect port. Working-VM egress/root enforcement and installation adoption remain the VM/DATA/EVID slices; local fixtures do not certify those boundaries.

Executable evidence: `tests/s15-effects-google.test.ts`, `tests/s15-effects-records.test.ts`, `tests/s15-effects-communication.test.ts`, `tests/s15-effects-conversation.test.ts`, `tests/s15-effects-recovery.test.ts`. These use a fake Google API, actual controlled HTTP services, deterministic browser protocol fixtures, scripted public Schway models, fake clocks and the real POLICY/CHAT/browser gateway. No Google/provider/account or real Chromium test is enabled by default. Live Google evidence remains optional and pending: owner-only self-send/dedicated test calendar, existing scopes only, raw evidence in ignored `.local`, credentials in protected configuration. No host is activated or migrated by this slice.
