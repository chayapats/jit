## `s16-desktop/v1`

The owner opens their existing service, signs in there and chooses Install in the client or browser. The browser confirms installation and creates a standalone app for that exact origin. The install control never claims success from displaying a prompt: installed state comes from standalone display mode or the browser's installation event. Unsupported, unavailable, dismissed and failed prompts are distinct from installation. Browser-menu instructions remain available when the prompt API is absent. App settings show the current service origin and explain native permissions and reconnect/update state in English/Thai.

Manifest identity and start path are fixed to S16; no credentials, endpoint parameters, custom protocol handlers, file handlers, share targets, scope extensions or host enrollment. HTTPS is required for remote installation, with browser-defined loopback development exceptions. Browser-managed session cookies remain confined to their origin. No session material or private client state is copied into an app package, another origin, a launcher, logs or a working VM.

Files use the existing owner-invoked file picker and protected upload/result/download paths. Microphone and notifications use their existing explicit controls and the browser/OS permission prompt. Installing or opening the app requests none of them. Permission denial remains recoverable through browser/OS settings, never a shell fallback. Native file access is limited to the selected File objects or the owner's chosen download destination; no persistent directory grant is added.

Only the service's existing authenticated APIs may start work or decide an exact approval. App/deep-link navigation is inspection, never authority. Query-based commands, arbitrary schemes, cross-origin URLs and unknown S16 paths are not launch commands. Browser origin rules, service Host/Origin/CSRF/fetch-metadata checks, sandboxed artifact rendering and exact-action revisions remain effective in the installed window. There is no privileged IPC surface to invoke.

## `s16-desktop-release/v1`

A release is a bounded immutable inventory of public bytes. The inventory identifies the contract, release SHA-256 and each asset's exact absolute same-origin path, full SHA-256, byte length and content type. It includes the compiled client with applicable license notices, styles, audio worklet, neutral English/Thai HTML shells, app icons and install manifest. It contains no installation-specific hostname, owner/session token, private API projection or model state. The release identity changes when any inventoried byte changes. Paths and inventories are generated by trusted package code, never taken from a page message or arbitrary remote manifest.

Public release assets are served with exact path/method/query validation, nosniff and an appropriate content type. A neutral shell has no private server rendering: it must reacquire the current session/bootstrap before rendering private facts. Legacy authenticated client paths remain compatible. Service/package outputs retain existing LICENSE/NOTICE/third_party custody; this slice imports no new third-party source or native runtime.

### Worker install and update

1. Fetch only the generated same-origin inventory with credentials omitted, redirect refused and a finite deadline/size bound. Check exact bytes, SHA-256 and content type before recording each public asset.
2. A partial cache is not a release. Commit its completion marker only after the entire inventory validates. Install failure removes only its own incomplete cache and never deletes the active or preceding complete release.
3. Do not force skipWaiting over an existing client. A waiting update is reported in the UI; it takes over after all existing app windows close. No automatic page reload, work resend or approval decision accompanies an update.
4. Controlled S16 navigation selects the active complete neutral shell, so HTML and code cannot come from different releases. Exact content-addressed assets come from that complete package. Unknown routes, arbitrary query/scheme/origin and every API/private response bypass this cache and retain service refusal/authentication behavior.
5. Retain the active and preceding complete public packages. Interrupted/malformed updates keep the prior complete app launchable. If required public bytes of the active package are missing/corrupt, recovery can use the preceding verified complete package or report unavailable; it must never label a partial package successful.

Only public static resources and neutral shells are eligible. Cache Storage must contain no request/response bytes from `/api/`, owner login/setup, files/artifacts, screenshots, protected browser sessions, generated model HTML, private download URLs, websocket/event streams or POST requests. Notification locale preference remains its separate non-private record. Storage pressure can evict browser caches; the app then needs a network connection to rebuild a complete package. Browser storage is recoverable delivery, not durable application authority.

### Recovery and compatibility

Disconnect produces an honest reconnect/offline state and withholds private projections that cannot be revalidated. Unknown work keeps its original durable request identity and requires existing read-back recovery; the worker never queues or retries effects. Reconnect refetches current owner/policy/source facts from the same service. An expired session signs in to the same installation; app installation cannot create a new owner.

Client code rollback cannot roll back server journals, owner generation, policy, withdrawal, budgets, action receipts or native sessions. Operator restoration of a prior service/client build must use existing compatibility/state-preservation gates. No app-cache operation authorizes a service update, schema conversion, production deployment or owner-host activation. Additive client capabilities remain negotiated through current bootstrap; unavailable features keep their existing honest state.

## Conformance and evidence obligations

- Verify actual installed standalone window and app identity, not only manifest presence, synthetic install events or browser viewport styling.
- Use that window and the actual service for Bots/work/files/results/approvals/computer views and original-send recovery. Scripted model/provider fixtures remain labelled deterministic.
- Prove completed package preservation across interrupted/corrupt install and closed-window activation; inspect every cached response and current server state.
- Exercise malicious navigation/deep links and a second origin; prove no cookie/CSRF disclosure, privileged native effect or host enrollment. Keep local API Host/Origin/token and inspect/execute regressions green.
- Exercise English/Thai, keyboard, loading/error/empty/reconnect and permission support/denial states using the actual bundle.
- Record exact source, package hash, OS/browser revision, command, outcomes and pending physical-device/live-service inputs. #431/#432 retain live account/device and owner-host acceptance.

No completion is claimed by this contract alone.
