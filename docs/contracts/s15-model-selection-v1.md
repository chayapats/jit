## MODEL15-03 renewal before listing with Schway `aac2fc0` (2026-11-03)

Delivered by [MODEL15-03 #381](https://github.com/chayapats/jit/issues/381). Pin: [tarball](../../vendor/schway-1.0.0-rc.2-39194f7.tgz), `schway@1.0.0-rc.2`, Schway main `39194f7439d3f97900477cfac22bbd7164937530` (merged via schway#457, tree `b63729cd5bc0a55b1fa9364ec57d28dec21a65d2`), SHA-256 `58c80215fa0d8330c73c07674038ae50aed5dd5e69cc9d95e5d421e689091b8a`. It adds `schway.host.route-renewal/v1` (`HostAuthBinding.renew`, `renewAuthRoute`, schway#455) under the unchanged `schway.host.release/v2`. Jit imports only public `schway/host` exports.

- **One credential lifecycle.** `openModelService` shares one `HostCredentialLifecycle` across its route hosts, renewals and catalog listings. The caller may supply `routeAuth.lifecycle`, which stays caller-owned. Otherwise the service creates one on first route use, over `routeAuth.store` or the OS secure store. Renewals and runs therefore share one single-flight token request, and listed choices stay bound to one credential owner.
- **Renew before an uncached listing.** The `listChoices` seam calls `host.auth.renew({ deadlineMs, signal })` before listing; cached choices need none, because Schway renews before each send.
  - A valid token is `fresh` and sends nothing.
  - An expired token, or one inside the refresh skew, sends at most one token request and is `renewed`. Renewal never sends inference or a catalog request.
  - Jit decides on `outcome`: `cancelled` maps to `cancelled`, `limit_exceeded` to `route_renewal_timeout`, and `failed` to the route status code. That code is `route_needs_login`, `route_rejected`, `quota_exceeded` (a rate-limited token endpoint), `route_integration_unavailable` (unreachable), `route_store_unavailable` or `route_store_invalid`.
  - A stopped or failed renewal sends no catalog or inference request.
- **Re-list rule.** If Schway rejects a *cached* choice as `invalid-input` (for example a new lifecycle credential epoch after a logout and sign-in), the cache is dropped and the step renews and lists once more. A choice listed in the same step that Schway rejects fails honestly with `route_choice_refused` (a new code in CHAT's safe codes); the cache is dropped and there is no loop.
- **Counting.** `catalogRenewal` records each pre-listing renewal of the step in `attempts`; the re-list of a cached choice adds one. It also records the latest outcome and route status, and the cumulative `renewalRequests`. That cumulative count is added to the step's `providerRequests.renewalRequests`, also when the step stops at the renewal, so a re-list never erases a token request already sent. A renewal that joins a run's in-flight renewal counts 0, because the run counts it, so summed steps never double-count.
- **Credential write fence.** Every `credentialWriteGuard` Jit passes (MODEL15 listing, renewal and route host; CHAT; GitHub runner) is `routeCredentialGuard(route)`. It checks credential ownership only: the write must target the credential identity of the route that host serves. It never checks work authority, cancellation or shutdown. A renewal whose response lands after its work was cancelled, or while the composition is closing (when `guardWork` refuses with `aborted`), still stores the provider's rotated refresh token. Refusing it would make Schway discard the token and force a new sign-in. Work fencing stays at the call sites and in `authorizeDispatch`.
- **Shutdown.** `ModelService.close()` still refuses synchronously while a step runs. It resolves once a service-owned lifecycle has closed. While a renewal whose caller stopped waiting is still storing a possibly rotated token, the lifecycle reports `busy`. `closeCredentialLifecycle` retries for at most `CREDENTIAL_CLOSE_BOUND_MS` = 35 seconds in total, backoff included. That covers Schway's 30-second refresher timeout plus the store write and stays well below the S15 unit's `TimeoutStopSec=60` (ops/package/installer/s15.ts), leaving time for the rest of shutdown. If the lifecycle is still busy at the bound, or the close fails otherwise, it logs `{"event":"credential_close_incomplete"}` (no credential data) and returns that code. It never rejects, so composition shutdown continues.
- **One lifecycle per process.** `composeS15` creates one credential lifecycle per composed installation, which is one per process in production. It passes that lifecycle as the caller-owned `routeAuth.lifecycle` to MODEL15, to CHAT `runConversation` (`ConversationOptions.routeAuth`) and to the GitHub VM coding runner (workspace factory `routeAuth`). Two renewals in one process therefore cannot race on a rotating refresh token. The lifecycle closes last on shutdown, with the same bounded `busy` retry. `S15CompositionOptions.credentials` (`store`, `fetch`) is the deterministic seam; production omits it and uses the OS secure store.
- **Limits.** CHAT and the GitHub runner do not list catalogs, so they need no pre-listing renewal; their hosts renew before each send. The S14 owner application in the same process keeps its own S14 lifecycle. Route availability (`checkAuthReadiness`) only reads the store. The S15 composition still has no observable sign-in event, so `forgetRouteCatalog` has no caller yet.

Evidence:

- `tests/s15-model-renewal.test.ts` covers:
  - a fresh process with an expired token, whose request order is renewal, catalog, inference, with `renewalRequests: 1`;
  - a valid token (`fresh`, zero requests);
  - needs-login, rejected, rate-limited and unreachable renewals, each with a distinct code and no catalog or inference;
  - cancellation before and after the token request, with `close()` waiting for the rotated token;
  - a held renewal past its deadline: `route_renewal_timeout`, the request count kept, and `close()` waiting for the rotated token;
  - a choice listed in the same step that Schway rejects, which gives `route_choice_refused` with its renewal counted and no loop;
  - a cached choice rejected after a logout and sign-in, which re-lists once with the renewal counted;
  - a renewal in flight when the work is cancelled and the service closes under a production-like guard: the rotated grant is stored and the next process renews without sign-in;
  - a Codex renewal through the service;
  - a run that joins an in-flight pre-listing renewal and counts 0, with one token request in total;
  - the `credential_close_incomplete` give-up within a bound below the unit stop timeout;
  - a renewal and a run on one lifecycle sharing one token request, counted once.
- `tests/s15-composition-credentials.test.ts` boots the composition with a CHAT interpretation and a MODEL15 step that both need renewal concurrently, and shows they share one token request.
- The packed consumer `tests/s15-model-packed-consumer.test.ts` proves that `renewAuthRoute` renews an expired token without inference and that listing then succeeds.

Executable codes added by this adoption:

- `effort_unsupported`: listed evidence lacks the pinned level; refused before I/O.
- `effort_unproven`: a dispatch or attempt whose requested, sent or provider-reported effort contradicts the pin; output withheld.
- `cost_bound_unknown`: a metered route without an enforced cap, or a dispatch whose cap differs.
- `route_control_refused`: Schway refused a body that could not carry the pinned controls; no I/O.
- `dispatch_refused`: a refusal that carried no Jit code.
- `auth_retry_refused`: Jit refused the resend after an auth rejection; the cause stays in the refused dispatch's `refusal`.
- `usage_invalid`: exact Schway counts differ from admitted sends; output withheld.
- `wrong_model`: dispatch route, provider or model mismatch.
- Route listing and provider status codes: `route_needs_login`, `route_store_unavailable`, `route_store_invalid`, `route_rejected`, `route_integration_unavailable` and `quota_exceeded`. Only an unlisted model or an unmapped status remains `route_unavailable`.

CHAT exposes these codes owner-side (its safe-code set). `public_dispatch_guard_missing` is retired for the route models of MODEL15 `runStep`, CHAT `runConversation` and the GitHub VM coding runner at this pin. CHAT and the GitHub runner intentionally pin no effort, require no output cap (Grok sends Schway's default cap there) and do not reconcile `providerRequests`; MODEL15 `runStep` is the governed path for those controls. CHAT decides a failed run only by its last model call's refusal, so a survived compaction refusal cannot hide a later failure.

Evidence: `tests/s15-model-dispatch.test.ts`, `tests/s15-conversation-dispatch.test.ts`, `tests/s15-github-dispatch.test.ts` and the packed consumer `tests/s15-model-packed-consumer.test.ts` (scripted transports through the public `HostAuthSelection.store`/`fetch` seam; no network or account). Service-level tests exercise every refusal code above, token expiry with a cached choice and in a fresh process, and a lifecycle logout/sign-in that makes the cached choice foreign. They assert the five integration points explicitly: wrappers forward `call` (exact, non-null `providerRequests` and per-attempt effort; a field-picking wrapper yields `null`); refusals are rethrown or chained by identity, never copied, also through Jit's services; `catalogModel` comes from the same credential owner, is cached per process and owner, and is re-listed after an observed sign-in, an `invalid-input` or a provider rejection; `requireOutputCap` and the exact cap are set on metered routes; and the evidence equals each `HostDispatch` (kind, sequence, body SHA-256 and length of the transported bytes, effort, cap) and the exact `providerRequests`.

Upgrade fence (schway#428): this pin saves and deletes credentials under an OS-released SQLite lock. Once it writes a credential under a service identity, every older untagged lock-directory Schway build under that identity, including Jit releases that vendored `697bf40`, fails all credential saves and deletes there, token renewal included. On any host where a Jit install shares a service identity with another Jit build or a Schway CLI, upgrade them together; see [ops-service §5](../runbooks/ops-service.md#5-upgrade-and-rollback).

## Executable MODEL15-01 refinement (2026-11-03)

The opt-in implementation is `src/s15/model/`; exported TSDoc defines the executable API. This smaller implementation supersedes the proposed record/port materializer below. A protected registry binds approved selections to exact account, billing and recipient refs and ranks ordinary/difficult choices. Current POLICY intersections and every owner pin still apply. Alternatives stay inside the original account/provider/billing/recipient binding, including across later steps; account changes require new owner authority. Every step records the selection, reason, requested effort, adapter evidence, per-stream usage samples and native correlation. Requested or adapter-mapped effort is not provider confirmation.

Candidate ranking follows the current protected POLICY/pin/catalog intersection from `work.modelSelections`. A registry entry alone is not approval; an unapproved higher-ranked model cannot displace an approved eligible choice. Older consumer ports without the optional projection narrow to the current guarded baseline selection.

`runStep` composes public `createHost`, `auth.createModel`, a forwarding `Model` and `session.submit/readResult`; Schway owns loops, retries, compaction and credentials. Each stream reserves, consumes one `guardReservation` and settles through POLICY. Context retains owner decisions and labelled source refs, whose lineage must be part of the current authority. Effect tools additionally require a responsibility guard and their owning adapter's final I/O gate. Unknown earlier calls cannot be bypassed with a new step ID. Restart is reconcile-only; `reconcile` reads existing POLICY settlement facts and never recreates a native call or result. Publication requires fresh current authority, account/availability and pins.

Public VM core-tool schemas are normalized to JSON before input hashing and model forwarding, matching the current CHAT adapter; TypeBox symbol metadata is not model input. The registered tool execution closure and its owning-service guards remain intact.

No monetary amount is supplied by this implementation. Metered calls without an installed budget hold with `finite_budget_required`. The owner-authorized subscription exception uses only a protected `PolicyOptions.subscriptionModels` registry, explicit finite concurrency and finite per-work calls/steps/active-time limits. It funds inference only; actions and reads retain their prior budget requirements. Subscription spend remains unknown, and an absent monetary ceiling/charge is projected as null. Usage samples deduplicate cumulative counters within each stream; a later known sample cannot erase a different unknown stream. Conservative charges never refund on settlement.

`createModelProjectionHandler` mounts authenticated read-only `GET /s15/models?workId=...` (`s15-model-budget/v1`): installation charged/measured/unknown values per ceiling, configured subscription technical limits, route availability, pins and per-work model disclosure. Filtering the selected work never hides sibling usage against an installation ceiling. No account/billing/budget mutation or visual UI is added. `src/s15/work/` supplies the [responsibility contract](s15-responsibility-v1.md). Deterministic executable evidence is in `tests/s15-model*.test.ts` and `tests/s15-model-work-*.test.ts`, including real public-host scripted execution and SIGKILL/reopen.

MG15-P01/P02/P03 below are the historical requirements. The MODEL15-02 section above states what the adopted pin now supports and what remains a limit: internal computation and monetary pricing are still not proved. Production cost bounds/registry bindings must come from protected approved configuration; local fixtures prove no live account, host, VM or universal effect enforcement. S14 remains default; no installation is activated or migrated.

### Demonstrated limits and proposed Schway requirements

These refine #323's necessary stream guard; they do not claim its candidate is an end-to-end physical-dispatch proof. There is no new native issue edge or upstream issue created here. The smallest public-only **unexecuted** counterexamples are M15-D077–D081 in the fixture guide.

## Closed data, identity and hashing

The checked-in `$defs` are the normative exact shapes, including every fixture input/output and scalar. All properties are required, nullable values explicit, unions closed and extra keys refused. `NamedRecordV1` is a closed **type/value pair union**; a declared type must validate its actual value, including scalar types. It is not a string enum beside an unconstrained value. No implementation files are created. Proposed locations after admission: `src/s15/model-{types,validation,selection,context,reservations,schway,recovery,ports}.ts`; eventual tests `tests/s15-model-{selection,pins,disclosure,usage,recovery}.test.ts`. Primitive semantics match the pinned #320 proposal: IDs `[A-Za-z0-9_-]{1,128}`, SHA-256 lowercase 64-hex, safe nonnegative/positive integers, epoch milliseconds, canonical nonnegative decimal minor units of at most 30 digits. Exact Unicode/content bytes; no trimming, normalization, newline rewriting or redaction after hashing. Reject negative zero, overflow, fractions/nonfinite numbers, invalid Unicode, prohibited controls, duplicate JSON keys before parse loses them, accessors/prototypes/cycles/sparse arrays and credential content before ordinary persistence. Credential detection is not proof all arbitrary secrets are recognized. Protected secrets/state never enter guest/models/prompts/logs/ordinary exports.

`C(x)` is compact JSON with ASCII keys sorted by UTF-16 code units, arrays in declared order, standard JSON escaping and integer spelling, no BOM/trailing LF. `H(d,x)=SHA256(UTF8(d+'\n'+C(x)))`; omit only that containing record's own `hash`, retaining nested hashes. Domain suffixes are exactly `route.v1`, `cost.v1`, `support.v1`, `policy.v1`, `scope.v1`, `context.v1`, `proposal.v1`, `plan.v1`, `receipt.v1`, `call.v1`, `charge.v1`, `claim.v1`, `result.v1`, `facts.v1`, each after the common `s15.model.` prefix. Raw blobs/BytesV1 hash raw bytes. Canonical padded RFC4648 base64, decoded length and raw hash must agree. Hashes prove bytes, never actors, account identity, policy matching or remote occurrence. Reference sets sort by canonical UTF-8, are unique by ID within their field's catalog, and never mean wildcard when empty.
