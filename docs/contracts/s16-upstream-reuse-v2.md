# Checked upstream reuse v2

BASE16-01 #405; [ADR 0080](../adr/0080-checked-upstream-reuse-and-release-notices.md); retained [ADR 0074](../adr/0074-rakazo-reuse-and-product-convergence.md). `third_party/rakazo/provenance.json` is a closed `jit.upstream-provenance/v2` inventory. Version 1 remains historical attribution, not a current build admission. This is review metadata and byte conformance, never a work/owner authority or a legal determination for unreviewed imports.

The checked inventory includes immutable repository/commit/tree/archive SHA-256, no upstream root NOTICE at that audited pin, inert original files with exact hashes, adapted destinations with exact hashes and prominent modification notices, actual runtime import sets, reviewed package dependencies and lock hash, nested dependency/asset review, and every applicable shipped notice/license. `provenance.sha256` is the separately recorded reviewed inventory digest: editing a pin without updating the reviewed inventory seal fails. This is a visible change-review guard, not a signature or proof against a maintainer who consistently edits both. No network, install script or upstream execution is part of validation. Builds accept only regular bounded in-tree files and reject missing/changed/unlisted metadata, source, notice or dependency. A matching hash does not substitute for code/license review.

`bun run upstream:check` validates the current checkout. `buildPackage` checks before creating output and after copying it; the normal release content pin then seals those bytes. `validateArtifact` repeats v2 checks before install/adoption. A historical v1/pre-S16 release remains eligible under its original content/dependency seal; new builders cannot emit a v1/missing inventory. Older release code remains usable through its existing compatibility rules. No installed artifact is rewritten.

The authenticated `/s16/client.js` response contains the complete applicable notice/license packet as a preserved comment. The actual build graph is checked for Jit-only source and reviewed React/React DOM/Scheduler package inputs. The upstream originals are audit data and cannot enter that graph. Source/release packaging retains them and their license; no upstream runtime, telemetry or full repository is shipped.

## Worked update and rollback

1. Start an issue-specific branch from the owning current stack. Read this inventory, ADR 0074, the upstream file and its nested imports/assets/licenses. Select a full immutable commit/tree and independently verify the archive/source bytes. Download as inert data only; do not run upstream install/build scripts. The existing worked reference is Rakazo `abf3c08145a05cba92a912d6c24fdfb5f569d0e0`, archive SHA-256 `10aa4afe806a958a56fa996451466899956d7b5db9bd7b3ce06109350f7150a3`.
2. Compare the two pinned original sources against the proposed revision. Copy only selected original files into the matching commit's `third_party/rakazo/sources/<commit>/...` audit paths. Preserve each original byte and applicable license/NOTICE. Record source hash, destination hash, imported runtime specifiers, source/asset/dependency review and a concrete modification summary. Adapt only the approved helper/component surface, keeping Jit contracts and identity.
3. Preserve the prominent destination copyright/Apache/source/modified notice. Review any new nested package/asset individually; update the dependency/lock/license inventory only after its review. Record SHA-256 of the final exact inventory bytes in `provenance.sha256` (64 lowercase hex characters and newline) as an explicit reviewed change. An inventory/seal edit is visible review work, not automatic approval. Do not copy a source's network/auth/runtime assumptions to make an import pass.
4. Run `bun run upstream:check`, typecheck, the adapted feature tests and package/consumer conformance. Inspect an actual release and actual served bundle: required notices/hashes present, reference originals absent from executable input graph, no new runtime/telemetry dependency. Record tested head and actual results in the PR; do not self-merge or activate a host.
5. Worked rollback: revert the adapted file and its inventory entry together to the previous reviewed bytes/pin, then repeat the same validator and package/consumer checks. The tests demonstrate destination drift failing, byte restoration passing, and duplicate/no-op validation not modifying files. A source-only revert with stale destination hash fails. Keep still-applicable notices; do not erase attribution merely because a module was removed.

This workflow does not replace protected installation/dependency seals, S14/S15 state preservation or owner-host cutover. An exact functional release rollback still follows its service/runtime compatibility and current-authority rules. Do not confuse a license/source rollback with authorization to rewind private state or unknown effects.
