# app.conversations/v2

Implemented logic contract for BOT14-01. FR-01/19/22/23/25, NFR-05/07/11/12. See [Bot/HTTP contract](app.bots-v1.md) for authentication and receipts.

`MessageCommand = Envelope<'message.post',{conversationId:string,text:string}>`; `expectedRevision` is the conversation revision returned by query. The receipt returns immutable owner `message`, revised `conversation` and queued `reply`. Posting records one durable chat intent. Retries do not add another message, proposal or inference call. Conversations are created for Jit at setup and separately for each accepted Bot; Bot addressing has no execution semantics. The initial slice has one conversation per created Bot, with no rename/membership editor.

`conversation(actor,id)` returns `{conversation,messages,proposals,replies}`; `home(actor)` returns owner profile, team and conversation/proposal/reply projections. Chat states: `queued`, `running`, `succeeded`, `blocked` with a safe reason. Messages are plain text with service-set role/identity/time. Proposal cards are separate typed data and cannot be inferred from message markup. Every committed reply increments the conversation revision; a submit based on an older page must refresh after `stale_revision`.

`ChatPort.reply(input:ChatInput,signal:AbortSignal):Promise<ChatOutput>` is a trusted adapter seam taking bounded immutable inputs. Production `schwayChat(directory)` uses only the pinned `schway/host` artifact (`1.0.0-rc.2`, revision `2068b7139f53bd62f85c3545546724e5367588cd`), strict context, exact empty tool registry, hostedLookup off, one native turn/attempt, 60-second deadline, owner-selected route/model, independent sessions and no provider fallback. Conversation inputs are labelled untrusted sources. It offers no file/computer/browser/external-effect tools. Ordinary conversation is the owner's configured bounded conversational capability, distinct from persistent work authorization. This first slice deliberately enables no conversational web tools.

`drainReplies()` claims committed outbox intents, commits bounded sanitized output and proposals, and never issues work grants. Crash recovery blocks running replies (`interrupted_no_auto_replay`) rather than resubmitting uncertain inference. Queued intents have not dispatched and remain drainable. Native correlation/enumeration and full lifecycle/backup integration are #254/#263; no safe native replay claim is made here. The composition root serializes service processes with a local runtime lock before recovery. Concurrent command writers serialize through SQLite; a failed receipt transaction is retryable with the same key.

The opt-in root `bun src/main.ts serve --s14` uses `JIT_S14_DATABASE` (default `.local/s14/application.sqlite`), `JIT_S14_ORIGIN` (default `http://localhost:3001`, loopback HTTP only in this foundation) and non-secret `JIT_S14_ROUTES` JSON `[{"id":"selected","provider":"codex","model":"<exact-owner-selected-model>"}]`. `bun src/main.ts setup --s14 --password-stdin` provisions authentication locally. No model route is invented; empty configuration blocks setup. Existing commands without `--s14` still import the legacy root, unchanged.

Before a writable SQLite open, header inspection refuses any non-S14/unknown-format/empty/symlink store with `s14_fresh_state_required` and `choose_a_separate_JIT_S14_DATABASE_keep_legacy_installation`. It reads only the original fixed header with ordinary filesystem reads, never SQLite (including legacy WAL/SHM). No lock, host, worker, migration, chmod, import, deletion or backup operation precedes that check. A fresh distinct path is allowed alongside legacy state. Unknown S14 versions also refuse; staged upgrades/restores belong to #263.
