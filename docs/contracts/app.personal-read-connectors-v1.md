# app.personal-read-connectors/v1

LIFE14-01 logic, S14 Phase C; FR-05/12/13/17/26/28/38/39/41; NFR-07/09/10. `S14Application.personal:S14Personal` (`src/s14/personal.ts`), `personal-types.ts`, `personal-reads.ts`, `personal-protocol.ts`, `personal-vault.ts`. Introduced in schema **13**; combined fresh schema **15**, earlier unreleased 1–14 refuse without changing their bytes. No private Schway import or provider adapter: this is a Jit service connector.

The owner supplies one Google **Web application** OAuth client per installation. No shared Jit client, central service, proxy account or automatic provider/account fallback. Explicit connection scopes are a nonempty subset of either `{gmail.readonly,gmail.send}` or `{calendar.readonly,calendar.events}`. Only the selected permission URIs are requested (`include_granted_scopes=false`); a token response with missing/additional consent refuses. A read connection cannot write. A write-only connection cannot read inbox/calendar metadata. Login is always owner-performed opt-in evidence.

Setup and grants use `execute`/ordinary owner receipts. Exported command and metadata shapes are in `personal-types.ts`; HTTP payloads below are authoritative for UI integration. `personal.client.set` retry identity excludes `clientSecret` rather than storing a secret digest. Values never return in receipts or metadata. Broker-only values are AES-256-GCM sealed with per-value random IV and identity-bound AAD, over the existing `ConnectionVault` atomic 0600/0700, ownership, no-symlink, forbidden-path checks. The 256-bit key and ciphertext live outside application/native/computer/backup directories. The root protects that directory from every computer component. Key plus ciphertext possession can decrypt: this is not host-administrator isolation. Client secret, codes, state, PKCE verifier, refresh and access tokens stay out of SQLite, prompts, logs, exports, backups and boxes; fingerprinting activates at ingress and boot. Ciphertext/key are not backup artifacts.

`personal.oauth.begin` creates a 10-minute, owner-generation/connection-revision-bound flow with random single-use state and S256 verifier. `authorization(actor,flowId)` returns its owner-only authorization URL. Callback captures the code once into the vault after checking state, expiry and current consent, without depending on cross-site Strict cookies. It redirects to `/` with no code/state in the destination. The owner returns to a same-origin authenticated page and submits `complete(actor,flowId)` (POST plus CSRF). Exchange is durably claimed before dispatch; duplicate completed calls return metadata, concurrent/interrupted claims cannot exchange again, and uncertain exchange requires fresh consent. Refresh coalesces per connection and rechecks consent before vault publication; invalid_grant/401 fences reads and source descendants. There is no retry/account switch.

Self-hosted redirect: set `JIT_S14_ORIGIN=https://<owner-controlled-host>` and register **exactly** that origin plus `/s14/personal/oauth/callback` in Google Cloud's Web client. A trusted HTTPS reverse proxy forwards to Jit's loopback HTTP `127.0.0.1:3001`, preserving the configured Host/origin; callback registration must match the client and installation origin. Google and the owner's browser must accept the hostname/certificate. The browser that logs into Google must be able to reach the installation (e.g. via owner's VPN); Google sends the browser redirect, not a server webhook. Google disallows some private/internal/raw-IP redirect names: a self-hosted installation must satisfy Google's current Web redirect policy, potentially with an owned domain, valid TLS and split DNS/VPN. No central relay, OOB pasted code or browser-on-server fiction is provided. For same-machine development only, explicit `http://localhost:<port>`/loopback is supported; a remote phone's localhost is the phone, so that redirect cannot connect to the server. Proxy access/error logs must omit OAuth callback query strings and request bodies. Guided setup and error presentation belong to the Opus UI slice.

`account` is an immutable owner-supplied label, **not inferred identity**. Gmail readonly verifies `users/me/profile.emailAddress` against it before connection activation. `gmail.send` alone and Calendar scopes cannot verify a Google email identity without additional consent; these remain `accountVerification:'owner_label'`, conspicuously distinct in metadata. A different login/reauth is a new connection revision and invalidates captured grants/drafts/lineage. No extra identity/profile scope is silently requested. API traffic always uses this exact opaque connection and Gmail `users/me`, never an owner label substituted as a user selector. Opt-in self-send evidence must additionally verify Gmail readonly on the same consent; that is a purpose-specific opt-in scope, not inferred from send consent.

`personal.grant.set` binds one installation-configured resource slot to one connection and Bot generation. Bot capability ceiling must already contain the slot; connection consent alone grants no Bot access. ScopePolicy snapshots pin connection, grant and revisions in work/routine admission. Every read, token release and evidence commit intersects current owner/attempt/Bot/resource/consent. Revoking or changing a slot appends independent revision tombstones; revoked personal slots cannot fall through to another ScopePort. Full connection revocation immediately fences local reads/context/publication and later makes one remote revoke attempt. `revocation:'pending'|'confirmed'|'unknown'` distinguishes it from local denial; Google project-wide account consent revocation may also invalidate sibling Google tokens, whose next request fails closed. Never claim remote revocation from a local receipt alone.

`reads.read(attemptId,{scope:{kind:'resource',id,revision},from,to,timezone},signal?)` uses `personal_read`, a finite window (at most seven days), ordinary read budget and a call reservation per HTTP request. Gmail: INBOX list at most five messages, full message GET, bounded plain UTF-8 text and at most one small text attachment per message; HTML/binary/oversize/deep MIME is labelled missing. No attachment code or external parser runs. Calendar: exact configured calendar ID, metadata timezone and up to twenty expanded events within timeMin/timeMax, preserving all-day/dateTime/DST data. Pagination is explicitly partial, never silently complete. Remote outputs have 256 KiB caps; evidence/model results have 32 KiB caps. Timeouts abort and wait for actual transport settlement; no capacity refund on uncertain usage.

Every item carries exact source ref, provider ID, source timestamp (or explicit unknown), retrieval time, event/calendar timezone and `untrusted:true`. Sources inherit admitted memory/access provenance and an account/resource pin; transitive claims, native contexts, handoffs, reports and artifacts remain fenced after revocation. Owner memory publication alone does not grant a receiver account access. Source content, attachments and event descriptions cannot create grants, change routines/recipients or approve effects. Sources are framed as data, never executable controls. Account-private external sources also join the existing Parallel outbound private-context corpus, so attribution as external cannot make mail/attachment/event text eligible for verbatim public search/URL disclosure.

`reads.brief(actor,workId)` returns `{workId,status:'complete'|'partial'|'missing',sections:PersonalRead[]}` with source timestamps, window/brief timezone, calendarTimezone even for empty calendars, missing reasons and a 15-minute input-staleness label. An empty successful current inbox/calendar is distinct from inaccessible, omitted, partial or stale input. Routine settlement checks every granted personal input and all returned outcomes independently of model text: failures/missing/stale inputs cannot become quiet no_update, and attention remains grouped by occurrence. No model-quality/real-OAuth support claim follows from fixtures.

Protocol source/date and exact field shapes: `src/s14/protocol/google-personal.json`, checked against Google's public docs **2026-10-31**. Deterministic evidence: `tests/s14-personal-reads.test.ts`, `tests/fixtures/google-personal.json`; no live Google API call or live-evidence file access. Opus setup, brief, accessibility/device and live login evidence remain unticked.

Reconciliation with main: `reads.evidence(tx,attemptId):PersonalReportEvidence[]` supplies actually-read current excerpts to the ordinary report validator and bounded graph handoffs. The union retains `provider:'google'`, `tool:'personal_read'`, `mode:'oauth'`, opaque `personal:<sourceId>`, source timestamp/timezones and exact scope/connection pins; it does not invent Parallel/public evidence. `reads.gaps(tx,workId)` returns typed service `read` gaps with optional `personal:{scopeId,stale,missing}` metadata; `reads.failed` uses the same facts for routine settlement. Model report prose cannot bypass committed report publication. Exact owner-retained historical evidence survives Bot retirement/capability edits, while new context/tools remain generation-fenced and consent/resource/source withdrawal still removes descendants. See ADR 0057 and `tests/s14-personal-integration.test.ts`.

Personal account, snapshot-share and memory-share slots reserve one shared identity namespace, including independent revocation tombstones. The free-slot query excludes personal grants; each creation command refuses an identity owned by another port (`personal_scope_exists`, `snapshot_share_exists`, `memory_share_exists`). Deterministic integration tests cover both creation orders and stale-image restoration. This prevents setup from reinterpreting an existing scope or offering an unusable share candidate.
