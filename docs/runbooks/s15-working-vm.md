# S15 working VM server integration

This is an opt-in server module for #321, #366, #369 (automatic setup) and #370 (several working computers); S14 remains the default. Since the owner's 2026-11-03 decision the default topology is one host: the controller creates and manages the working VM as a nested KVM guest (below). Owner-supplied VMs with the JSON setup are the optional path, and the fallback where KVM is absent. Read [ADR 0067](../adr/0067-s15-working-vm-operation-and-settlement.md) and the [contract](../contracts/s15-working-vm-v1.md#implemented-server-contract-2026-11-03). It does not migrate/adopt an existing installation or run an inference loop.

## Protected composition

Create `VmStore` at a new protected absolute path, `VmManagers` over that journal and a `ConnectionVault`, `VmEnrollment` with the real authenticated-owner verifier, `WorkingVmService` with the current-work policy port, and `startVmRegistryProxy` on a protected controller port. Mount `createVmApi` behind the existing owner-authenticated ingress (including Host/Origin/CSRF checks). Never expose its actor callback, management registry or backend factory as model tools.

`VmPolicyIntegration` is the supported real POLICY15 binding. Construct it with the protected VM journal, exact VM-resource resolver, current-attempt verifier, installation-approved finite cost function and external-recipient resolver. Register `integration.adapter` and `integration.reads` when calling `openPolicyService`, and compose `integration.catalogs(baseCatalogs)` so policy guards resolve current protected VM/snapshot generations. Then pass `integration.bind(policy)` as the VM service policy port. Do not supply an allow-all port in production. A null price bound holds; this module installs no budget or standing rule.

VM reads and fixed workspace/unit setup use `reserveRead` → single-use `guardRead` → `settleRead`/`publishRead`. Content search is a fixed `rg` argv operation, never shell text relabelled read-only. Mutations use the registered `working_vm` action adapter, durable POLICY claim, final `DispatchContext.commit` and guarded publication. Large local file writes bind their entire immutable request by byte count/hash while retaining the original live callback outside the guest; this preserves POLICY's 128 KiB command bound. Lost callbacks cannot be recreated from a hash or action slip. Policy success here certifies captured VM transport/result bytes, not truth of guest output or root-proof effect compliance.

Snapshot preparation is ordinary protected management inside the admitted VM purpose. A subsequent system shell requires a current protected snapshot lineage fence. Each operation pins current VM generation; an explicitly work-pinned old VM fence remains stale after a restart, and must not be silently rebound. A new artifact destination produces a real held action reference before HTTP/guest write. Approval/effect/recipient policy stays in POLICY15; a VM actor cannot install it.

Use `WorkingVmPort.openAttempt` from the conversation executor. Pass the real policy work actor, exact VM/work/attempt, cancellation signal, and `access:'inspect'` for inspection. Use `mode:'system'` only for a trusted system-administration handler; it is exclusive and snapshots first. A plain root shell can still disrupt the guest; there is no root-proof command classifier or prevention promise under option B. Close sessions when work waits for CI/review. Never route failures to `localExecutionBackend` or a protected-host shell.

`VmSession.evidence()` returns safe metadata, not command output or credentials. Output is guest-reported. `cancel` immediately fences publication, then closes the exact unit; failed cooperative read-back retains capacity and makes the whole shared VM uncertain. Only explicit owner recovery may escalate to hypervisor stop/restore. Strong stop does not turn an unknown historical outcome into success/non-occurrence or refund policy usage.

## Jit-managed local working VM (default on KVM hosts)

Host prerequisites (controller host, Linux x86_64 or aarch64):

- KVM: `/dev/kvm` present. If the controller host is itself a VM, nested virtualization must be enabled on its hypervisor (`/sys/module/kvm_intel/parameters/nested` or `kvm_amd` reads `Y`/`1`). Without it Jit reports `vm_host_unsupported` and setup falls back to owner-supplied enrollment.
- Packages: `qemu-system-x86` (x86_64) or `qemu-system-arm` plus `qemu-efi-aarch64` (aarch64), `qemu-utils`, `cloud-image-utils`, `netcat-openbsd`, `openssh-client` and `dbus-user-session` (user bus for `systemctl --user`). No third-party binary is downloaded; only the pinned Ubuntu cloud image is fetched and its SHA-256 verified.
- QEMU identity: `install.sh --s15` creates all of this (see [s15-install.md](s15-install.md)). QEMU runs as the separate unprivileged `jit-s15-vmm` (VM15-03), a member of `kvm` with a lingering user manager, so the QEMU unit runs outside the controller's cgroup and survives controller restarts and upgrades. The controller `jit-s15` is not in `kvm`; it reaches the QEMU identity only through `sudo -n -u jit-s15-vmm -- /opt/jit-s15/libexec/jit-s15-vmm …` (the only command its sudoers rule allows). A running user manager does not pick up new groups; the installer restarts it only when it lacks them, when no VM can be running. Never run QEMU as root. Hosts without `vm.vmm` (developer and evidence hosts) keep the older single-identity mode: QEMU runs as the service user, which must then be in `kvm`.
- Disk: about 0.6 GiB for the read-only base image plus a 60 GiB sparse overlay, which must fit in free space minus the installer reserve. Keep the protected state directory within 64 characters (QMP and proxy Unix socket paths).

Protected composition passes `vm.local: {}` with `managementVault` (`S15RuntimeConfig.vm.local: true` for the explicit runtime). Then `POST /s15/vm/management {"kind":"qemu"}` registers the local manager with default sizing and `VmEnrollment.enrollLocal(owner, {id, managerId})` creates and enrolls it: verified image, overlay, generated client and guest host keys, NoCloud seed, start, pinned SSH, cloud-init completion and Docker through a bounded provisioning proxy lease, then the ordinary inventory/binding/egress checks. Capability rows: network isolation is proven by the hypervisor argv plus the refused egress probe; snapshot/stop stay unproven until an observed protected recovery. `GET/POST /s15/vm/resources` reads and edits CPU/RAM/disk for the next start; nothing is typed into config files. Normally none of this is called by hand: the automatic setup below does it.

Automatic setup (SETUP15-01): with `vm.local: true`, `setup --s15` checks the host (`probeLocalVmHost`), registers the single local manager with the default sizing, downloads and verifies the pinned image, creates the disk and keys, boots the guest, finishes first-time setup and enrolls it as the pool's default member, printing one `{"state":"s15_computer_progress","step":"…"}` line per step and then `s15_initialized` with a `computer` field (`enrolled`, `failed` with step and code, `paused`, or `fallback` with the host code). The owner types nothing. The job is durable in `vm.sqlite` (`vm_provisioning`): interrupting setup or restarting the controller is safe, because `serve` resumes the job at boot without a second VM or manager, re-verifies what exists and removes an unfinished machine directory by its exact path. The Web setup step and `/resources/computer` show the current step and elapsed time, and on failure the step, the reason, the next step and "Try again" (`/s15/forms/computer/provision`, re-run from the failed step). Failed jobs never retry on their own. Host codes and what to do: `vm_kvm_unavailable` (no `/dev/kvm`; enable nested virtualization on the parent hypervisor), `vm_kvm_denied` (the QEMU identity cannot open `/dev/kvm`; re-run `install.sh --s15`, which repairs its `kvm` membership), `vm_qemu_missing` (install the packages above), `vm_host_too_small` and `vm_disk_insufficient` (free space or use an owner-supplied VM), `vm_host_unsupported` (not 64-bit Linux). For each of these the card shows the owner-supplied enrollment form instead.

Several working computers (POOL15-01): the team's working computer is a pool. `vm.id` names the pool and its default member; every other member is an enrollment record, so no pool list is configured. "Add another computer" on `/resources/computer` first registers the computer's management (Lima instance, or a VM-scoped Proxmox token that is stored write-only) and then runs the owner-supplied enrollment below under a Jit-chosen id; without an unused adapter the enrollment refuses with `vm_management_required`, because a computer without a proven hypervisor binding never receives work. Upgrading an installation seeds each existing work's affinity from its first recorded session, so old work keeps its computer. New work goes to the ready, undrained member with the most free session room (ties to the default member); every later attempt of the same work returns to the member holding its workspace, recorded durably in `vm_affinity`. TEAM leases, snapshot fences, stop proof and uncertainty fencing are per member, so system administration or a fault on one member never stops the others. "Stop using this computer" drains a member: no new work is placed there, running work finishes and bound work keeps returning; "Use this computer again" undoes it. Removing a member and moving work between members are not supported.

Operations: the VM runs as `<name>.service` in the QEMU identity's user manager (`sudo runuser -u jit-s15-vmm -- env XDG_RUNTIME_DIR=/run/user/$(id -u jit-s15-vmm) systemctl --user status 'jit-work-*'`). Its disk, seed and QMP socket are under `/var/lib/jit-s15-vm/machines/<name>/`; the controller's keys and VM state stay in `/var/lib/jit-s15/state/runtime/vm-local/`. The registry proxy listens on `/var/lib/jit-s15-vm/control/proxy.sock`, bound by `jit-s15-vm-proxy.socket` (it starts and stops with `jit-s15.service`). Do not stop it with `systemctl` by hand while work runs; use owner recovery, which proves the stop. After a controller restart Jit re-attaches and re-verifies a running VM; after a host reboot it starts a previously running VM again and re-verifies it before admitting work. A VM stopped by recovery or restore stays stopped until the owner starts it.

Live evidence: build an exact commit on the controller as a disposable evidence identity, then `JIT_S15_X64_EVIDENCE=1 bun ops/evidence/s15-x64.ts --sha <commit>` (default cases `provision,root,apt,egress,snapshot,restart`; optional `docker`, `concurrency` and `soak` with `--soak-minutes`). It records exact build/config/image hashes under ignored `.local/s15-evidence-x64/`, keeps protected state in a short directory under the identity's home and stops the working VM afterwards. It uses no model inference, owner credential, real recipient or money.

## Owner JSON setup (owner-supplied VMs)

1. `POST /s15/vm/setup {}` returns one public-key bootstrap command. Paste it once in the new VM. It configures only dedicated public-key access, key-file permissions and stable cloud-init SSH host keys. The private key stays protected.
2. Optionally `POST /s15/vm/management` with either `{kind:'lima',instance}` or `{kind:'proxmox',baseUrl,node,vmid,token,proxy:{address,port}}`. This write-only secret input returns only `managerId`. The Proxmox token is stored in the protected vault and never returned or injected into the guest.
3. `POST /s15/vm/check {setupId,host,port?,user?,managerId?}` uses the transport defaults (port 22, user jit), observes the typed target's host key and returns `checkId`, `fingerprint`, typed address, transport profile and bounded guest-reported OS/architecture/hardware/sudo/Docker facts. Confirm that fingerprint through the VM console/management channel.
4. `POST /s15/vm/enroll {id,checkId,fingerprint,transportProfile:'ssh-sudo-systemd/v1',maxSessions?:2}` checks SSH/sudo/Python/systemd, external management and direct-egress refusal, and persists the exact target. Host-key changes refuse; no silent key replacement or config editing follows.
5. `GET /s15/vm/status?id=<id>` returns safe status/capability rows only. Missing audit/network proof is unproven, missing recovery is unavailable, and a configured adapter alone is not proven recovery. `POST /s15/vm/settings {id,maxSessions}` edits capacity without evicting or settling current work.
6. `POST /s15/vm/recover {vmId,snapshotId?}` is owner-only. It fences the VM, strongly stops it and optionally restores only a registered protected snapshot. It leaves the VM stopped; it never resumes old commands or authority. Restart/re-verification is a separate explicit owner `POST /s15/vm/start {vmId}` action. It rechecks external custody/egress and creates a new fence without resuming old work.

7. `POST /s15/vm/snapshots/retire {vmId,snapshotId}` retires only that protected recovery point. An active or uncertain system session's fence refuses retirement. Automatic policy-claimed retirement retains the latest three points by default (`snapshotRetention`, bounded 1–8), preventing a lifetime system-administration cap.

Enrollment compares the SSH guest's NIC with the independently read hypervisor NIC. Lima also requires the exact protected SSH forward. A wrong/missing binding leaves isolation unproven and recovery unavailable; pre-binding provisional registrations must be checked/enrolled again rather than silently trusted. Recovery retires old live sessions, timers and cleanup transports before strong stop; old-generation callbacks cannot fence a successfully recovered/restarted VM.

HTTP requests use bounded JSON bodies. Management secrets need the owning ingress's secret-redaction/write-only handling. Public errors/status use English/Thai i18n keys; this module supplies no visual design. The S15 UX handoff owns presentation.

## External network and VM setup (owner-supplied VMs)

This optional path applies to owner-supplied VMs for extra compute or hosts without KVM. The earlier x64 owner steps are installation-specific and live in ignored `.local/s15-jit-work-owner-steps.md` in the main checkout. For a Proxmox VM, create a new `jit-work` VM with 4 CPU/8 GiB/60 GiB and passwordless sudo. A VM-scoped Proxmox role gets only VM.Audit, VM.PowerMgmt, VM.Snapshot and VM.Snapshot.Rollback on the new VM; read-only Sys.Audit on `/` and the selected node permits all firewall activation checks. Enable Datacenter/Node/VM firewall and the VM NIC firewall flag. Outbound default is DROP with only TCP to the protected controller proxy port allowed; existing host-initiated SSH replies remain allowed. No guest-facing Jit API, management token, host mount, socket, browser profile or generic tunnel is allowed.

For a new arm64 Lima VM, use QEMU plain mode, empty mounts/networks, no agent forwarding/proxy environment propagation and a fixed SSH port. Install Python/sudo/systemd/Docker in the trusted baseline. `limaRestrictedQemu` supplies a protected QEMU wrapper that injects restricted user networking and one fixed proxy guest-forward. Set the trusted `LimaVmManagement` environment to that wrapper; specify the real QEMU UEFI firmware in the new Lima config because the wrapper changes Lima's firmware search location. Do not modify `jit-arm` or `jit-ac12-*`. Snapshot uses graceful shutdown before capture; an uncooperative guest that cannot quiesce fails rather than claiming a consistent snapshot. Strong emergency recovery may force-stop the guest.

The proxy supports anonymous apt/npm/pip/registry acquisition through owner-approved exact hosts. Each active work gets a revocable scoped proxy lease. CLI tools receive its proxy environment; tools that discard environment (sudo, Docker daemon) require explicit guest-local proxy configuration within the current work. Owner `GET/POST /s15/vm/registries` reads/replaces the exact list through the protected settings callback; replacing it closes existing tunnels. No upstream account credential is injected. Logs contain only session, destination host and byte counts. Default host lists do not include `github.com` or `api.github.com`; new hosts use protected policy and a new proxy incarnation. An exact HTTPS URL/SHA-256 bounded artifact path supplements it. TLS passthrough is destination control, not content-level disclosure prevention, and registry access may disclose workspace data.

SSH connection starts to the same enrolled endpoint are spaced by 100 ms to avoid burst failures observed with the Lima transport. This is a bounded dial queue, not an exclusive work/command lease: guest commands remain concurrent. Queue time consumes the original command deadline, cancellation and current-authority checks apply before the actual spawn, and a failed connection is never retried. The scope keeper lasts for the remaining session lifetime rather than the shorter setup-command limit.

## Validation

Run `bun test tests/s15-vm*.test.ts`, `bun run typecheck`, the full `bun test` and `git diff --check`. Integration tests use the real POLICY15 service, registered handlers/adapters and its durable ledger with scripted VM transports; lower-level tests also use opaque actor fakes, fake time and disposable local helper stand-ins; they are not VM/root isolation evidence. Real arm64 operations, guest network bypass attempts, cooperative cancellation, protected snapshot/restore and strong stop are opt-in and recorded only in ignored `.local` evidence. x64 live evidence for the Jit-managed local VM comes from `ops/evidence/s15-x64.ts` on the controller host. `tests/s15-vm-qemu.test.ts` and `tests/s15-vm-local.test.ts` cover the local manager with a fake host-command runner, fake QMP, fake `/proc` and a fake clock. `tests/s15-vm-provisioning.test.ts`, `tests/s15-vm-pool.test.ts`, `tests/s15-composition-pool.test.ts` and `tests/s15-web-computer-pool.test.ts` cover the host probe, the setup job (including a restart at every step), placement, affinity, per-member fences and the Web states in Thai and English. No paid inference, existing Jit deployment, provider/billing change or live website session is needed for these VM tests.
